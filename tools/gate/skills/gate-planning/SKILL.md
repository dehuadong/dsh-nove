# Planning

把当前对话与项目上下文整理成最少但足够的规划工件，使工作具备实施条件。先确定各项事实的项目属主，再按需让产品合同与技术探索往返收敛；不为填满文档类型而创建工件。

## 1. 确定工作项

复用当前任务、既有工作项或项目已配置的跟踪器定位本次工作项。工作项负责本次目标、交付范围、产品行为与验收、评审和批准证据，并链接长期设计的属主。跟踪器是可选配置；没有跟踪器时，当前任务会话承载本次工作项。

复用合适的既有工作项；确实需要新的规划根节点时才创建 Proposal。没有跟踪器时不要为满足格式而另建 Proposal 文件，直接在当前任务中记录范围、验收、评审与批准事实。创建或更新 Proposal 时读取 [proposal.md](./proposal.md)。

工作项直接写清本次产品行为、范围和验收。本项目不使用独立 Spec；跨工作项持续生效的合同由工作项拥有，长期技术设计与决定写入 Agent Note。proposed Note 承载实施前设计评审，工作项从自身链接到 Note。Note 的位置、格式与生命周期遵循 `write-agent-notes`；写或迁移 Note 时使用随本技能提供的 `write-agent-notes.md` 方法。不得要求为定位本次工作项配置 Issue tracker。

## 2. 收敛产品合同与技术设计

### 产品合同

产品行为、范围与验收由本次工作项写全；本项目不建立独立 Spec。跨工作项持续生效的合同由工作项拥有，并在相关 Note 中链接，不复制成第二套合同。

### 探索性设计

当技术可行性会实质影响产品范围时，读取 [技术设计检查项](./rfc.md)，在 proposed Note 中形成探索草案。

探索草案必须区分产品事实与临时假设，把影响产品范围的结论反馈给工作项，不得作为实施依据。

产品合同与探索草案可以往返修改，直到范围与验收不再依赖未解决的技术可行性问题。

### 技术设计定稿

需要解决重要技术决定时，使用 [技术设计检查项](./rfc.md)，把已确定的产品合同转成 Agent Note 中的技术设计；一份产品合同可以由多个边界明确的 Note 分别承接。

设计定稿遵循 [技术设计规则](./rfc.md) 的合同稳定性与评审条件。Note 的 proposed/implemented 表示交付生命周期，不代替评审和批准证据。

使用项目既有领域语言和适用架构约束。领域术语与模型变化使用 `domain-modeling`；需要为架构决定单独建档时，使用 `adr` 的准入条件判断，在相关 Agent Note 中记录决定。

### 决定权限

在已同意的产品合同、既有架构和项目约束内，自主解决普通技术选择。

涉及未解决的产品、业务、兼容性、成本、风险、架构方向或其他价值判断时，交由用户决定，除非用户已经明确委托决定权。

## 3. Review findings

Plan Review is owned by the gate's `gate-plan-review` worker; do not run it here.

gate 返回发现后，逐条决定其属主并在对应工件修正：产品范围与验收回到工作项，本次规划的技术设计回到 Agent Note，工作状态与批准证据回到工作项。引用输入的问题按项目配置反馈其属主，并报告受影响范围。不得自行宣称整体通过。

## 4. 完成与交接

Planning 完成需要同时满足：

- 产品范围和验收条件已经稳定；
- 实施所需设计已按项目约定接受或批准；
- 设计完整承接工作项产品合同；
- 所需决定已解决；
- gate 的 Plan Review 报告没有未解决发现（由 gate 提供，不由本 worker 自行宣称）。

若用户只要求规划，交付规划结果与评审证据后结束。端到端任务把 receipt 交回 gate；执行授权由 gate 单独核对，不在本 worker 内推进。
