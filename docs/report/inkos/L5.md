# InkOS 机制研究：L5

专题：内容依赖、历史修订与一致性传播｜2026-10-21

本轮继续独立研究 InkOS，以 `master` 分支的实际代码为依据，分析历史章节发生变化后，整个作品系统如何处理内容依赖。

重点不是提出理想化设计，而是回答：InkOS 现在究竟实现了什么、依赖如何传播、状态如何处理、哪些一致性风险仍然存在。

## 一、本轮最重要的源码发现

本次已经定位到关键实现：

[packages/core/src/pipeline/runner.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/pipeline/runner.ts)

历史章节修订逻辑明确包含以下处理：

1. 读取目标章节前一章的运行状态快照。
2. 使用修订 Agent 生成新正文。
3. 基于修订后的正文重新计算状态变化。
4. 执行状态一致性校验，必要时尝试协调恢复。
5. 对目标章节之后的全部章节写入 `upstream-revision` 审阅标记。
6. 如果修订的是最新章节，则可以更新当前作品状态；如果修订的是历史章节，则只提交该章正文和章节索引，不倒退当前运行状态。

这里有一个尤其重要的细节：

InkOS 当前具备“历史修订后的后续章节批量风险标记”，但这不等于具备“精确识别受影响章节并自动完成一致性修复”。

源码中的 `upstream-revision` 标记附带的是通用连续性复查提示，`evidence` 为空，而不是逐项列出受影响的人物、事件、伏笔或因果关系。

这一点使 L5 的研究方向变得非常明确。

## 二、L5 总体研究模型

根据 runner.ts 的已验证代码绘制。右侧体现风险通知，不表示已经实现自动依赖图传播与修复。

这条路径体现两项已有能力：防止历史修订直接污染当前运行状态，以及向后续章节传播连续性风险信号。

但也留下核心问题：旧状态、旧摘要、旧索引与新正文之间的一致性如何最终恢复？

## 三、L5.1：历史修订的基线管理

### 3.1 为什么需要前一章 Snapshot

假设一部小说已完成 50 章，现在修改第 18 章。

如果用第 50 章的角色状态去重新计算第 18 章，就会产生时间倒置：角色可能已经知道第 30 章才揭露的秘密，或者已经获得第 40 章才得到的物品。

InkOS 采用的处理方式，是从目标章节的前一章加载结构化快照。

`loadRuntimeStateSnapshotAtChapter()` 实际读取：

```
story/
  snapshots/
    17/
      state/
        manifest.json
        current_state.json
        hooks.json
        chapter_summaries.json
```

该函数分别用对应的 Schema 解析这些内容，并要求四项齐全；缺失时抛出错误，而不是回退到当前状态。

源码：[runtime-state-store.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/state/runtime-state-store.ts)。

这意味着历史章节修订有一个清晰的时间边界：

第 N 章的候选新状态必须建立在第 N−1 章的历史快照上，而不能用最新状态直接推导。

### 3.2 Snapshot 的保护范围

| 对象                       | 在快照中的作用        |
| ------------------------ | -------------- |
| `manifest.json`          | 结构化状态的版本与元数据约束 |
| `current_state.json`     | 截至该章的世界及角色运行状态 |
| `hooks.json`             | 截至该章的伏笔状态      |
| `chapter_summaries.json` | 截至该章的章节记忆      |

但快照是一个历史时点的状态集合，并不天然包含完整的因果关系图。

例如，快照可能表明某个角色已经获知秘密，却未必能表示“这个认知状态具体依赖第 18 章哪一句正文”。

研究判断：InkOS 实现了时序基线隔离，但不能据此认定已经实现细粒度语义依赖追踪。

## 四、L5.2：内容依赖究竟分几种

历史修订所引起的依赖，可以区分为五个层级。

| 依赖类型 | 示例                    | InkOS 当前可见的处理  |
| ---- | --------------------- | -------------- |
| 文件依赖 | 章节正文与章节索引             | 修订时同步更新        |
| 状态依赖 | 第 18 章事件改变人物状态        | 重新计算目标章节状态     |
| 时间依赖 | 第 19 章应以第 18 章结束状态为起点 | 基于前一章快照计算      |
| 语义依赖 | 第 35 章回忆第 18 章的一次承诺   | 后续章节统一标记复查     |
| 派生依赖 | 摘要、检索索引、上下文引用旧正文      | 尚不能证实完整自动失效与重建 |

文件依赖和时间依赖比较适合程序直接处理。

语义依赖复杂得多，因为它可能并不涉及相同的人物名称或关键词。

例如：

> 第 18 章取消了一次救援行动，但第 35 章仍写着“他始终记得那夜舍命相救的人”。

后续章节既可能没有直接提及“救援”，也可能用其他表达回忆同一事件。

仅靠文件路径、章节编号或关键词匹配，都无法证明依赖关系存在或不存在。

### 4.1 当前实际采用的传播策略

`runner.ts` 对目标章节以后的所有章节执行类似逻辑：

```
if (ch.number > targetChapter) {
  return {
    ...ch,
    observations: [
      ...ch.observations.filter(
        observation => observation.code !== "upstream-revision"
      ),
      {
        code: "upstream-revision",
        summary: downstreamRevisionNotice,
        evidence: [],
      },
    ],
  };
}
```

可以看出三件事。

第一，传播范围是全部后续章节。

修改第 18 章，第 19—50 章都会被标记，而不是根据实际语义依赖计算受影响子集。

第二，传播的是审阅风险，不是正文修复。

标记只表示后续章节需要重新检查连续性，不代表这些章节已经被修改。

第三，它不是完整的版本依赖记录。

标记并未提供来源修订版本、具体依赖事实、旧值与新值、证据位置等信息。

因此，将这种机制称为“保守式下游风险传播”比较准确。

其优点是不会遗漏章节范围；代价是产生较多不需要修订的复查工作，而且不能保证复查时准确发现真正的语义冲突。

## 五、L5.3：历史章节修订如何影响作品当前状态

这是本轮最值得注意的实现边界。

在 `runner.ts` 中，系统明确区分两种情况：

| 场景     | 实际提交行为                                                       |
| ------ | ------------------------------------------------------------ |
| 修改最新章节 | 调用 `writer.saveChapter()`，保存重新结算的章节结果                        |
| 修改早期章节 | 使用 `commitAtomicFileSet()` 写入修改后的章节正文及 `chapters/index.json` |
| 后续章节   | 添加 `upstream-revision` Observation                           |
| 当前运行状态 | 修改早期章节时不直接回退                                                 |

源码中的注释说明，只有最新章节拥有当前事实；修改历史章节不能直接倒退实时故事状态。

### 5.1 为什么不能简单回滚最新状态

假设：

- 第 18 章，角色获得一把钥匙。
- 第 25 章，钥匙被转交。
- 第 40 章，钥匙已经销毁。
- 第 50 章，故事推进到另一个阶段。

现在修改第 18 章，让角色从未获得过那把钥匙。

如果仅把当前状态回退到第 17 章，则会丢失第 19—50 章所有已发生的事件；如果不回退，则第 25、40 章又可能引用一把已经不应存在的钥匙。

InkOS 采取的策略是：保留现有后续作品和当前运行状态，同时标记后续章节需要连续性复查。

这是一个避免破坏现有作品的策略，但并没有完成整条因果链的重新计算。

### 5.2 由此暴露的状态一致性窗口

历史正文修改提交后，至少可能同时存在：

- 修订后的第 18 章正文；
- 按旧第 18 章延续写成的第 19—50 章；
- 依据原先章节链计算的当前状态；
- 与旧事件对应的历史快照及摘要；
- 已经记录的 `upstream-revision` 风险标记。

这些信息并不必然立刻一致。

因此需要区分：

事务一致性：一次提交不会只写入一半文件。

语义一致性：所有后续章节、角色状态、伏笔、记忆都与最新正文事实相符。

InkOS 的原子文件集可以为前者提供保障，但无法仅靠原子写入实现后者。

这也是为什么“修改已经落盘”不等同于“整部作品的历史一致性已经恢复”。

## 六、L5.4：历史记忆与检索索引的一致性

在 L3、L4 中已经分析过 InkOS 的三类内容：

- 权威数据：结构化状态及章节正文。
- 派生数据：章节摘要、可读投影及上下文材料。
- 检索投影：FTS5/BM25 索引及带来源定位的检索结果。

L5 必须回答的是：当原始章节发生修订，这三类内容能否同时进入正确的版本状态？

### 6.1 检索索引可重建，不等于内容会自动失效

InkOS 2.0 的 README 明确说明，原始文件是权威来源，检索索引可以重建。

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub

+1



但是，可重建性与版本有效性是两回事。

例如，修改第 18 章后：

| 内容            | 需要确认的问题         |
| ------------- | --------------- |
| 第 18 章正文      | 是否已更新为新版本       |
| 第 18 章摘要      | 是否根据新正文重新计算     |
| 第 19—50 章摘要   | 是否可能包含旧事件的延续    |
| 当前状态          | 是否仍包含旧历史派生出的事实  |
| FTS 检索索引      | 是否移除或更新旧章节片段    |
| Composer 的上下文 | 是否仍能召回已失效的旧事实   |
| Agent 输出      | 是否能够追踪使用过哪些来源版本 |

目前的 `runner.ts` 历史章节修订分支可以证明正文和章节索引的提交，却不足以证明所有下游摘要、快照及检索投影已经重新构建。

尤其要注意：即便第 18 章的新正文已经重新索引，如果第 35 章的旧摘要仍包含过去的因果关系，检索系统仍可能从该摘要召回与最新剧情冲突的内容。

### 6.2 这属于传播问题，不只是召回问题

检索系统负责找到相关内容；但在找到内容之前，需要先回答哪些来源仍然有效。

两者是不同机制：

```
内容发生变化
    ↓
识别受影响的派生内容
    ↓
使失效结果不可继续作为有效事实
    ↓
必要时重建摘要与状态
    ↓
刷新检索投影
    ↓
Composer 只使用有效来源
```

上述为完整一致性链路的研究判定标准，并不是声称 InkOS 已经全部实现。

目前可见的关键缺口是从“发现历史修改”到“精准失效并重建所有受影响派生内容”的自动闭环尚未被证实。

## 七、L5.5：Agent 协作如何处理历史修订

根据已检查的代码，历史修订不是简单让 Reviser 直接替换文件。

其调用过程涉及多个明确的职责。

| 角色或程序模块            | 实际责任                    | 是否负责下游传播    |
| ------------------ | ----------------------- | ----------- |
| Reviser Agent      | 根据原文、修订目标、审阅结果生成新的候选正文  | 否           |
| Writer 状态结算        | 根据新正文及基线快照重新生成状态        | 处理目标章节      |
| StateValidator     | 校验新状态与章节内容是否一致          | 处理目标章节      |
| Continuity Auditor | 重新审阅修订内容，产生 Observation | 处理目标章节      |
| PipelineRunner     | 决定提交路径，更新章节索引和后续风险标记    | 是，保守式传播     |
| Context Composer   | 为后续 Agent 编译上下文         | 需要验证如何处理旧版本 |

这个划分说明 InkOS 已经实现了相对清晰的角色与执行职责分离。

但有一个值得继续验证的问题：当 Agent 后续收到 `upstream-revision` 标记时，该标记是否会自动触发特定的复审任务？还是只出现在章节元数据中，等待用户或者另一个动作显式调用？

当前代码能够证明标记被写入，不能仅凭标记存在就认定后续 Agent 会自动执行复查。

## 八、L5.6：恢复机制与事务边界

历史修订过程中，还存在两个不同的恢复问题。

### 8.1 状态恢复

此前 InkOS v0.4.5 存在一个第一章重写问题：由于没有 Chapter 0 快照，重写第一章时旧状态没有正确清空。项目变更日志记录，v0.5.0 已通过初始化 snapshot-0 处理这一问题。

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub

+1



这说明基线快照并不是可有可无的缓存，而是历史重算的前提。

本轮当前源码也印证了这一点：缺少目标章节前序结构化快照时，安全修订流程直接失败。

### 8.2 事务恢复

InkOS 使用原子文件集、工作区和写入锁降低部分落盘和并发问题。

但在当前历史修订代码中，`archiveChapterVersion()` 与之后的原子文件集提交是两个可见的操作步骤。因此，不能把该流程理解为“版本归档、正文替换、所有派生数据更新、风险清除在一个全局事务中完成”。

这里至少需要区分：

| 保障层次            | 当前判断                        |
| --------------- | --------------------------- |
| 单次文件集的原子提交      | 有明确代码实现                     |
| 历史正文版本留存        | 有 `archiveChapterVersion()` |
| 缺失基线时拒绝继续       | 有明确实现                       |
| 并发章节写入保护        | 有锁机制                        |
| 修订后自动重算全部后续状态   | 未证实                         |
| 历史修订全过程的全局事务    | 未证实                         |
| 崩溃后恢复到全作品语义一致状态 | 未证实                         |

因此，InkOS 的故障恢复机制和语义依赖恢复机制不能混为一谈。

## 十一、研究结论：InkOS 的 L5 属于哪种机制

可以把内容依赖处理区分为三个层次。

第一层

局部一致性

保证目标章节与其状态计算有明确的基线，并通过校验。

InkOS 已有明显实现

第二层

保守式风险传播

上游变化时，标记全部后续章节，避免把潜在问题当成已消失。

InkOS 已有明确实现

第三层

语义依赖的精准传播和修复

识别具体受影响事件、章节、摘要与状态，失效后重建并复验。

尚未证实完整实现

本轮的统一判断是：

InkOS 已具备历史时点重算、局部状态校验、版本归档和向下游传播风险的技术基础，但当前观察到的依赖传播以章节范围为粒度，尚不能证明已经形成事件级、角色级、伏笔级的精准依赖图及自动修复闭环。

这一结论也修正了一个容易产生的误解：InkOS 对历史章节的 `upstream-revision` 处理不是完全没有依赖传播，而是采用了保守式传播；其能力边界在于传播的精度和后续恢复是否自动闭合。

## 十二、下一轮适合研究什么

经过 L1—L5，当前剩余的关键问题已经相当集中。建议下一轮进入 L6：Runtime Skill、专业资源与 Agent 实际执行链。

可以选取一次 Writer 创作、一次 Reviewer 审稿、一次 Reviser 历史修订，逐函数检查 Skill 的发现、激活、资源读取、提示词拼装、工具注入、上下文来源与执行结果。

这样能够回答：InkOS 的专业知识究竟只是放在资源文件里，还是每个 Agent 确实在正确的时机、以正确的版本、按照明确的执行合同使用了它。

本轮源码依据： [PipelineRunner](https://github.com/dehuadong/inkos/blob/master/packages/core/src/pipeline/runner.ts)、[Runtime State Store](https://github.com/dehuadong/inkos/blob/master/packages/core/src/state/runtime-state-store.ts)、[Chapter Workspace](https://github.com/dehuadong/inkos/blob/master/packages/core/src/state/chapter-workspace.ts)、[CHANGELOG](https://github.com/dehuadong/inkos/blob/master/CHANGELOG.md)。
