# InkOS 创作系统机制研究：从工作流到数据库检索与长期记忆

这次先独立研究 InkOS，不急于讨论 Novel 应该怎么实现。

我查看了 [InkOS 仓库](https://github.com/dehuadong/inkos) 当前 `master` 中的 `packages/core`，包括 Agent、状态 Reducer、SQLite 检索、记忆召回、上下文编译、审阅、剧情预演、任务执行记录和中断恢复等实现。

一个重要发现是：InkOS 值得研究的，不只是多个 Agent 如何分工，而是它如何将创作过程组织成“权威数据 → 检索与上下文 → Agent 执行 → 证据审查 → 状态更新 → 可恢复记录”的系统。

## 一、完整的机制分类

你图片中的 6 个基础机制和 7 个扩展方向都值得保留。在进一步查看源码后，我建议将 InkOS 的研究范围整理为 15 个机制，分成四组。

| 分组    | 机制                 | 重点研究的问题            |
| ----- | ------------------ | ------------------ |
| 创作生产  | 1. Agent 任务编排      | 如何分工、调度、交接、避免重复劳动  |
| 创作生产  | 2. 创作生命周期          | 从构思、规划、创作到定稿如何推进   |
| 创作生产  | 3. 场景、读者承诺与节奏      | 如何避免注水、重复情节和无效推进   |
| 数据治理  | 4. 结构化状态与 Reducer  | 什么是事实，什么是变化，如何防止矛盾 |
| 数据治理  | 5. 伏笔与人物连续性        | 如何追踪承诺、知识、关系与事件    |
| 数据治理  | 6. 权威资料与派生视图       | 如何避免多份资料相互冲突       |
| 检索记忆  | 7. 数据库索引与精准召回      | 如何快速找回几十章前的资料      |
| 检索记忆  | 8. 上下文编译与 Token 预算 | 如何只给 Agent 当前需要的信息 |
| 检索记忆  | 9. 外部素材导入与检索       | 如何利用小说、参考资料和研究素材   |
| 质量治理  | 10. 审阅证据与精准修订      | 如何证明问题存在并避免扩大修改    |
| 质量治理  | 11. 跨章节质量趋势        | 如何识别长期节奏、情绪和质量问题   |
| 质量治理  | 12. 创作方向预演         | 如何比较剧情路线而不修改正式作品   |
| 运行可靠性 | 13. 任务输入输出契约       | 如何确保 Agent 交付可验收   |
| 运行可靠性 | 14. 执行轨迹与中断恢复      | 如何避免重复执行、丢失进度      |
| 运行可靠性 | 15. 失败诊断与可观测性      | 如何知道任务为什么失败、如何继续   |

其中最值得深入理解的是第 7、8 两项，因为它们决定了长篇小说增长后，Agent 是否还能准确使用早期信息。

## 二、数据库索引与长期记忆：InkOS 实际怎么做

这部分不是猜测。InkOS 已经存在对应实现：

- [retrieval/local-search.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/retrieval/local-search.ts)
- [utils/memory-retrieval.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/utils/memory-retrieval.ts)
- [materials/retrieve.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/materials/retrieve.ts)

### 1. 它采用的是 SQLite FTS5，而不是默认依赖向量数据库

权威数据源

章节摘要 · 结构化伏笔 · 卷摘要 · 外部素材

SQLite FTS5 检索索引

中文分词 · 关键词匹配 · BM25 排序 · 来源定位

候选召回与语义筛选

根据当前创作任务，选择真正有关联的记忆

当前 Agent 的任务上下文

相关事实、伏笔、摘要与可追溯来源

这里需要区分三种技术：

| 技术               | 解决什么问题       | InkOS 当前情况          |
| ---------------- | ------------ | ------------------- |
| SQLite 普通表与索引    | 精确存储、过滤、关联数据 | 已使用                 |
| SQLite FTS5 全文检索 | 根据关键词召回相关文本  | 已实现                 |
| Embedding 向量检索   | 根据语义相似性召回文本  | 本次所检查的这条检索链未见向量索引实现 |

InkOS 的“语义筛选”是另一层机制：从候选文本中选择与任务相关的资料，不代表底层一定采用 Embedding。

### 2. 为什么需要全文检索？

假设一部小说已经写到第 168 章。

Writer 准备写一段剧情：

> 男主再次见到曾经救过自己的陌生女子。

这个人物可能只在第 12 章短暂出现，第 48 章有过间接提及，第 126 章出现一条相关线索。

如果只读取最近十章摘要，Agent 很可能不知道她的历史。

全文检索可以根据人物名字、身份、曾发生的事件和当前任务目标，召回较早的记录。

不过，检索解决的是“找得到”，不是自动保证“理解正确”。例如角色化名、同义表达、隐藏身份和隐含因果关系，都可能让词法检索遗漏重要信息。这也是 InkOS 后续需要语义筛选的原因。

### 3. FTS5 与 BM25 的具体作用

`local-search.ts` 中建立了全文检索虚拟表，查询时使用 BM25 排序，并对标题赋予高于正文的权重。

它的实现还包括：

- 使用 `Intl.Segmenter` 做分词；
- 对中文相邻汉字补充二元组合，改善短词检索；
- 根据 `scope`、`kind` 过滤不同资料类型；
- 根据内容哈希只更新变化的索引项；
- 删除已失效的索引记录；
- 使用事务确保索引更新一致。

这说明它不只是简单的字符串搜索，而是有资料类别、排序和增量维护的检索组件。

### 4. 最重要的设计：数据库不是小说的最终权威

InkOS 的注释明确说明：SQLite 索引是可以重建的检索投影。

换句话说：

- 章节摘要和伏笔状态才是权威资料。
- SQLite 存储适合快速查询的副本。
- 索引丢失时，可以从权威资料重新构建。
- 修改索引不应直接改变人物命运或故事事实。

这个原则很重要。

如果把搜索数据库同时当作最终事实库，后期遇到索引损坏、缓存过期或重建不一致时，就会很难判断哪个版本才是真的。

### 5. 它如何避免过度召回？

`memory-retrieval.ts` 不会简单地把全部命中结果交给 Writer。

它先组织三类可检索内容：章节摘要、尚未解决的伏笔，以及卷摘要。然后进行 FTS5 查询，再通过语义选择器选出真正相关的记录。

还有一个值得注意的细节：它不会因为某条伏笔的 FTS 排名很低，就永远把它排除。

当前实现会把未命中的候选也加入语义选择范围，只是给较低的排序分数。这有利于降低纯关键词遗漏，但作品很长时，也意味着候选筛选可能有额外的上下文和模型成本。

此外，`retrievalTrace` 会记录查询、候选得分和语义筛选后的 ID。因此可以回头分析：为什么某条记忆被召回，为什么另一条没有。

这比只返回一段“模型认为相关的历史”更可验证。

## 三、上下文编译：检索出来以后，如何交给 Agent？

检索出资料只是第一步。

假设一个章节需要使用 30 条历史信息，但 Agent 的上下文预算只允许使用其中一部分。如何压缩？哪些内容不能丢？

InkOS 有两层相关实现：

[context-compiler.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/harness/context-compiler.ts) 和 [semantic-context-compiler.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agents/semantic-context-compiler.ts)。

### 1. 将上下文区分为两种类型

| 类型                | 内容举例                | 处理规则     |
| ----------------- | ------------------- | -------- |
| Protected（受保护）    | 作者硬性约束、任务合同、不可违背的设定 | 不允许语义压缩  |
| Compressible（可压缩） | 相关历史摘要、检索素材、背景信息    | 可按任务目标提炼 |

假设作者明确要求“某个人物绝不能在结局死亡”，这是硬约束，不应该被模型在压缩历史时省略。

但第 12 章与第 24 章出现过的两段环境描写，如果对当前章节只有背景价值，就可以被压缩。

### 2. Token 预算是硬约束

InkOS 的上下文编译器会计算两类资料的 Token 消耗。

如果受保护资料本身已经超过预算，它会抛出错误，而不是悄悄截掉一部分；如果总内容超限，就只针对可压缩内容执行语义编译，之后再次检查预算。

这意味着保真优先于强行塞进模型上下文。

### 3. 压缩后的内容仍然要保留来源

语义编译器要求保留重要实体 ID、名称、未解决状态、因果事实、约束和来源指针。

例如：

原始资料：

> 第 36 章，谢某在城门外把一封密信交给李某，李某并未阅读，而是交给了随从。

不能被压缩为：

> 李某知道了密信内容。

好的压缩应当保留“信件发生转移”与“李某尚未阅读”两个关键事实。

因此，InkOS 的上下文机制可以理解为：

搜索负责找到候选，语义筛选负责判断关联，上下文编译负责在预算内保留关键事实。

这三者不能混为同一个“记忆功能”。

## 四、Agent 任务编排与创作生命周期

InkOS 的相关实现分布在 `agents/`、`agent/`、`harness/` 和状态模块中。

与传统的多 Agent 自由聊天不同，它更强调每个角色做什么、能操作哪些对象、用什么格式交付，以及谁能正式提交。

规划

创作

审阅

修订

结算

权威状态更新与下一轮任务准备

关键机制包括：

任务权限和职责隔离。 Writer 可以提交正文候选，但不等于它能宣布最终定稿；Reviewer 可以指出问题，但不应该直接重写作品的权威事实。不同角色的结果需要由领域操作接收和验证。

任务结果与成功状态分离。 Agent 输出了一段文字，不等于执行成功。需要验证任务所要求的材料是否产生、是否符合范围、是否有足够证据。

授权不能通过角色暗示获得。 用户同意故事方向，不等于允许重写已经定稿的几十章。执行范围与任务权限应当被明确约束。

InkOS 的 [artifact-edit-policy.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/harness/artifact-edit-policy.ts) 就在处理这类问题：受领域操作管理的文件不能被普通文件编辑路径随意绕过。

### 这里最重要的价值

不是 Agent 数量，而是角色之间的交接可以被机器检查。

如果审阅提出三个问题，修订后至少要能明确回答：改了什么、哪一项解决了、哪一项仍然存在、是否超出授权范围。

## 五、结构化状态、伏笔生命周期与事实连续性

InkOS 的 [state-reducer.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/state/state-reducer.ts) 与 [settler-tool.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agents/settler-tool.ts) 很值得结合研究。

### 1. 状态变化不是重写整份设定

例如男主与女主的关系：

人物关系的状态变化

第 15 章

彼此不信任

第 28 章

短暂合作

第 46 章

产生信赖

每次变化需要有章节事实作为依据，而不是 Agent 在人物档案中直接写下新关系。

Reducer 接收的是变化操作，例如新增事实、终止已失效事实、更新伏笔、写入章节摘要，而不是让 Agent 自由覆盖整个状态文件。

### 2. 伏笔不是普通待办事项

InkOS 的伏笔状态包括：

| 状态          | 含义           |
| ----------- | ------------ |
| Open        | 已埋设，等待发展     |
| Progressing | 出现实质推进       |
| Deferred    | 有意识地延后       |
| Resolved    | 已经回收         |
| Superseded  | 作者已正式撤销其原有前提 |

尤其值得注意的是 `mention` 和 `upsert` 的区别。

某条伏笔在第 30 章又被提到，不代表它真的推进了。只有事件造成新的认知、证据、风险或因果发展，才应该更新其状态。

另外，已经回收的伏笔不能随便撤销；作者正式废弃伏笔时需要保留历史理由，而不是直接删除记录。

### 3. 人物的知识不等于作品世界中的事实

这是实际写长篇时非常容易出现的问题。

例如：

- 读者知道幕后主使是谁。
- 男主不知道。
- 女主只知道一部分。
- 反派误以为自己的计划没有暴露。

四者都可以同时成立。

所以，长期连续性至少需要区分：

客观事件、人物知识、人物信念、信息来源与生效时间。

InkOS 已有事实、状态、来源和连续性审查机制，但上述完整认知模型不能仅凭现有 Reducer 文件就认定已经全部实现。这是值得在进一步研究中单独验证的能力边界。

## 六、审阅证据与精准修订

InkOS 的 [review-tool.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agents/review-tool.ts) 采用结构化审阅结果，而不仅是一段“总体评价”。

审阅项可以携带问题代码、判定、证据和原文来源位置。

特别值得借鉴的是四种不同的结果：

| 结果          | 含义               |
| ----------- | ---------------- |
| Issue       | 有证据支持的问题         |
| Resolved    | 已确认修复            |
| Observation | 中性观察或建议          |
| Unavailable | 缺少必要材料或执行证据，不能判断 |

这里的 `Unavailable` 很重要。

如果没有取得某章的早期版本，就不能声称“修订已经保持原风格”；如果没有检查完整上下文，就不能声称“人物关系完全连续”。

此外，InkOS 还区分了质量问题、执行问题和范围问题。

例如作者只要求调整第三场对话，但修订 Agent 顺手改变了结尾，这是修改范围越界，即使结尾写得更好，也不应视为自动获得授权。

因此值得关注的不是增加审阅项数量，而是让每项审阅都可以回答：

依据是什么？问题影响什么？需要修订多大范围？修订后如何验证？

## 七、创作方向预演：在不改变正式作品的情况下做决策

InkOS 的 [forecast/runner.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/forecast/runner.ts) 实际实现了剧情分支预演。

其过程大致是：

1. 读取当前权威故事上下文。
2. 确定一个需要分歧决策的剧情点。
3. 生成若干候选发展分支。
4. 比较分支的情节走势。
5. 保存预演结果和上下文指纹。
6. 作者选择某一分支；正式应用仍是独立操作。

例如同一个故事节点可以比较：

| 分支 | 发展方式   | 主要影响        |
| -- | ------ | ----------- |
| A  | 主角公开证据 | 快速升级外部冲突    |
| B  | 主角隐瞒证据 | 加深人物之间的不信任  |
| C  | 主角交换证据 | 引出新的利益关系和风险 |

它不只是生成三段故事简介，而是把候选发展保存为独立的预演成果，并且在基础作品改变后判断预演是否过期。

预演结果不等于正式剧情。 这是与作者确认、状态权威治理相一致的边界。

## 八、长期创作的任务恢复、执行轨迹和可观测性

这三个机制容易被混在一起，但职责不同。

InkOS 的 [episode-store.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/harness/episode-store.ts) 使用 SQLite 保存执行 Episode 和事件记录。`session-transcript-restore.ts` 则负责恢复会话消息，并处理未完整结束的工具调用。

| 机制         | 记录什么              | 解决的问题       |
| ---------- | ----------------- | ----------- |
| 任务 Episode | 任务身份、开始结束状态、执行事件  | 哪件事完成了、失败了  |
| 会话恢复       | 可恢复的对话与工具调用信息     | 宿主重启后如何恢复对话 |
| 执行证据       | 输入基线、操作记录、结果与失败原因 | 如何证明执行结果    |
| 状态事务       | 正式作品数据的原子更新       | 防止中断留下半成品   |

例如连续写十章时，第七章审阅中途宿主崩溃。

理想的恢复流程不是重新创作全部十章，而是识别前六章已定稿、第七章停在审阅阶段、哪个候选正文仍然有效，以及原有任务凭证是否已经失效。

InkOS 的 Episode、事务和会话恢复模块为这种机制提供了基础。但不能仅凭这些模块存在，就断言任何外部宿主都能无损恢复所有 LLM 执行状态。

另一个有价值的细节是：执行记录不必重复保存完整小说正文。InkOS 的 `action-observation.ts` 会提取任务结果的控制信息，正文则保留在实际作品资料中。

这样既减少重复数据，也有利于长期运行时控制上下文和日志规模。

## 九、额外值得关注但容易忽略的机制

除了前面重点介绍的内容，我认为还有四个方向值得继续研究。

| 机制        | 价值                    | 需要特别验证             |
| --------- | --------------------- | ------------------ |
| 外部素材溯源    | 保存资料出处、片段位置和用途，支持精准引用 | 外部素材是否与正式作品事实严格隔离  |
| 索引更新与失效治理 | 数据改变后自动更新或重建索引        | 是否会返回已删除、已撤销或过期的信息 |
| 任务工作集治理   | 只为当前 Agent 准备相关的对象和资料 | 过滤后是否遗漏必须遵守的作者约束   |
| 可重复的评测场景  | 使用固定样例衡量检索、创作、修订与恢复   | 是否真正测试质量，而不仅是接口成功  |

其中，索引失效治理值得与数据库检索一起研究。

例如第 80 章被重新定稿，修改了一段人物身份信息。检索数据库中基于旧摘要生成的索引必须更新，而引用该旧事实的后续任务也需要识别变化。

这里存在三个不同动作：

- 更新索引：让查询返回新版资料。
- 失效判断：识别旧召回结果不再适用。
- 依赖审查：确认下游剧情是否受影响。

数据库索引本身不能替代后两项。

## 十、综合理解：InkOS 的机制如何协同工作

作者意图与创作合同

目标、约束、已确认方向、权限

权威状态

人物、事实、伏笔、摘要、版本

检索与工作集

FTS5、语义筛选、上下文预算

Agent 任务执行

规划、写作、审阅、修订、结算

质量与状态验证

证据、因果、权限、冲突

执行证据与恢复

事件、任务进度、异常处理

受控提交新的作品状态

并更新可重建的检索索引和上下文来源

这套架构的核心不是 SQLite，也不是多 Agent，而是让不同机制形成闭环：

资料有权威 → 信息能找回 → Agent 能使用 → 结果可验证 → 状态安全更新 → 失败可以恢复。

## 十一、后续研究的优先顺序

在尚不考虑 Novel 具体实现的前提下，我建议这样排序：

| 优先级 | 机制组合                     | 为什么                 |
| --- | ------------------------ | ------------------- |
| P0  | 检索索引 + 记忆召回 + 上下文编译      | 直接关系到长篇创作能否准确找回早期信息 |
| P0  | 读者承诺 + 伏笔状态 + 剧情推进       | 直接关系到长篇内容质量与连续吸引力   |
| P0  | Agent 交付 + 审阅证据 + 安全状态提交 | 保障协作结果可靠            |
| P1  | 跨章质量评价 + 局部精准修订          | 减少重复情节和无效返工         |
| P1  | Episode + 执行记录 + 中断恢复    | 提高长时间自动创作可靠性        |
| P2  | 剧情预演 + 外部素材研究            | 增强复杂创意决策和创作辅助能力     |

另外，数据库技术选择也不需要预先锁定为“必须引入向量数据库”。

比较合理的研究顺序是：

结构化精确查询 → SQLite FTS5 → 语义筛选 → 基于召回测试判断是否需要 Embedding。

只有在角色化名、隐含语义、跨章节因果等测试中证明词法召回不足时，再评估混合向量检索的收益、成本和复杂度。

### 目前研究能得出的结论

InkOS 具备实质性的 SQLite 全文检索、结构化状态、语义筛选、Token 预算、审阅证据、预演与执行记录能力。但这些机制都有边界：全文检索不是理解，摘要不是事实权威，预演不是已确认剧情，CI 通过也不代表长篇创作质量一定达标。

下一步最有价值的工作是先研究“长期记忆和上下文管理”这条完整链路：从哪些数据需要索引、如何切分和定位、怎样召回、如何识别失效，到怎样将必要事实交给不同 Agent。

随后再以这些已经核实的 InkOS 机制为参考，审视 Novel 当前的 JS Runtime、Skill 和资源文件各自承担什么职责、哪些可以复用、哪些确实缺失。这样才能避免一开始就把功能建议变成额外的架构和文档负担。
