# InkOS 机制研究：L7

专题：内容质量控制、审阅反馈与创作效果验证｜2026-10-21

本轮继续独立研究 InkOS，不讨论 Novel 的改造实现。

研究重点从 L6 的“Skill 是否真正进入模型”推进到：专业创作方法是否转化为可执行的审阅标准，审阅问题如何驱动修订，以及修订结果能否得到有证据的验证。

## 一、核心结论

本轮通过读取 `ContinuityAuditor`、`Observation`、`ReviserAgent`、`ChapterReview`、`BaseAgent` 等源码，确认 InkOS 已形成以下基本机制：

综合各模块的逻辑闭环，并非声称所有创作入口均强制执行以上全部步骤。

但必须区分两种能力：

InkOS 已有较明确的证据化审阅、结构化问题提交、局部修订及修订后复核机制。

尚不能证明它已形成成熟的文学质量度量系统，能够持续验证人物弧光、故事节奏、读者期待等创作目标的实际达成程度。

这两者不是同一回事。

## 二、L7.1：InkOS 究竟如何定义内容质量

可以将小说质量拆分为三个不同层次。

| 质量层次  | 典型问题                 | 当前可见机制                    |
| ----- | -------------------- | ------------------------- |
| 硬性约束  | 字数、正文为空、编辑越界         | 程序校验                      |
| 叙事一致性 | 人物设定冲突、因果错误、历史连续性    | Reviewer + ContextPackage |
| 文学表现力 | 人物弧光、场景张力、节奏、悬念、读者期待 | 专业 Skill + 模型审阅           |

前两层更容易形成确定性的结果。

第三层则涉及主观但可以提供证据的文学判断。

例如，“第 18 章人物动机不成立”可以通过人物既定目标和具体台词进行分析；但“这一章读起来不够精彩”并没有天然可执行的唯一标准。

### 2.1 一个值得注意的源码事实

在 `builtin-profiles.ts` 中，内置 Profile 的 `qualityCriteria` 当前统一初始化为空数组：

```
qualityCriteria: []
```

同时，`writer-prompts.ts` 明确写明，叙事技巧来自已激活的长篇写作 Skill。

这说明在本次检查的内置 Profile 层，InkOS 并没有预置一份结构化、可由程序逐项评分的文学质量量表。

其文学规则更主要地通过 Skill、作品约束及 Reviewer 的模型判断来发挥作用。

这不是说系统没有质量审查，而是说明：

质量规则的知识表达与质量结果的机器验证，仍是不同层次的机制。

### 2.2 文学专项的研究判断

| 文学维度  | 应当验证的内容         | 已确认程度              |
| ----- | --------------- | ------------------ |
| 人物弧光  | 当前选择是否体现角色动机和变化 | 可依据上下文审阅，未见独立弧光验证器 |
| 故事节奏  | 冲突推进、信息释放和情绪起伏  | 可模型评价，未见明确的程序量化规则  |
| 场景设计  | 目标、阻力、行动、结果和转折  | 可依赖 Skill，专项执行仍需验证 |
| 读者期待  | 期待建立、延迟、兑现和反转   | 尚未证实独立跟踪机制         |
| 叙事连续性 | 事实、人物状态及因果是否冲突  | 已有专门 Auditor       |
| 修订范围  | 是否修改了授权范围以外的内容  | 已有代码级证据约束          |

因此，不能因为 InkOS 拥有专业写作和审阅 Skill，就直接推断它已经可以对每一章的文学价值进行稳定、可重复的量化评分。

## 三、L7.2：Reviewer 如何输出真正有证据的问题

这是本轮源码验证最充分的环节之一。

`ContinuityAuditor.auditChapter()` 接收正文、章节编号、语言和 `ContextPackage`，并将正文与选定的权威上下文组成审阅来源。

它并不是简单要求模型输出几段点评，而是要求提交结构化审阅结果。

### 3.1 Observation 的核心结构

根据 `review-tool.ts` 和 `observation.ts`：

```
{
  code: string,
  summary: string,
  assessment:
    | "issue"
    | "resolved"
    | "observation"
    | "unavailable",
  category?: "quality" | "scope" | "execution",
  sourceRefs: [
    {
      sourceId: string,
      startLine: number,
      endLine: number
    }
  ]
}
```

这里有三个重要设计。

第一，审阅判断与事实证据分离。

`summary` 说明发现了什么，`sourceRefs` 指出正文或上下文中的证据来自哪里。

第二，问题和已解决不是同一种状态。

`issue` 表示存在问题；`resolved` 表示审阅认定相关问题已解决；`unavailable` 表示缺乏必要来源或执行证据，不能直接判定内容有错。

第三，内容质量、执行行为、授权范围被明确区分。

- `quality`：文学内容或叙事一致性问题。
- `scope`：修改是否超出作者授权范围。
- `execution`：某项执行操作是否完成。

这避免了把“修订超范围”误称为文学质量差，也避免用正文叙述推测工具是否成功执行。

### 3.2 引用来源由程序验证

`resolveObservationSources()` 负责将模型选择的来源行号解析为原始文本片段。

它会拒绝以下情况：

- 来源 ID 不存在。
- 行号越界。
- 选择的范围只有空白。
- 引用内容与提供的来源不一致。
- 非 `unavailable` 观察缺少来源引用。

换句话说，模型不能仅凭自己编造的一段话，就提交一条看似有证据的正常审阅发现。

示例：有证据的叙事问题

以下为研究示例，不是 InkOS 实际运行输出。

角色行为与既定动机冲突

issue

第 12 章角色明确拒绝背叛盟友，但第 14 章突然主动出卖盟友，正文未提供足够的动机转折。

来源 A：第 12 章相关对话

来源 B：第 14 章实际行动

但也有一个边界：程序能验证引用确实出现在原始资料中，却不能仅靠字符串或行号验证“这段证据在文学上是否充分支持结论”。

来源真实性已经获得程序保障；判断合理性仍依赖审阅模型。

## 四、L7.3：审阅发现怎样驱动修订

从源码来看，InkOS 支持不同修订模式，而不是简单使用同一个“重写整章”指令。

| 修订模式          | 允许改变的内容     | 主要控制方式       |
| ------------- | ----------- | ------------ |
| `polish`      | 文字表达        | 保留故事事实、事件与因果 |
| `rewrite`     | 受影响段落；必要时整章 | 修订协议与结果校验    |
| `rework`      | 场景结构、冲突设计   | 在给定权威范围内重构   |
| `spot-fix`    | 指定局部文本      | 行范围合同与结构化替换  |
| `anti-detect` | 文字表面表达      | 保留剧情事实与因果    |

### 4.1 普通修订流程

```
原章节
   ↓
已有 Observation 或用户修订指令
   ↓
Reviser 读取权威 ContextPackage
   ↓
生成修订后的正文
   ↓
字数及内容有效性校验
   ↓
状态重新结算
   ↓
状态一致性验证
   ↓
重新进行审阅
   ↓
记录新版本及 Observation
```

`runner.ts` 中，修订后的正文重新交给 Writer 结算状态，并经过 StateValidator 检查。

这说明审阅、修订、状态验证并不是完全孤立的三个功能。

### 4.2 `spot-fix` 的精确修订机制

这是比较成熟的程序约束。

在 `ReviserAgent.submitSpotFix()` 中，模型首先提交需要修改的原始行范围：

```
submit_chapter_edit_ranges
```

随后调用：

```
textRangeEditContract(
  originalChapter,
  result.ranges
)
```

接着模型只能提交被选择区域的替换文本。

程序负责将替换内容应用到原文，并保留所选范围以外的字节。

如果修改后的篇幅不符合合同，程序拒绝这次候选结果，而不是先修改原文件再尝试恢复。

由此可以确认：

InkOS 的局部修订已将“只修改指定内容”部分转换为程序可验证的合同，而不完全依赖模型遵守提示词。

### 4.3 但修订模式仍有不同强度

`spot-fix` 的保护能力比普通 `rewrite` 更强。

对于普通整章重写，程序可以检查空正文、字数、状态与审阅结果，但仅凭这些验证不能保证所有未授权的语义变化都被发现。

因此需要将“局部修改的文本边界完整性”与“全章修订的语义忠实性”分开评价。

## 五、L7.4：修订后是否真正重新审阅

本轮从 `runner.ts` 追踪到：修订后重新调用审阅，并将所得观察与状态验证观察组合。

关键对象为：

```
const postRevisionObservations = [
  ...postRevision.observations,
  ...stateValidation.observations
];
```

实际代码还处理状态不一致且缺乏具体 Observation 时的兜底提示。

随后：

```
const remainingObservations =
  postRevisionObservations;
```

最后保存到目标章节的索引元数据中。

### 5.1 已经闭合的部分

可以确认存在：

修订候选生成

已实现

修订后再次审阅

已实现

状态重算与验证

已实现

记录修订后的 Observation

已实现

但这里还有一处重要区别。

重新审阅不等于逐条证明旧问题已经解决。

例如，第一次审阅有三个问题：

- A：人物动机冲突。
- B：场景转折过快。
- C：伏笔解释不充分。

修订后新的审阅只发现问题 D，并不逻辑上证明 A、B、C 都已经解决。

为了证明 A、B、C 已解决，需要建立旧 Observation 与修订版本、新证据、新判断之间的关系。

当前的 Observation 结构虽然支持 `assessment: "resolved"`，但这不足以证明系统已对所有旧问题实现稳定的逐项追踪。

### 5.2 审阅失败如何处理

`chapter-review.ts` 在正常写章时捕获审阅异常，返回 `review-unavailable`，并保持原始正文。

因此：

- 审阅确实会被调用；
- 审阅不可用会被记录；
- 不能认定所有审阅失败必然阻断正文提交。

这说明 InkOS 更偏向将一部分文学审阅结果作为可观察的问题记录，而不是为所有文学质量问题设置强制中止条件。

## 六、L7.5：质量反馈能否跨章节累计

这一部分需要结合 L5 的历史修订机制理解。

目前可以确认：

- 章节索引可保存 Observation。
- 历史修订可向后续章节传播 `upstream-revision`。
- 后续任务可以通过章节与上下文机制获得相关历史信息。
- Skill 注入和上下文编译有可记录的执行证据。

但这些机制尚不能直接证明 InkOS 已建立完整的长期质量反馈模型。

例如，连续五章出现“人物行动缺少充分动机”，系统能否识别这是同一种持续性写作问题，并在第六章创作之前主动注入针对性的创作方法？

目前检查到的代码并不能充分回答这个问题。

### 6.1 应区分三个反馈层级

| 反馈层级    | 目标               | 研究判断              |
| ------- | ---------------- | ----------------- |
| 单章反馈    | 发现当前正文的问题        | 已实现               |
| 修订反馈    | 修改后检查是否还有问题      | 已实现，但旧问题逐条关闭需继续核实 |
| 跨章节质量学习 | 汇总反复出现的问题并影响未来创作 | 尚未证实              |

第三层尤其涉及长期文学风格、节奏与叙事技巧的持续调整。

如果只是不断累积 Observation，而没有稳定的跨章节分类、趋势汇总和反馈注入，就还不是完整的质量学习闭环。

## 七、L7.6：文学质量能否真正验证

下面将用户关心的五个文学领域逐一与当前机制对照。

| 文学领域  | 可形成的证据          | 当前实现边界                       |
| ----- | --------------- | ---------------------------- |
| 人物弧光  | 动机、选择、代价、角色变化   | 可以审阅具体事件，未证实全书弧光追踪           |
| 故事节奏  | 章节推进、冲突变化、信息密度  | 主要依赖模型判断，未见专门节奏检测模型          |
| 场景设计  | 场景目标、冲突、行动、结果   | 可按 Skill 审阅，缺少独立完成状态模型的证据    |
| 读者期待  | 承诺建立、悬念延迟、兑现、反转 | 可以借助伏笔资料，未证实完整期待生命周期验证       |
| 文风一致性 | 叙述人称、角色声音、表达习惯  | 有 Style Guide 及权威约束，语义评价依赖模型 |

这里特别需要区分：

作品事实的一致性检查与文学创作目标的完成度检查。

例如，角色从懦弱走向勇敢，即使没有任何设定冲突，也可能因为变化缺乏铺垫而导致人物弧光不成立。

又如，章节没有时间线错误，却可能连续十章缺少真正的情节推进。

这类质量问题不是单纯依靠 StateDelta、Snapshot 或来源一致性校验就能发现的。

InkOS 已提供专业 Skill 和有来源的审阅能力，但还不能把这些能力等同于完整的文学目标追踪系统。

## 九、本轮最重要的三个认识

### 1. InkOS 的审阅体系已经不只是自由文本点评

通过 Observation Schema、来源定位、证据解析与模型结果工具，审阅发现可以成为结构化且可追溯的产物。

尤其是对原始来源行号、文本引用真实性的验证，比只要求 Agent“给出修改建议”更有实际执行价值。

### 2. 修订流程有程序约束，但质量判断仍依赖模型

局部修订、篇幅检查、状态结算可以通过程序直接约束。

人物动机、情绪变化、节奏快慢、读者期待等文学问题，则不能只依靠 Schema 保证判断正确。

因此 InkOS 的质量机制可以理解为：

程序保证结果有结构、来源可信且操作受控；模型负责判断内容问题和文学表现。

### 3. 当前质量反馈更偏向任务闭环，而非持续学习闭环

InkOS 已具备：

`创作 → 审阅 → 修订 → 复审 → 记录`

但要进一步形成：

`反复问题 → 质量趋势 → 创作策略调整 → 后续章节验证 → 全书质量评估`

仍需要更多机制证据。

这两条链路的差别，正是 L7 的核心结论。

## 十、L1—L7 累计研究结论

| 层级 | 研究主题          | 目前最重要的发现                   |
| -- | ------------- | -------------------------- |
| L1 | Runtime 与执行底座 | 统一 Harness、结构化 Action、执行控制 |
| L2 | 记忆、上下文及检索     | 来源可追踪、上下文按任务组织             |
| L3 | 作品内容组织与权威     | 设定、规划、正文、状态等承担不同语义         |
| L4 | Agent 协作与交接   | 专业角色具有不同输入输出与执行责任          |
| L5 | 依赖与历史修订       | 历史基线和保守式下游风险传播已实现          |
| L6 | Skill 与专业资源   | Skill 有真实加载、检索、注入和执行证据机制   |
| L7 | 内容质量与反馈       | 证据化审阅与受控修订较明确，长期文学效果闭环尚未证实 |

综合来看，InkOS 最成熟的部分是生产过程可执行、内容来源可追踪、修订操作可约束。

需要继续深入验证的，则是内容语义依赖的精准传播，以及文学质量目标在多章节创作中的持续跟踪与反馈。

## 十一、研究结论与源码依据

本轮完成了 L7 的主要机制研究，并识别出一个明确的后续研究缺口：文学质量不仅需要审阅工具，还需要能够将叙事目标与实际章节表现持续关联的机制。

主要依据：

- [ContinuityAuditor：证据化审阅](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agents/continuity.ts)
- [Observation：问题及来源校验](https://github.com/dehuadong/inkos/blob/master/packages/core/src/models/observation.ts)
- [Review Tool：结构化审阅合同](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agents/review-tool.ts)
- [Reviser：修订模式及局部编辑](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agents/reviser.ts)
- [Chapter Review：常规章节审阅](https://github.com/dehuadong/inkos/blob/master/packages/core/src/pipeline/chapter-review.ts)
- [PipelineRunner：修订后状态校验与复审](https://github.com/dehuadong/inkos/blob/master/packages/core/src/pipeline/runner.ts)

至此，InkOS 的 L1—L7 第一轮总体机制研究已经形成完整的主题覆盖。

下一阶段更适合对这些研究结论做一次横向整合：区分实际已经实现的机制、仅有部分实现的机制、尚未得到证据支持的机制，并还原从作品创意到定稿的端到端内容生产链路。这样可以避免各层研究分别成立，却忽略跨层调用时的实际断点。
