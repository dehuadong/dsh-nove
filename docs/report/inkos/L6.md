# InkOS 机制研究：L6

Runtime Skill、专业资源与 Agent 实际执行链｜2026-10-21

本轮继续独立研究 InkOS，不讨论 Novel 的改造方案。研究目标是验证：Skill 如何从静态文件变成真正被 Agent 使用的专业能力，以及它与 Runtime、作品上下文、工具权限之间的实际关系。

## 一、核心发现

本轮已核查 `master` 分支中的 Skill 激活、资源加载、Worker 上下文编译和 Agent 调用代码。

与前几轮不同，本次找到了能够直接回答关键问题的实现：

InkOS 不只是保存了一批 SKILL.md；它确实在 Worker 模型调用之前读取已激活 Skill、检索相关参考材料，并将专业内容注入模型输入，同时记录 Skill 和资源的执行证据。

具体实现涉及：

- [builtin-profiles.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/harness/builtin-profiles.ts)：Profile 与必需 Skill 的绑定。
- [activations.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/skills/activations.ts)：解析、合并及检查 Skill 激活。
- [skill-tool.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agent/skill-tool.ts)：`use_skill`、资源读取与按任务检索。
- [base.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agents/base.ts)：模型调用前的 Skill 注入与上下文编译。

不过，需要区分三个不同级别的证据：

| 证据层级                      | 本轮结论        |
| ------------------------- | ----------- |
| Skill 文件存在                | 已确认有加载体系    |
| Skill 内容实际进入模型调用链         | 已确认有代码路径    |
| Agent 在文学决策中正确执行 Skill 方法 | 仅凭注入代码还无法证明 |

第三层最重要，也最容易被误判。模型收到写作指导，不等于模型已经按指导完成了人物弧光、节奏控制或场景设计。

## 二、InkOS 的 Skill 执行架构

这个结构不是单纯的 Prompt 拼装。其中特别值得研究的是两个独立的 Skill 激活入口：

交互式激活：模型调用 `use_skill` 工具，按当前用户意图选择技能。

生产式激活：作品 Profile 与当前 Work 决定必需技能，Worker 在模型调用前自动加载它们。

两种方式最终都可形成 `ActivatedSkillGuidance`，但触发时机和来源不同。

## 三、L6.1：Skill 如何被发现和激活

### 3.1 Profile 是作品类型与专业能力之间的绑定

`builtin-profiles.ts` 明确配置了不同作品类型需要的 Skill。

例如，长篇小说 Profile 包含：

```
requiredSkillIds: ["inkos-long-writing"],
recommendedSkillIds: ["inkos-story-review"]
```

这里有一个关键区别：

- `requiredSkillIds`：必需 Skill。
- `recommendedSkillIds`：推荐 Skill，不等于自动强制激活。

在 `activations.ts` 中，`resolveProfileSkillActivations()` 默认只选择 required 项，只有传入 `includeRecommended` 才会包含推荐项。

因此，不能因为长篇 Profile 推荐 `inkos-story-review`，就认为所有 Writer 调用必然同时激活审阅 Skill。

审阅操作仍应检查具体调用配置。

### 3.2 作品还可以增加专属技能

当前源码还根据 Work 的 `creationKind` 选择对应 Skill，包括：

| 创作类型         | 对应 Skill                     |
| ------------ | ---------------------------- |
| Fanfic       | `inkos-fanfic-writing`       |
| Continuation | `inkos-continuation-writing` |
| Spinoff      | `inkos-spinoff-writing`      |
| Imitation    | `inkos-imitation-writing`    |

这表明专业方法不只由“长篇小说”这种大类决定，也可以由作品的创作模式决定。

### 3.3 必需 Skill 缺失时会怎么样

`resolveProfileSkillActivations()` 会检查必需 Skill 是否存在，缺失时抛出错误。

这体现了一条程序级约束：必需专业能力不是仅在提示词里写“请使用”；系统可以在解析阶段明确检查其可用性。

但这只能证明资源可加载，不能证明该 Skill 的每条文学方法都被模型执行。

## 四、L6.2：专业资源如何真正加载

本轮找到了两种资源加载方式，并非所有参考文件都会无条件注入。

### 4.1 显式资源加载

`createUseSkillTool()` 暴露的工具名称为 `use_skill`。

调用参数包括：

```
{
  skillId: string,
  resourcePath?: string,
  query?: string
}
```

执行时：

- 根据 `skillId` 查找实际 Skill。
- 如果提供 `resourcePath`，读取对应文本文件。
- 如果提供 `query`，检索相关参考片段。
- 另外读取 SKILL.md 中符合规则的静态资源链接。
- 将 Skill 主体和资源形成 `ActivatedSkillGuidance`。

对于显式文件路径，源码实施了安全路径检查、符号链接检查、文件类型检查和 512 KiB 大小限制。

这说明资源不仅可以被发现，也存在明确的读取边界。

### 4.2 按当前任务自动补齐专业资源

最值得研究的是 `hydrateActivatedSkillGuidance()`。

它的注释明确指出：生产 Worker 从宿主接收 Skill 本身，而相关静态资源应当在真正模型调用之前，依据当前任务文本检索。

对应逻辑为：

```
const linked = await loadLinkedSkillResources(
  activation.skill
);

const resources = await retrieveSkillResources(
  activation.skill.id,
  activation.skill.baseDir,
  query
);
```

随后对已有资源、显式链接资源、按任务检索结果进行去重合并。

这意味着 InkOS 的专业资源组织至少包含三种不同使用方式：

| 资源来源              | 激活依据            | 使用方式    |
| ----------------- | --------------- | ------- |
| SKILL.md 主体       | Skill 被激活       | 注入专业方法  |
| SKILL.md 中引用的静态资源 | 文档内的可识别链接       | 自动读取    |
| References 中的相关片段 | 当前 Worker 的任务文本 | 检索后按需读取 |

其中 `loadLinkedSkillResources()` 使用的匹配规则针对 `references/` 和 `examples/` 下的 Markdown、文本资源。

因此，一个普通路径并非只要出现在任意位置就必然被自动加载。是否匹配资源解析规则，直接影响调用结果。

### 4.3 References 检索属于动态专业上下文

此前 L3、L4 研究过作品资料检索。本轮进一步发现，Skill References 也在 Worker 调用前按任务进行检索。

但这两种检索服务的对象不同：

作品内容检索回答“这部作品此前发生了什么”。

专业方法检索回答“完成当前创作任务，需要遵循什么技巧与操作方法”。

例如，在一种合理的资源组织中：

- Writer 可能需要场景叙述、对话和节奏方法；
- Reviewer 可能需要一致性、证据判断和叙事质量标准；
- Reviser 可能需要最小修订、局部替换及保持人物声音的方法。

这些是调用机制允许的用法，并不意味着已经证明每个任务都检索出了完全正确的专业片段。

## 五、L6.3：Skill 如何进入真正的模型消息

本轮最有价值的代码是 `prepareWorkerMessages()`。

其关键顺序如下：

1. 确定作者真实请求

   读取当前执行作用域中的 `authorRequest`，并将其放入系统消息，限制下游委派指令扩大操作范围。
2. 确定当前 Work 与 Profile

   根据作品标识、Work Manifest 和执行作用域解析作品类型及 Profile。
3. 解析必需技能

   检查当前激活集合；必要时加载 Profile 必需 Skill 与作品专属 Skill。
4. 从用户任务消息提取检索 Query

   组合当前 Worker 的用户消息内容，作为专业资源检索输入。
5. Hydrate 专业资源

   加载链接资源及任务相关检索片段，形成完整的激活集合。
6. 编译模型上下文

   如果模型提供 Context Window，使用 `ContextSourceRegistry` 和 `compileContext()` 进行上下文编译。
7. 调用模型并获取结果

   最终消息交给 `runWorkerAgent()` 或 `runWorkerAgentTool()`，执行普通生成或结构化结果提交。

### 5.1 三个明确的上下文来源

源码注册了以下 Source：

| Source ID | 内容                              | 保护属性      |
| --------- | ------------------------------- | --------- |
| `task`    | 当前 Worker 的模型消息                 | Protected |
| `skills`  | 已激活 Skill 主体及专业资源               | Protected |
| `work`    | Work ID、标题、Profile、语言、Lineage 等 | Protected |

然后根据 Context Window 计算预算：

```
budgetTokens =
  contextWindow
  - maxOutputTokens
  - 2048
```

再进入 `compileContext()`。

这里要特别强调：这是一个专业 Worker 消息编译层，不代表作品全部历史、正文、状态都在这里自动检索。Writer、Reviser 等 Agent 仍然通过各自的业务输入获取 `ContextPackage`、章节内容和其他作品材料。

### 5.2 Skill 的实际优先级

`appendActivatedSkillGuidance()` 生成的指导信息明确声明：

> 它是专业方法，而不是作者意图、作品正史、输出格式的覆盖指令，也不是额外修改权限。

因此，InkOS 在 Prompt 拼装阶段已经尝试建立明确的语义边界：

作者意图 → 当前操作合同 → 作品事实 → 专业 Skill 指导。

这不是简单把全部文件拼接到 Prompt 顶部，而是明确告诉模型不同内容各自具有什么权威。

不过，以上只是指导优先级。系统是否还能在结果校验阶段识别每一种越权的文学决策，需要另外检查。

## 六、L6.4：Writer、Reviewer、Reviser 三条调用链

Writer：从上下文生成正文与状态

`PipelineRunner` 创建 `WriterAgent`，Writer 组合系统写作协议及受治理的用户上下文，之后通过 `BaseAgent` 的模型调用方法获取注入的 Skill。

Writer 不直接依靠 `use_skill` 工具完成正文生成，而是使用已经准备好的专业指导和任务上下文执行模型调用。

Reviewer：以 Observation 输出审阅结果

正常写章流程中，`reviewChapterDraft()` 调用 `ContinuityAuditor.auditChapter()`，传入正文、章节编号、题材和 `ContextPackage`。

其结果是 Observation 及审阅摘要，正文在这个函数中并不被直接修改。

Reviser：在修订合同内生成新版本

`ReviserAgent` 的输入包含原章节、Observation、修订模式、权威上下文和篇幅约束。

对局部修订，代码首先通过结构化结果选择需要修改的行范围，然后使用文本范围合同限制修订边界。

### 6.1 Reviewer 的一个重要行为

本轮读取 `chapter-review.ts` 发现，`auditChapter()` 抛出异常时，并非必然导致写章失败。

该函数会捕获异常并返回：

```
{
  unavailable: true,
  observations: [{
    code: "review-unavailable",
    evidence: []
  }]
}
```

随后将该审阅结果返回给 PipelineRunner。

这是一个非常重要的实际行为：

正常写章流程会调用审阅，但审阅调用失败时，这一函数采用记录不可用状态的方式，而不是在函数内部强制中断整条写作流水线。

是否由其他下游环节决定阻断提交，需要检查那些环节的实际判断；不能直接说 InkOS 对所有审阅失败都实行强制质量门禁。

### 6.2 Reviser 的局部修订不是纯粹 Prompt 约定

局部修订使用 `submit_chapter_edit_ranges` 等结构化结果工具来确定修改区域。

这使“只改需要修改的内容”不仅是一句文学指令，还部分转化成可以被程序检查的文本范围约束。

但范围正确不等于内容正确。局部修改仍可能引入新的因果矛盾，因此还需要后续状态与连续性验证。

## 七、L6.5：Skill 与 Runtime 之间的权责边界

本轮可以确认：InkOS 将专业方法、业务上下文、执行权限分在不同层次。

| 层次                | 负责什么                  | 不负责什么      |
| ----------------- | --------------------- | ---------- |
| Skill             | 告诉 Agent 如何完成某类专业创作   | 不授予工具权限    |
| References        | 提供可检索的技巧、案例与静态资料      | 不决定作品事实    |
| ContextPackage    | 提供特定任务需要的作品上下文        | 不直接修改作品    |
| Worker Agent      | 根据任务和专业知识生成结果         | 不自行决定持久化权限 |
| Result Tool       | 对结构化产物进行 Schema 和合同校验 | 不保证文学质量    |
| PipelineRunner    | 编排专业执行顺序、状态处理和持久化     | 不代替作者作创作决策 |
| Runtime / Harness | 执行确认、权限、状态与证据记录       | 不负责具体文学构思  |

这比“所有规则写在 AGENTS.md，Agent 自己照着办”的机制更进一步，因为若干关键约束已经在程序层实现。

例如，Reviser 的编辑范围、Profile 必需 Skill 的存在性、工具权限边界，以及某些状态校验，并非完全依赖模型自觉。

## 八、L6.6：能否追踪 Agent 实际使用了什么内容？

本轮发现 InkOS 确实记录了 Skill 注入证据。

在 `prepareWorkerMessages()` 中，执行时调用：

```
recordExecutionEvidence("skills-applied", {
  worker: workerId,
  skills: ...
});
```

记录信息包括：

- Worker 标识；
- Skill ID；
- Skill 来源；
- Skill 主体的 SHA-256；
- 资源路径；
- 资源片段起止位置；
- 资源内容的 SHA-256。

上下文编译之后，还会产生：

```
recordExecutionEvidence("context-compiled", {
  worker: workerId,
  trace: compiled.trace
});
```

这意味着 InkOS 不仅有专业知识加载机制，还开始具备加载来源与实际编译上下文的可追踪性。

不过，证据分三个层次：

| 证据                 | 能够证明什么            | 不能证明什么                 |
| ------------------ | ----------------- | ---------------------- |
| `skills-applied`   | 哪些 Skill 和资源被准备使用 | 模型是否真正遵循内容             |
| `context-compiled` | 上下文经过哪些来源编译       | 模型是否正确理解全部事实           |
| 结构化结果及审阅           | Agent 最终输出了什么     | 所有文学决策都能对应到具体 Skill 条款 |

另外，是否所有执行环境都持久化这些证据、保留多久、能否跨会话查询，本轮没有完成端到端验证。

## 九、当前发现的限制与风险

| 研究项目                     | 当前结论          |
| ------------------------ | ------------- |
| Skill 按作品类型自动激活          | 源码已确认         |
| 作品专属 Skill 绑定            | 源码已确认         |
| 必需 Skill 缺失检查            | 源码已确认         |
| 静态参考资源自动加载               | 源码已确认         |
| 按任务 Query 检索专业片段         | 源码已确认         |
| Worker 模型调用前注入 Skill     | 源码已确认         |
| 专业指导和作者意图区分              | Prompt 合同已确认  |
| Skill / Context 注入证据     | 源码已确认         |
| 所有推荐 Skill 自动激活          | 不成立，取决于调用选项   |
| 审稿失败必然阻断写章               | 不成立，审稿函数有降级返回 |

| Skill 更新后历史产物自动失效        | 尚未证实          |
| Skill 质量与作品质量之间存在可量化反馈闭环 | 尚未证实          |

### 9.1 一个需要关注的上下文问题

`prepareWorkerMessages()` 会把当前 Worker 的全部 `user` 消息拼接为 Skill 检索 Query。

对于 Writer，这些消息可能包含较长的章节意图和受治理上下文；对于 Reviser，则可能包含 Observation、上下文及完整原章节。

这意味着检索 Query 未必总是一个短而明确的文学方法需求。

源码确认了按任务检索，但并不能因此认定查询构造已经达到最佳效果。长文本查询中的关键词稀释、无关信息和语言差异，都值得单独测试。

### 9.2 一个值得继续检查的激活逻辑

`prepareWorkerMessages()` 在必需 Skill 缺失时执行自动补齐。

但如果必需 Skill 全部存在，其他作品专属 Skill 的解析是否在上游已经完成，就依赖调用者传入的 `activatedSkills`。

因此，必须区分：

- Profile 注册了某个 Skill；
- 上游完成了 Skill Resolution；
- 当前 Worker 实际携带对应 Activation；
- 最终执行证据记录了该 Skill。

这四件事不应被当成同一件事。

## 十、L6 最终研究结论

InkOS 的 Skill 机制具有三个值得明确记录的特点。

第一，Skill 不是固定嵌入各 Agent 代码中的大段 Prompt。 专业知识通过 Profile、Work、Skill 激活及资源检索进行组织，并在模型调用之前注入。

第二，Skill、References 与执行权限分离。 专业方法指导模型如何创作，程序控制可以调用什么、如何提交结果、如何验证操作范围。

第三，存在可追踪的运行证据。 Worker 的 Skill ID、内容哈希、参考资源片段和上下文 Trace 可以被记录，具备进一步验证专业方法是否真正进入执行链的基础。

但仍存在一个关键边界：

InkOS 当前已能在程序层证明“专业内容被准备并注入”，尚不能仅凭这些机制证明“模型严格、正确地执行了专业创作方法”。

所以，L6 不应简单归纳成“Skill 调用机制已经完全成熟”，而应该分成两个结论：

- 加载与注入链路：已经有明确、较完整的实现。
- 专业方法的语义执行、效果评价和反馈优化链路：需要进一步验证。

## 十一、下一轮研究建议：L7

经过 L1—L6，下一轮建议进入：

L7：内容质量控制、审阅反馈与创作效果验证。

重点研究 InkOS 如何把文学方法转化为可执行和可验证的审阅标准，包括人物弧光、故事节奏、场景设计、读者期待、前后呼应，以及审阅 Observation 如何驱动修订和再次验证。

具体需要追踪：

1. Skill 中的文学指导是否映射到 Reviewer 的检查维度。
2. Reviewer 怎样引用正文证据，而不只是给出主观评分。
3. Reviser 怎样根据 Observation 进行最小范围的有效修改。
4. 修订后是否重新审阅，以及问题怎样判定解决。
5. 质量问题是否能够跨章节累计，并在后续规划、写作中被重新使用。

这将补齐 L6 尚未解决的核心问题：专业 Skill 不只是被调用，还能否形成可观察、可验证的内容质量结果。
