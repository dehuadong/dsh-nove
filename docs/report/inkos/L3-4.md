# InkOS 机制研究：L3 + L4

专题：作品内容组织、权威来源、生命周期与 Agent 协作机制｜2026-10-21

本轮继续沿用此前确立的 InkOS 七层研究分类。这里的 L3、L4 是我们的研究维度，不是 InkOS 官方架构命名。

- L3：作品内容模型、权威与版本管理。研究作品信息如何分类、组织、保存、更新、检索和失效。
- L4：Agent 职责、上下文交接与工作流控制。研究不同创作角色如何获得所需内容、产生结果，以及结果如何成为下一阶段的输入。

研究对象仍然是 InkOS，不延伸到 Novel 的实现设计。

## 一、核心研究结论

InkOS 最值得研究的不是拥有多少种 Agent，也不是创建多少个作品文档，而是它尝试建立了一套贯穿创作生命周期的机制：

内容类型决定资料的语义，权威来源决定哪些事实可信，生命周期决定何时生效，Agent 契约决定谁能提出改变，而 Runtime 决定哪些改变可以正式提交。

研究抽象图：表示信息与控制流，不意味着每个方框都对应独立进程或独立 LLM 调用。

从已公开的 InkOS 2.0 说明来看，其强调统一生产 Harness：模型理解请求并调用能力，系统负责确认、上下文、状态、原子落盘和产物真实性；长篇写作中的规划、上下文组装、写作和审稿均由统一的 Harness action 进行调度。

这引出 L3 与 L4 必须共同回答的五个问题：

1. 某条内容究竟是什么类型？是作者要求、剧情计划、已发生事实，还是审稿意见？
2. 同一件事存在多个不同版本时，哪个来源具有权威？
3. 内容从草稿、候选、已接受到失效，经过什么流程？
4. 每个 Agent 具体收到哪些内容，并交付什么结构化结果？
5. Agent 的结果怎样通过程序调用进入持久化状态，而不只是停留在一次模型回答中？

这五个问题构成本轮统一研究的主线。

## 二、L3：作品内容类型与组织体系

### 2.1 内容不能只按照文件格式分类

研究 InkOS 时，需要区分三个不同维度：

- 业务语义：内容表达的是创作目标、世界设定、角色变化、故事事件，还是审核意见。
- 权威级别：内容是作者已确认的约束、已正式采纳的作品事实，还是未经确认的候选内容。
- 存储形态：内容最终存在 Markdown、JSON、运行快照、数据库索引或其他介质中。

这三者不能混为一谈。

例如，章节摘要和正文都可能是文本，但正文是故事实际发生内容的直接证据，摘要是对正文的派生描述。不能因为摘要更短、更容易召回，就允许其覆盖正文事实。

### 2.2 统一内容类型清单

结合此前研究的 InkOS 内容对象，按语义可以归为以下十类。

| 内容类型  | 代表性对象                      | 权威来源           | 主要消费者                     |
| ----- | -------------------------- | -------------- | ------------------------- |
| 创作意图  | Author Intent、Brief        | 作者明确决策         | Architect、Planner         |
| 创作合同  | Story Frame、Book Rules     | 已接受的创作定义       | Planner、Writer、Reviewer   |
| 世界设定  | 世界规则、地点、组织、背景              | 被采纳的设定资料       | Planner、Writer、Reviewer   |
| 角色模型  | 角色档案、关系、动机、人物弧光            | 已采纳设定及演化状态     | Planner、Writer            |
| 叙事规划  | Volume Map、章节意图、Beat Plan  | 已接受的规划版本       | Composer、Writer           |
| 正文内容  | 章节正文、已定稿文本                 | 已提交的作品版本       | Reviewer、Reviser、Settler  |
| 运行状态  | 角色位置、关系、物品、剧情状态            | 已校验的状态快照       | Planner、Composer、Writer   |
| 历史与记忆 | 章节摘要、事件记录、伏笔               | 正文与已采纳状态的派生结果  | Composer、Planner、Reviewer |
| 审阅与修订 | Observations、修改建议、修订候选     | 审阅记录与修订工作区     | Reviser、Writer、作者         |
| 外部参考  | 导入素材、知识资料、Skill References | 外部来源，不自动成为作品事实 | 检索系统、Agent                |

这里需要特别说明：这是根据已发现的对象及职责形成的研究分类，不代表 InkOS 源码中存在一个完全同名的十类枚举。

分类本身揭示了四个重要区别。

第一，人物档案与人物运行状态不同。

人物档案描述较稳定的身份、性格、目标、成长方向。运行状态描述截至当前章节，这个人物已经知道什么、做过什么、处于什么关系、拥有何种资源。

因此，人物弧光不能只保存为一段静态人物小传。真正的成长过程需要结合：

`Character Definition → Planned Arc → Scene Event → Accepted State → Historical Evidence`

第二，故事规划和故事正史不同。

Volume Map、Beat Plan 负责描述预期发生的事；已提交正文和状态负责描述实际发生的事。

某个伏笔在规划中预计第 20 章兑现，不意味着第 20 章正文一定完成兑现。规划不能直接提升为既成事实。

第三，历史记录和当前状态不同。

历史事件说明变化如何发生；状态快照说明当前结果是什么。

例如“角色已经知道秘密”可以表现为当前状态，但“角色在哪一章、通过什么行动知道秘密”属于历史证据。二者相互关联，却不能互相替代。

第四，外部资料与作品事实必须隔离。

InkOS 2.0 已公开支持书籍级资料绑定：导入素材可以绑定具体作品并声明用途，创作时根据当前任务检索相关片段，而不是整体灌入上下文。原始文件是权威来源，FTS5/BM25 索引只是可重建投影。

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

这里的“权威来源”还必须进一步区分：外部文件是该参考资料自身的原始来源，却不是作品世界事实的权威。

## 三、L3：内容权威不是单一优先级

### 3.1 至少存在四种不同的权威

| 权威维度 | 它回答的问题        | 典型依据                |
| ---- | ------------- | ------------------- |
| 决策权威 | 故事应该向哪里发展？    | 作者明确确认的意图           |
| 设定权威 | 作品允许什么、不允许什么？ | 已接受的作品合同和设定         |
| 事实权威 | 故事实际发生过什么？    | 正式提交的正文及校验状态        |
| 来源权威 | 这条信息从哪里来？     | Artifact、版本、出处、校验信息 |

重点是：不同权威解决不同的问题，并非将全部资料排成一条绝对优先级即可。

例如，作者在第 30 章之后决定更改人物命运，新的作者意图具有决策权威，但不能因此让第 10 章已经发生的事实自动消失。

如果要求重写第 10 章，就需要通过历史修订流程处理正文、摘要、状态和后续依赖，而不是直接修改最新人物档案。

### 3.2 内容冲突时应该如何理解 InkOS 的边界

以下是依据其内容权威和工作流架构归纳的冲突判断模型，并非已经验证的源码决策表。

| 发生冲突的内容          | 判断依据          | 不应发生的行为         |
| ---------------- | ------------- | --------------- |
| 新作者意图 vs 旧规划     | 新意图是否正式采纳     | 静默保留旧计划作为最终指令   |
| 正文 vs 章节摘要       | 正文的有效版本       | 用旧摘要覆盖正文事实      |
| 角色设定 vs 运行状态     | 稳定设定与事件变化的区别  | 把角色暂时状态当成永恒设定   |
| 新章节 vs 旧状态快照     | 状态是否完成结算      | 仅凭正文生成就认定状态已更新  |
| Skill 建议 vs 作者决定 | Skill 的方法指导地位 | 让文学技巧规则越权推翻作者目标 |
| 外部素材 vs 内部世界规则   | 素材来源及绑定用途     | 将素材检索命中当成作品正史   |

这也是为什么 InkOS 的统一 Harness、结构化 action/result 和提交机制具有实际价值：它们提供了区分“模型提出了什么”和“系统正式接受了什么”的技术边界。

### 3.3 从内容权威到版本谱系

此前研究涉及的 Artifact Revision、Snapshot、Checksum、Work Lineage，可以统一理解为四个不同问题：

Artifact：这是什么内容

Revision：这是第几个有效版本

Checksum：内容是否发生变化

Lineage：它由什么输入或前序版本派生

这四类信息加起来，才有机会回答历史修订后最困难的问题：

“第 18 章修改了一个关键事件，第 19—50 章的哪些内容可能依赖旧事件？”

目前不应把 InkOS 的版本记录能力直接等同于完整的跨章节依赖失效传播能力。此前研究已发现来源版本一致性和下游失效闭环仍是需要核验的边界。

## 四、L3：内容生命周期与真实生效点

作品信息的生命周期应分两条路径理解。

### 4.1 创作合同及规划类

提出

候选

已接受

被替代

作者可以改变方向，但已经接受的规划应保留版本关系，不能简单覆盖历史。

### 4.2 正文及运行状态类

生成候选正文

审阅 / 修订

状态提取 → 一致性校验 → 原子提交

正式作品内容与状态

进入后续检索、上下文、状态快照及历史恢复链路

InkOS 2.0 公开说明了安全章节工作区：正文、状态、伏笔与运行快照先校验再原子提交，失败不应产生“状态已经前进但正文没有提交”的半完成状态。

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

这是已经明确描述的机制。但需要区分两个范围：

- 同一次章节提交的原子性：有明确的设计说明。
- 历史修订导致的所有下游章节、摘要、检索项的依赖传播：目前不能据此证明已经完整实现。

另外，候选、已接受、失效这些词表示研究中的语义状态，不应在没有源码证据时认定 InkOS 每种内容对象都拥有完全一致的状态字段和状态机。

## 五、L4：Agent 角色分工与协作合同

### 5.1 Agent 不应该按“能做什么”简单划分，而应按“拥有哪种决策权”划分

根据前序 InkOS 研究，长篇创作可以抽象为以下角色协作链：

逻辑角色协作链。Composer、Validator、Reducer 等可能是程序服务或步骤，并非都拥有独立的 LLM Agent 实例。

### 5.2 各角色结构化输入与输出

| 角色                  | 主要输入               | 主要输出                    | 权限边界       |
| ------------------- | ------------------ | ----------------------- | ---------- |
| Architect           | 作者意图、题材、参考资料       | 故事框架、角色设定、世界定义候选        | 不能自行替代作者裁决 |
| Planner             | 创作合同、卷纲、当前状态、历史事件  | 章节目标、剧情节拍、连续性约束         | 不直接改变正文正史  |
| Composer            | 任务、检索结果、上下文预算、权威资料 | ContextPackage、来源 Trace | 不修改作品事实    |
| Writer              | 当前章节计划、编译上下文、写作方法  | 正文候选                    | 生成不等于正式提交  |
| Reviewer            | 正文、作品规则、上下文及证据     | 审阅 Observation          | 观察不等于自动修改  |
| Reviser             | 原文、问题、修订指令、权威资料    | 修订候选及变化说明               | 不能越权改变作品合同 |
| Settler             | 接受的正文、此前状态         | 状态变化候选                  | 不能绕过状态校验   |
| Validator / Reducer | 状态变化、当前快照、约束       | 校验结果、下一有效状态             | 不负责文学创意决策  |

这张表是职责合同的研究抽象，不是对仓库每个函数参数的逐字段转录。

它揭示了一个重要规律：Agent 不必全都能阅读完整作品，也不必全都能写作品文件。

例如，Reviewer 最重要的产物并不是“修改后的正文”，而是可定位、可追溯的问题证据。Reviser 才是根据问题生成修订候选的角色，而 Runtime 负责判断修订是否可以提交。

### 5.3 L4 的真实控制中心：统一 Harness

InkOS 2.0 的一个关键演进是统一 Chat Agent 和生产管线的执行面。

其公开说明强调：

- Studio Chat、TUI、CLI 和生产 Worker 共享 pi-agent 工具循环及结构化 action/result。
- 专业生产 Pipeline 成为可以直接调用、观察、中断和恢复的能力。
- Skill 向 Agent 提供专业方法和静态参考，不直接赋予执行权限。
- 写入、编辑、创建等副作用受到工具协议和确认闸门约束。

  [image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

  GitHub



因此不应将 InkOS 简单理解为“八个 Agent 互相聊天，最后写出小说”。

更准确的研究模型是：

对话 Agent 负责理解用户意图和选择动作；专业生产阶段负责完成具体内容任务；系统执行层负责参数、权限、状态、持久化与恢复。

这也意味着 Planner、Writer、Reviewer 等逻辑角色不一定等于八个持续运行的独立模型会话。不同角色可以由同一模型在不同提示、资源和输入条件下承担。

## 六、Agent 如何真正获得内容

这是 L3 与 L4 的交汇点，也是 Skill、检索、内容权威能否真正发挥作用的关键。

### 6.1 不是读取所有文件，而是编译任务上下文

实际调用需要经过以下逻辑步骤：

1. 确定当前任务

   例如创作下一章、审核指定章节、修改人物关系冲突。不同任务对资料的需求不同。
2. 取得当前作品的有效权威资料

   包括适用的创作合同、作品状态、章节计划及必要的历史事实。
3. 召回相关历史和外部参考

   通过检索投影找到相关段落，并保留原始来源和位置。检索命中不代表自动成为最高优先级的事实。
4. 加载任务相关 Skill 及参考资源

   将专业方法注入当前任务，而不是把全部创作规则强塞进每个 Agent 的上下文。
5. 编译 ContextPackage

   区分必须保留的 Protected 内容与可压缩的 Compressible 内容，在 Token 预算内选取材料并产生 Trace。
6. 执行当前 Agent 并处理结果

   产出计划、正文、观察或状态变化，再经过相应校验及提交边界。

这里的第 2—5 步属于此前研究建立的上下文编译链路。InkOS 公开文档确认了 protected/compressible 分层、FTS5/BM25 统一检索和按任务使用参考资料的总体机制。

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

但具体 Skill 内容是在每个生产子阶段单独重新加载，还是在统一 Chat Agent 阶段通过 action 参数及系统提示继承，需要进一步做调用点级验证。不能仅因为仓库有 Skill 文件，就认定所有专业 Agent 都正确消费了它。

### 6.2 不同角色真正需要的信息不同

以下矩阵表达各角色的典型上下文需求：

● 必需　◐ 按需　— 通常不需要

| 内容           | Planner | Writer | Reviewer | Reviser | Settler |
| ------------ | ------- | ------ | -------- | ------- | ------- |
| 作者意图与创作合同    | ●       | ●      | ●        | ●       | ◐       |
| 角色与世界设定      | ●       | ●      | ●        | ●       | ◐       |
| 卷纲、章节计划      | ●       | ●      | ◐        | ◐       | —       |
| 当前状态快照       | ●       | ●      | ●        | ●       | ●       |
| 历史摘要与关键事件    | ●       | ●      | ●        | ●       | ◐       |
| 原章节正文        | ◐       | ◐      | ●        | ●       | ●       |
| 文学 Skill 与参考 | ◐       | ●      | ●        | ●       | —       |
| 审阅问题与证据      | ◐       | ◐      | —        | ●       | —       |

这不是从源码导出的固定加载表，而是根据角色合同推导出的应检查的调用矩阵。

核心判断是：如果系统只是统一加载同一批文件，然后将全部内容分别交给每个 Agent，就还没有实现真正的角色化上下文编译。

## 七、四条关键实际调用路径

### 路径 A：新建作品与规划

```
用户创意与需求
    ↓
Chat Agent 理解意图
    ↓
创建作品动作 / 必要确认
    ↓
Architect：形成作品框架与设定候选
    ↓
作者决策 / 正式接受
    ↓
作品基础资料与版本
    ↓
Planner：产生卷纲或章节规划
    ↓
持久化规划产物
```

这一条最重要的边界：作者表达的创意、模型生成的设定和正式采用的作品定义，不能被视为同一件事。

仍需具体核实 Architect 输出是否总是经过明确接受步骤，以及哪些中间产物会被自动保存为有效版本。

### 路径 B：创作下一章

```
write next / Chat 写作动作
    ↓
读取作品当前有效状态
    ↓
Planner 获取章节意图
    ↓
Composer 召回并编译上下文
    ↓
Writer 生成正文候选
    ↓
Reviewer 记录 Observation
    ↓
Settler 提取状态变化
    ↓
Validator / Reducer 校验
    ↓
章节工作区原子提交
    ↓
更新正文、状态、运行快照
```

这条路径可以视为 InkOS 长篇生产机制的核心。

不过，这个图是整合前序研究形成的逻辑顺序，不证明 Reviewer 在所有执行模式下都是提交前阻断门禁。InkOS README 对 `write next` 的说明是写下一章并记录审稿 Observation，因此记录审阅与审阅未通过则禁止提交必须单独核实。

### 路径 C：审阅与精准修订

```
选择章节与修订目标
    ↓
读取当前正文版本
    ↓
Reviewer 生成问题及证据
    ↓
Reviser 基于原文与问题生成候选
    ↓
对比修订前后差异
    ↓
校验涉及的状态及作品规则
    ↓
提交新正文版本
    ↓
重建或刷新受影响的派生资料
```

InkOS 已公开介绍了短篇整篇修订和安全章节重写能力，并提到修订后再次审稿、保留原稿版本。

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub



但这里必须区分两个不同结论：

- 存在可执行的审阅、修订、留存原稿机制。
- 历史修订后能够识别并修复全部跨章节语义依赖。

后者不能直接从前者推出。

### 路径 D：下一章节的记忆恢复

```
当前任务
    ↓
有效作品合同 + 当前状态
    ↓
检索历史事件与章节记忆
    ↓
过滤来源、版本与相关性
    ↓
ContextPackage
    ↓
Planner / Writer
    ↓
新章节
    ↓
新的已接受事实、快照与历史
```

这一条决定长篇创作能否持续维持连续性。

历史记忆不是把所有旧聊天记录放入 Prompt，也不是一个不断膨胀的 Story Bible，而是通过已存资料、可重建索引与任务上下文重新恢复必要信息。

这里尤其需要核实：检索系统是否会过滤被历史修订废弃的片段；如果旧摘要仍然能被检索命中，Composer 是否有足够的版本信息将其排除。

### 8.1 已确认的关键机制

基于本轮可访问的 InkOS 2.0 项目说明，可以确认其明确采用或公开声明以下机制：

- 统一 pi-agent Harness 与结构化 action/result。
- 专业 Skill 与工具执行权限分离。
- 本地 SQLite FTS5/BM25 检索，原始文件与索引分离。
- 书籍级参考材料绑定、按任务检索。
- protected / compressible 上下文分层。
- 章节工作区内校验及原子提交。
- 可恢复的多章顺序执行，以及独立审阅、修订能力。

## 九、本轮的最终统一结论

从 L3 和 L4 两个层面来看，InkOS 的内容生产体系可以归纳为以下六条原则：

1. 作品内容具有不同语义：意图、合同、设定、规划、事实、历史、审阅和参考资料不能互相替代。
2. 权威由来源及接受状态决定：不是哪个文档最新、哪个检索结果排名高，哪个就具有最终决定权。
3. Agent 负责专业内容判断：不同角色拥有不同上下文需求与产物职责。
4. 程序负责生产控制：任务编排、执行权限、校验、状态应用与持久化不能只依赖 Prompt 约定。
5. 上下文是按任务编译的临时工作产物：不是简单加载 Story Bible、摘要和 Skill 全文。
6. 版本与依赖必须共同考虑：仅保存历史版本不能自动解决历史修订后的下游一致性问题。

最值得关注的设计思想是：

L3 管理作品中哪些内容有效、为什么有效；L4 管理不同角色如何消费这些内容，以及如何提出受控的内容变化。两者通过 Context Composer、结构化结果和 Runtime 提交机制连接。

这使 InkOS 不再只是一个带有写作 Prompt 的文本生成器，而是朝着具有状态、来源、审阅与持久化控制的内容生产系统发展。

但判断它是否已经具备完整的“内容权威—Agent 交接—依赖失效—历史恢复”闭环，仍需要源码级与运行级证据。

## 十、下一轮研究方向

建议下一轮进入 L5：内容依赖、历史修订与一致性传播，并保持独立研究 InkOS 的原则。

重点沿一条真实案例追踪：早期章节改变关键事件后，人物状态、故事规划、章节摘要、记忆索引、后续 Agent 上下文和下游章节如何识别旧版本，哪些自动失效，哪些需要重新生成，以及失败后如何恢复。

这一轮将能直接验证 L3 的权威和版本信息，是否真正贯穿了 L4 的 Agent 生产与交接链路，而不是仅存在于各自独立的数据结构中。
