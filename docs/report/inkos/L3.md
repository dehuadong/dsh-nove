# InkOS 深度研究报告：L3 作品内容模型、权威与生命周期

独立专题 · 基于 master 分支源码 · 2026 年 10 月 21 日

本轮将 L3 从此前 L3 + L4 的联合研究中独立出来，只研究 InkOS 如何表示、组织、保存、确认、演化和检索作品内容。

不讨论 Agent 如何编排，也不延伸到 Novel 的设计与实现。

## 一、研究摘要：InkOS 不是简单的文档管理系统

本轮核查了 `WorkManifest`、`ArtifactRevision`、`source-sync`、`RuntimeStateDelta`、`StateReducer`、`Snapshot` 及内容投影相关源码。

最重要的发现是：InkOS 实际并行使用两套不同但相互关联的内容状态体系。

- Artifact 体系：管理作品内容的文件、身份、版本、接受状态及来源谱系。
- Runtime State 体系：管理作品内部已经发生的事实、伏笔进展、章节记忆及历史状态快照。

此外，还有章节规划、权威设定、原始参考资料和检索投影等内容组织机制。

逻辑内容模型。图中的连线表示内容组织关系，不意味着所有数据属于同一个数据库或完全同步的事务。

这一发现非常重要，因为之前联合研究将“创作合同、正文、状态、记忆”视为一组内容类型，但没有充分分析其底层的不同存储语义。

本轮需要明确：

Artifact Revision 的 `current` 表示哪个文件版本被正式选中；Runtime State 的当前事实表示截至某一章节，作品世界处于什么状态。这是两个完全不同的“当前”。

## 二、L3.1：Work 是顶层内容身份和组织边界

InkOS 2.0 的 `WorkManifestSchema` 使用以下主要字段：

```
{
  version: 2,
  id: string,
  title: string,
  profileId: string,
  language: string,
  status: "draft" | "active" | "archived",
  lineage: WorkLineage[],
  artifacts: ArtifactManifest[],
  metadata: Record<string, unknown>,
  createdAt: string,
  updatedAt: string
}
```

源码：[harness/contracts.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/harness/contracts.ts)。

### 2.1 Work 不是某个章节文件夹

它是统一的作品容器，定义作品身份、生产类型、生命周期和内容清单。

`profileId` 决定它属于什么作品模式，比如长篇、短篇、剧本、翻译或互动作品。

因此，InkOS 的统一 Work 概念，不要求所有作品具有相同的正文内容结构。

长篇小说可以具有章节和伏笔状态，而翻译作品可以具有来源、术语表和翻译产物。统一的是 Work 与 Artifact 管理基础，而不是把所有创作类型强制塞进同一个 Story Bible 模板。

### 2.2 Work 生命周期

draft

active

archived

这三个状态反映作品容器的生命周期，不是正文审阅状态。

- `draft`：作品已登记，但可能尚未满足持续生产条件。
- `active`：作品处于正式活动状态。
- `archived`：作品被归档。

需要注意：状态枚举本身不能证明存在一条不可逆的线性状态机。源码允许 Work 在某些操作中更新状态，具体转换约束要看执行入口。

### 2.3 Lineage 表示跨作品来源

`WorkLineageSchema` 包含：

```
{
  relation: string,
  sourceWorkId: string,
  sourceArtifactId?: string,
  sourceRevisionId?: string
}
```

这表示一个作品能够记录它来自哪个作品、哪个产物及哪个版本。

例如，改编和衍生作品可以保留与原始作品的谱系关系。

但 Lineage 是来源关系，不等于语义依赖图。

它能记录某个新作品来自哪个旧产物，却不能仅靠这些字段理解两部作品中哪些角色、事件或场景一一对应。

## 三、L3.2：Artifact 的身份、种类与版本模型

这是本轮源码最充分、也最值得单独研究的内容之一。

### 3.1 ArtifactManifest

一个 Artifact 的核心结构为：

```
{
  id: string,
  kind: string,
  currentRevisionId: string | null,
  revisions: ArtifactRevision[],
  metadata: Record<string, unknown>
}
```

这里将内容身份与文件版本分离。

- `id`：这一项内容的稳定标识。
- `kind`：内容种类。
- `currentRevisionId`：当前被选中的版本。
- `revisions`：版本历史。
- `metadata`：补充来源及业务信息。

因此，某个章节即便发生多次修改，逻辑上仍可以指向同一 Artifact，并拥有多个 Revision。

### 3.2 ArtifactRevision

Revision 结构

```
{
  id: string,
  parentRevisionId: string | null,
  path: string,
  snapshotPath?: string,
  contentType: string,
  status:
    | "candidate"
    | "current"
    | "superseded",
  checksum: string,
  byteLength: number,
  episodeId?: string,
  createdAt: string
}
```

字段可以分成四个语义层面：

| 维度      | 字段                               | 回答的问题         |
| ------- | -------------------------------- | ------------- |
| 身份      | `id`                             | 这是哪个版本        |
| 谱系      | `parentRevisionId`               | 从哪个版本演化       |
| 存储与完整性  | `path`、`snapshotPath`、`checksum` | 内容存在哪里，是否变化   |
| 生命周期与执行 | `status`、`episodeId`、`createdAt` | 是否被采纳，由哪次执行产生 |

这里的 `episodeId` 很重要，它将内容版本与一次生产执行关联起来。

但 `Episode` 关联并不意味着版本已经通过文学质量验收，只能表示该版本与对应执行事件存在关联。

### 3.3 版本状态的实际含义

candidate

候选

current

已采用

superseded

被替代

逻辑示意。代码允许将已有版本提升为 current，因此并不是严格不可逆的单向流程。

`ArtifactManifestSchema` 还实施以下约束：

- 最多只能有一个 `current` Revision。
- `currentRevisionId` 必须指向已登记的 Revision。
- 当存在 `current` Revision 时，引用字段必须与它一致。

这些是程序可检查的版本一致性约束，而不是仅靠 Markdown 约定“最新文件就是正式版本”。

### 3.4 新版本如何产生

InkOS 具有两种值得区分的机制。

`stageArtifactRevision()` 可以创建新的 Revision，由 `promote` 参数决定是候选版本还是当前版本。

`syncWorkSourceArtifacts()` 则可以根据作品 `source/` 中的实际文件内容与哈希，建立或更新版本登记。

这意味着 InkOS 同时支持：

- 显式创建并提升版本；
- 将源文件变化同步进 Artifact Registry。

不能把这两种入口简单等同，因为它们对候选处理和文件路径的管理方式不同。

## 四、L3.3：权威来源如何建立和读取

此前研究最不充分的地方，是仅将“作者要求、设定、正文、摘要”排列成一个权威顺序，却没有检查程序如何真正确定有效版本。

本轮源码中有一个明确答案：Artifact 的读取默认以 `currentRevisionId` 为准，而不是简单读取最近创建的文件。

### 4.1 实际读取路径

`readArtifactRevision()` 的核心逻辑是：

```
const artifact = work.artifacts.find(
  item => item.id === input.artifactId
);

const revision = artifact?.revisions.find(
  item => item.id === (
    input.revisionId ??
    artifact.currentRevisionId
  )
);
```

即调用者未明确指定版本时，使用当前已登记版本。

源码注释明确指出，不得以最新候选替代当前选中的版本。

读取时还会检查：

- Artifact 与 Revision 是否登记在 Work 中；
- 实际路径是否仍位于作品目录内部；
- 快照文件是否存在；
- 文件实际 SHA-256 是否与版本登记一致。

如果文件内容与登记不符，抛出 `ARTIFACT_REVISION_CONFLICT`。

这说明 InkOS 的 Artifact 权威并不只来自“文件路径存在”，还包含登记版本、内容完整性和来源边界。

源码：[artifact-reader.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/harness/artifact-reader.ts)。

### 4.2 已接受与最新修改是两个不同概念

假设有一个章节 Artifact：

| Revision | 状态         | 说明       |
| -------- | ---------- | -------- |
| R1       | superseded | 曾经采用的旧正文 |
| R2       | current    | 当前正式正文   |
| R3       | candidate  | 尚未接受的新修订 |

如果调用者未指定版本，`readArtifactRevision()` 读取 R2，而不是 R3。

这避免未确认的修订候选自动取代正式正文。

不过，在其他直接读取源文件的代码路径中是否也始终遵循该版本选择，仍需逐个核对。Artifact Reader 的保护不能自动推断为整个仓库所有文件读取路径都已统一受控。

### 4.3 权威至少存在三个不同层次

| 权威层次          | 依据                            | 已有程序机制                  |
| ------------- | ----------------------------- | ----------------------- |
| Artifact 版本权威 | `currentRevisionId`、Checksum  | 已确认                     |
| 作品世界状态权威      | 已校验 Snapshot、StateDelta       | 已确认                     |
| 创作语义权威        | 作者意图、Book Rules、Story Frame 等 | 存在输入与提示约束，未证实统一的程序级冲突裁决 |

这三个层次不能被归并成一个简单优先级。

尤其是作者更改故事方向时，新决定可以改变后续计划，但不能使历史正文、派生摘要和当前状态自动同步。

## 五、L3.4：Runtime State 是怎样表示作品事实的

Artifact 管的是内容版本，Runtime State 管的是故事内部事实。

InkOS 采用结构化的状态模型，而不是只有一份持续追加的 `current_state.md`。

### 5.1 当前事实模型

`CurrentStateFactSchema`：

```
{
  subject: string,
  predicate: string,
  object: string,
  validFromChapter: number,
  validUntilChapter: number | null,
  sourceChapter: number
}
```

这是一个带时间范围的事实表达。

例如，以下是示意数据，并非实际项目记录：

```
{
  "subject": "角色A",
  "predicate": "持有",
  "object": "铜钥匙",
  "validFromChapter": 12,
  "validUntilChapter": null,
  "sourceChapter": 12
}
```

这里区分了：

- 事实主体；
- 属性或关系；
- 事实对象；
- 生效章节；
- 失效章节；
- 来源章节。

相比直接在人物档案中写“角色 A 现在拥有铜钥匙”，这种模型可以明确表示事实的变化范围。

但 `sourceChapter` 是章节级来源，并非直接记录具体段落、行号或 Artifact Revision。因此它还不是完整的事件证据图谱。

### 5.2 当前状态与历史事实不同

`CurrentStateState` 保存所有结构化事实及当前章节。

渲染 `current_state.md` 时，系统过滤掉在当前章节已经失效的事实：

```
fact.validUntilChapter === null ||
fact.validUntilChapter >= state.chapter
```

因此，底层状态可以保留带时间范围的事实，而当前 Markdown 投影主要呈现仍然有效的信息。

Markdown 是当前状态的可读视图，不应被当作完整历史数据库。

### 5.3 StateDelta 表示变化，而不是再次复制全部状态

`RuntimeStateDeltaSchema`：

```
{
  chapter: number,
  factOps: {
    upsert: StateFactInput[],
    expire: StateFactSelector[]
  },
  hookOps: {
    upsert: HookRecord[],
    mention: string[],
    resolve: string[],
    defer: string[]
  },
  newHookCandidates: NewHookCandidate[],
  chapterSummary?: ChapterSummaryRow
}
```

这一设计非常关键。

第 20 章不需要输出整个世界状态，只需要提交第 20 章引起的变化。

例如：

```
此前状态：角色 A 持有铜钥匙
第 20 章：角色 A 将铜钥匙交给角色 B

Delta：
  expire → A 持有铜钥匙
  upsert → B 持有铜钥匙

结果：
  当前持有者变为 B
```

这类模型适合维护长期连载中的状态演化。

但它有一个前提：模型正确提取正文中的状态变化。Reducer 可以检查结构和部分状态规则，却无法单凭三元组保证所有隐含语义都被正确提取。

## 六、L3.5：伏笔不只是文档清单，而是状态对象

InkOS 的 `HookRecordSchema` 实际包括：

```
{
  hookId: string,
  startChapter: number,
  type: string,
  status:
    | "open"
    | "progressing"
    | "deferred"
    | "resolved"
    | "superseded",
  lastAdvancedChapter: number,
  expectedPayoff: string,
  notes: string,
  dependsOn?: string[],
  paysOffInArc?: string
}
```

这比静态的“伏笔列表”更进一步。

### 6.1 伏笔生命周期

open

progressing

resolved

deferred

延期

superseded

被替代

表示可出现的状态，不是严格的全状态转换图。

`StateReducer` 的代码体现了以下行为：

- `resolve` 一个不存在的 Hook 会报错。
- 对 `superseded` Hook 执行 resolve 或 defer 会被拒绝。
- 延期伏笔时，不会凭空更新最近推进章节。
- Hook 处理之后按照章节与 ID 进行稳定排序。

这说明伏笔已具备某些程序校验，而不仅是写作建议。

### 6.2 `dependsOn` 暗示伏笔间依赖关系

`dependsOn?: string[]` 允许一个伏笔记录依赖其他标识。

`paysOffInArc?: string` 则允许关联预期回收的故事弧线。

但从存在这两个字段，不能直接推断系统具备完整的伏笔依赖传播引擎。

例如，伏笔 A 被废弃，依赖它的伏笔 B 是否会自动进入失效状态，需要具体 Reducer 或依赖分析代码证明。

目前已确认的是数据模型支持记录依赖信息，而不是已经实现复杂的自动依赖管理。

## 七、L3.6：章节摘要是结构化历史记忆

`ChapterSummaryRowSchema`：

| 字段             | 语义   |
| -------------- | ---- |
| `chapter`      | 章节编号 |
| `title`        | 章节标题 |
| `characters`   | 出场人物 |
| `events`       | 关键事件 |
| `stateChanges` | 事实变化 |
| `hookActivity` | 伏笔动态 |
| `mood`         | 情绪基调 |
| `chapterType`  | 章节类型 |

这解释了为什么 InkOS 既保存正文，也保留摘要。

正文负责完整叙事，摘要负责将关键历史信息组织为更易检索和消费的形式。

### 7.1 摘要不是正文权威的替代品

例如：

第 15 章正文包含完整的交涉过程、角色试探、情绪变化和隐藏动机。

摘要可能只写：

“角色 A 与角色 B 达成交易，A 得知某项秘密。”

这有助于后续检索，但未必保留所有伏笔暗示。

如果模型在第 30 章仅依靠摘要续写，就可能遗漏第 15 章细微但重要的叙事信息。

因此，章节摘要是有价值的派生记忆，并不天然具备与正文相等的信息完整性。

### 7.2 摘要的结构化程度也有边界

当前源码中，`events`、`stateChanges`、`hookActivity` 等字段仍然是字符串。

这意味着摘要能够按章节组织不同语义栏目，却未必能够程序化地列出每个事件的唯一 ID、参与角色、因果边和正文来源位置。

它属于半结构化历史记忆，不等于完整的事件数据库。

## 八、L3.7：Snapshot、StateDelta、Projection 的关系

这三类对象构成 InkOS 作品运行状态的核心。

### 8.1 Reducer 如何保证时序

`applyRuntimeStateDelta()` 会检查：

- Delta 是否符合 Schema。
- 提交章节是否比已有 `lastAppliedChapter` 更晚。
- 摘要章节是否与 Delta 章节一致。
- 是否发生不允许的重复摘要。
- Hook 操作是否满足状态约束。
- 应用后的完整 Snapshot 是否通过状态验证。

如果 `allowReapply` 没有启用，重复应用同一章节或向后应用旧章节会被拒绝。

这可以避免一些基本时序错误，但不保证模型提取出的故事事实必然正确。

### 8.2 结构化状态与 Markdown 投影

`saveRuntimeStateSnapshot()` 同时写入：

```
story/
  state/
    manifest.json
    current_state.json
    hooks.json
    chapter_summaries.json

  current_state.md
  pending_hooks.md
  chapter_summaries.md
```

JSON 表示可机器验证的状态，Markdown 是面向人类阅读及内容消费的投影。

这是本轮一个非常明确的结论：

InkOS 的核心运行状态并不依靠解析 Markdown 来恢复；Markdown 可以由结构化状态重新生成。

这里还有一个细节：`renderHooksProjection()` 输出 `hookId`、状态、推进章节、预期回收和备注，但不会将 `dependsOn`、`paysOffInArc` 全部呈现于当前表格。

因此，可读投影不保证保留原始状态对象的全部结构。

不能通过修改 Markdown 表格，假定已经完整修改底层伏笔状态。

### 8.3 历史时点快照

除了当前状态，InkOS 还支持按章节加载历史快照：

```
story/snapshots/17/state/
```

系统要求结构化快照完整，缺失时直接报错。

其价值在于可以从正确历史基线处理旧章节，而不是用第 50 章的当前状态重新解释第 18 章。

但如 L5 所发现的，历史章节修订后的所有下游状态，不会因此自动完成因果一致性重算。

## 九、L3.8：内容目录与统一 Work Registry 的关系

需要特别区分物理文件路径和逻辑内容身份。

InkOS 具有：

- `works/<work-id>/work.json`：统一 Work Manifest。
- `works/<work-id>/source/`：源内容文件集合。
- Artifact Revision 快照：留存版本内容。
- `story/state/`：作品的结构化运行状态。
- `story/snapshots/`：按章节保存的历史状态。
- `story/*.md`：设定、状态或历史信息的可读文档。

对于具体作品，后几类内容位于其相应的作品源目录之内。这里只展示主要相对路径，不把它们误写为仓库根目录下的一套平行 Work。

### 9.1 source-sync 不只是复制文件

`syncWorkSourceArtifacts()` 会：

1. 枚举实际 Source 文件及显式写入集合。
2. 计算内容 SHA-256。
3. 找到对应 Artifact。
4. 判断内容是否与当前版本一致。
5. 产生新 Revision 或复用已有 Revision。
6. 根据 `accept`、`acceptPaths` 决定是否提升为当前版本。
7. 保存 Revision Snapshot 和 Work Manifest。

它还会处理被删除的 Source 文件：在满足接受条件时清空对应 Artifact 的当前版本，并记录删除信息。

因此，文件的创建、变化和删除，可以对应到 Artifact Registry 中的生命周期变化。

### 9.2 内容版本由哈希参与标识

`source-sync.ts` 使用内容的 SHA-256 推导 Revision ID。

这具有两个重要含义：

- 内容没有变化时，不必因为一次执行就新增完全相同的版本。
- 内容发生变化时，可以区分不同字节内容的版本。

但需要注意：

内容哈希相同，只能证明字节一致，不能证明其在不同语境下具有相同的创作意义。

另一方面，Artifact Revision 的版本谱系也不等于 Git 那样的完整通用提交图。它表示当前内容管理中的版本及父版本关系。

## 十、L3.9：索引、检索与原始资料的权威关系

InkOS 2.0 的公开说明指出，它使用 SQLite FTS5/BM25 将故事记忆、参考资料和专业资源建立为可检索的投影。

这里至少存在三层数据：

| 层次         | 责任          | 是否直接拥有作品事实权威 |
| ---------- | ----------- | ------------ |
| 原始正文及已接受资料 | 保存实际内容      | 是，按内容类型和版本区分 |
| 结构化运行状态    | 保存已经结算的作品事实 | 是，属于状态权威     |
| 搜索索引       | 提供候选定位和排序   | 否            |

索引不是另一份独立正史。

例如，FTS 检索命中了一个旧章节摘要，不能仅因为 BM25 分数高，就认定它比当前正文更可信。

索引能够回答“哪些内容可能相关”，但不能仅靠相关性评分回答“哪些内容仍然有效”。

这与 L5 的研究直接相关。

### 10.1 源码明确支持的范围

通过 `ChapterTraceSchema` 可以确认，检索过程至少能够记录：

- 检索引擎；
- Query；
- 选择模式；
- 候选 ID、Kind、Source 和 Score；
- 被语义选择的候选 ID。

它提供的是上下文来源追踪能力。

### 10.2 尚未证实的范围

目前仍不能确认所有索引记录都具有统一的：

- Artifact Revision 绑定；
- 来源失效标记；
- 上游修订依赖；
- 自动删除或重建状态；
- 语义冲突过滤规则。

所以，InkOS 已有统一检索基础，并不等于建立了统一的内容权威解析引擎。

## 十一、L3.10：不同内容类型的统一权威与生命周期矩阵

下面将此前分散的研究整合为一张更严格的矩阵。

| 内容类型                     | 主要存储模型               | 有效性依据         | 生命周期或变化方式                                     |
| ------------------------ | -------------------- | ------------- | --------------------------------------------- |
| Work                     | Work Manifest        | 作品身份及状态       | draft、active、archived                         |
| 正式内容 Artifact            | Artifact Manifest    | 当前 Revision   | 候选、接受、被替代                                     |
| Story Frame / Book Rules | 作品源文档及版本             | 已采纳的设定内容      | 修改后形成新版本                                      |
| ChapterMemo              | 结构化规划及持久化产物          | 当前有效章节计划      | 生成、复用、更新                                      |
| 章节正文                     | Source、Artifact、章节索引 | 已正式保存的版本      | 写作、修订、归档                                      |
| 当前事实                     | Runtime State        | Snapshot 校验结果 | upsert、expire                                 |
| 伏笔                       | HookRecord           | 结构化伏笔状态       | open、progressing、deferred、resolved、superseded |
| 章节摘要                     | ChapterSummaryRow    | 已结算的历史内容      | 随章节状态更新                                       |
| 历史 Snapshot              | 章节状态文件集              | 结构完整性及状态校验    | 按章节留存                                         |
| 审阅 Observation           | 章节元数据或审阅产物           | 有来源的审阅判断      | 问题发现、复查、结果记录                                  |
| 外部参考素材                   | 源文件及检索投影             | 原始来源与使用范围     | 导入、绑定、索引、更新                                   |
| ContextPackage           | 临时结构化输入              | 选中来源与当前任务     | 构建、消费、结束                                      |

要特别强调：表中“有效性依据”并不表示存在一个已经验证的全局权威决策函数。 InkOS 实际将权威管理分布在 Artifact Registry、StateReducer、作品规则和专业执行逻辑中。

## 十二、L3.11：内容模型还存在哪些边界

综合已经读到的源码，最值得记录的是以下五个问题。

### 12.1 Artifact 身份与作品语义身份并不完全等价

一个 Artifact 可以表示一份章节文件，但不一定表示该章节内部的每个角色、事件、伏笔和转折。

因此，即使版本管理完整，也未必可以直接回答：

“这个人物关系变化究竟发生在哪个场景，受到哪些其他事件影响？”

Artifact 版本是文件级谱系；作品因果关系是内容语义级谱系。

### 12.2 状态事实仍以三元组为主

`subject / predicate / object` 具有通用性，但在文学创作中也有表达限制。

例如，“角色表面接受条件，实际准备背叛对方”同时涉及行为、心理、伪装、意图和时间。

这些内容可以编码为若干状态事实，但不会天然形成完整的心理变化模型。

### 12.3 摘要结构化不等于事件完全结构化

`ChapterSummaryRow` 中的大量字段仍是字符串。

它适合摘要、阅读和检索，却不一定适合程序直接做细粒度事件关联与依赖传播。

### 12.4 权威判定仍是分布式的

Artifact Registry 决定当前文件版本。

Runtime Snapshot 决定当前结构化状态。

Book Rules、Story Frame 和作者指令决定创作约束。

它们并未被本轮源码证明统一收敛到一个覆盖所有业务语义的权威解析服务。

### 12.5 历史修改后的语义重建仍是开放问题

根据 L5 已检查的 `PipelineRunner`，历史章节修改后，后续章节主要通过 `upstream-revision` 获得复查标记。

这是保守式风险传播，不是对全部事件、状态、摘要、索引进行精准依赖重算。

因此，内容模型的局部结构化程度较高，但跨章节因果关系仍然无法仅靠现有字段得到完整证明。

## 十四、独立 L3 的核心结论

本次研究可以将 InkOS 的内容体系归纳为三个相互关联的层次。

第一层：内容资产管理。 Work、Artifact、Revision 管理作品文件的身份、当前版本、来源和历史。这里程序约束比较明确。

第二层：作品运行事实管理。 StateDelta、StateReducer、Snapshot、HookRecord、ChapterSummary 管理小说世界如何随章节发生变化。这里已形成较完整的结构化数据模型。

第三层：语义权威与长期一致性。 Story Frame、Book Rules、作者指令、正文事实、状态和记忆之间需要协调权威。已有多项局部机制，但尚未证明具备统一且覆盖全部历史依赖的语义裁决闭环。

L3 最有价值的研究发现，不是 InkOS 使用了 JSON、Markdown 或 SQLite，而是它将“内容的版本身份”与“故事世界的运行状态”分开管理，同时用结构化状态和可重建投影降低对纯文本约定的依赖。

其最清晰的边界也在这里：文件级版本管理和章节级状态演化已经较为明确，但事件级因果关系、统一权威裁决及跨版本语义一致性仍然需要更强的运行证据。
