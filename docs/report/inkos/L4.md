# InkOS 深度研究报告：L4 Agent 协作与任务交接机制

独立专题 · 源码级研究 · 2026-10-21

研究范围： Agent 架构、角色职责、任务编排、上下文传递、结构化输出、权限边界、执行控制、失败恢复及跨任务协作。

研究对象： InkOS 的 `master` 分支，重点为 `packages/core` 和专业生产 Pipeline。

本报告只研究 InkOS 实际机制，不讨论 Novel 的改造方案。

## 一、研究摘要

本次独立检查 `PipelineRunner`、`PlannerAgent`、`ComposerAgent`、`WriterAgent`、`ContinuityAuditor`、`ReviserAgent`、`BaseAgent`、`worker-agent` 及相关执行模块后，可以确立一个比之前 L3+L4 联合报告更精确的结论：

InkOS 的 Agent 协作核心不是多个 Agent 自由讨论，而是由 Runtime 主导的、有顺序、有结构化输入输出、有持久化边界的专业任务编排。

其结构可以概括为：

简化逻辑关系图。审阅、修订和状态校验在不同操作中的先后顺序会不同；部分角色不是独立的长期运行 Agent。

可以确认以下五个重要特征：

1. 中心化编排：`PipelineRunner` 明确控制任务顺序，并非 Agent 之间无限制委派。
2. 专业化 Worker：Planner、Writer、Auditor 等分别承担特定语义任务，通过不同提示和结构化结果工具执行。
3. 双层上下文：业务 `ContextPackage` 提供作品资料，`prepareWorkerMessages()` 再注入当前任务、Skill 和 Work 元数据。
4. 结构化交接：模型结果通过工具 Schema 交回宿主，宿主负责校验、保存和提供给下一阶段。
5. 协作与权限分离：Agent 可以提出内容结果，但不能因为模型输出一句指令就自动拥有额外的文件写入权限。

不过，InkOS 不是所有场景都采用同一条固定 Agent 链路。新建作品、规划章节、正常写章、精准修订、历史章节重写，是不同的执行路径。

## 二、L4 的研究边界与证据等级

这份报告将 L4 划为七个子主题：

| 子主题  | 研究重点                               |
| ---- | ---------------------------------- |
| L4.1 | Agent 角色体系与真实实例边界                  |
| L4.2 | Coordinator、Runtime 和 Pipeline 的关系 |
| L4.3 | Agent 输入输出与结构化合同                   |
| L4.4 | 上下文构建、传递及生命周期                      |
| L4.5 | 多阶段协作及真实调用链                        |
| L4.6 | 失败、重试、中断、恢复与并发                     |
| L4.7 | 执行证据、质量反馈及协作完整性                    |

同时采用三类判断：

- 源码确认：已经读到实际函数实现和调用位置。
- 部分确认：找到相关实现，但尚未证明整个端到端行为。
- 未证实：不能仅凭文档或局部代码推出完整能力。

报告中会区分代码直接证据与架构分析推论，避免将合理设计模型误认为已经实现的源码。

## 三、L4.1：真实 Agent 角色体系

### 3.1 首先区分“角色”“实例”和“步骤”

InkOS 源码中存在多个 Agent 类，但这不意味着每个角色都作为独立的常驻进程存在。

以 `PipelineRunner` 为例：

```
const writer = new WriterAgent(
  this.agentCtxFor("writer", bookId)
);
```

这里创建的是一个专业 Agent 对象，其上下文由 Runner 提供。它可以通过统一的模型客户端执行专业任务。

因此需要区分：

| 概念             | 含义                       |
| -------------- | ------------------------ |
| Role           | 工作职责，例如 Planner 或 Writer |
| Agent Class    | 实现该角色行为的代码类              |
| Agent Instance | 某次执行中创建的对象               |
| Model Call     | 实际向模型请求推理或生成             |
| Pipeline Stage | 整体生产任务的一个阶段              |
| Runtime Action | 被 Harness 授权和调度的能力调用     |

这些对象并不一一对应。

例如，一个 Writer 实例不仅可以生成正文，也可以调用状态结算；一次精准修订可能涉及多个结构化模型调用。

### 3.2 主要专业 Agent 职责

| 角色                | 职责          | 主要输出                      | 权限或合同边界         |
| ----------------- | ----------- | ------------------------- | --------------- |
| Architect         | 生成作品框架和基础设定 | Foundation 产物             | 受作者创作意图约束       |
| Planner           | 规划章节语义目标    | ChapterMemo、ChapterIntent | 不直接成为已发生正文事实    |
| Composer          | 检索和编译任务上下文  | ContextPackage            | 不负责决定正文情节       |
| Writer            | 写作章节、结算正文状态 | 章节正文、状态变化候选               | 提交由 Pipeline 控制 |
| ContinuityAuditor | 检查连续性与内容问题  | Observation、AuditResult   | 不直接修改正文         |
| Reviser           | 根据问题和指令修订   | 新正文候选                     | 受修订范围和结果合同约束    |
| StateValidator    | 检查状态变化是否一致  | ValidationResult          | 负责验证而非文学设计      |
| Radar             | 市场和内容研究     | 研究结果                      | 不直接建立作品正史       |

上述主要职责已经能从类定义、调用点和结果类型找到依据。

不过，不能将所有实际 Agent 都等同为长篇写作链路中的必经角色。例如 Radar 属于专业研究能力，并非每写一章都必然调用。

### 3.3 角色是否可以共享同一个 LLM？

可以。

`PipelineRunner.agentCtxFor()` 根据角色名称调用 `resolveOverride(agent)` 获取模型及客户端：

```
private agentCtxFor(
  agent: string,
  bookId?: string
): AgentContext {
  const { model, client } =
    this.resolveOverride(agent);

  return {
    client,
    model,
    projectRoot: this.config.projectRoot,
    bookId,
    logger: this.config.logger?.child(agent),
    onStreamProgress: this.config.onStreamProgress,
    signal: this.currentAbortSignal(),
    activatedSkills: this.currentActivatedSkills(agent),
  };
}
```

说明 InkOS 支持按角色选择模型配置，同时每个角色都能获取自己的专业 Skill 激活集合。

这体现的是角色级执行上下文隔离，而不是要求每个角色配备独立的模型服务。

## 四、L4.2：谁真正负责协调不同 Agent？

这里需要分三层研究。

### 第一层：交互式 Coordinator

面向用户请求的统一 Harness 负责把自然语言意图转化为能力调用，例如写下一章、修订某章或者开展审阅。

用户不需要分别手动给 Planner、Composer 和 Writer 发送消息。

但模型能决定调用某项已暴露的能力，并不意味着它能自由绕过执行权限或持久化规则。

### 第二层：PipelineRunner

这是专业生产编排的核心。

例如，`writeChapters()` 不是让多个 Writer 同时生成任意章节，而是：

```
for (
  let index = 0;
  index < chapterCount;
  index += 1
) {
  const result =
    await this._writeNextChapterLocked(...);
}
```

还会通过 `acquireBookLock(bookId)` 获取作品写入锁。

这里可以确认：

同一本作品的一次多章生产，按章节顺序推进，每一章结束后再进入下一章。

这与自由并行生成多章不同，因为后续章节可能依赖前章实际写出的事件和更新后的状态。

### 第三层：专业 Agent 内部调用

本轮发现一个值得单独记录的情况：

`PlannerAgent.planChapter()` 自己会调用：

```
new ComposerAgent(this.ctx)
  .selectTaskContext(...)
```

然后基于该 ContextPackage 生成 ChapterMemo。

这说明 InkOS 并非所有角色协作都只能发生在 Runner 顶层。某些专业 Agent 内部也直接复用另一个角色的上下文选择能力。

不过，这种调用属于明确的代码委派，不是模型自主发起无限递归的 Agent-to-Agent 对话。

### 4.1 控制流与信息流不同

| 关系                           | 控制流    | 信息流                 |
| ---------------------------- | ------ | ------------------- |
| Coordinator → PipelineRunner | 调用专业能力 | 用户请求及参数             |
| Runner → Planner             | 创建和执行  | 当前作品、章节及意图          |
| Planner → Composer           | 调用选择能力 | 规划目标与检索约束           |
| Runner → Composer            | 调用完整编译 | 章节计划、参考资料           |
| Runner → Writer              | 执行写作   | Memo、ContextPackage |
| Runner → Auditor             | 执行审阅   | 正文、上下文及审阅目标         |
| Runner → Reviser             | 执行修订   | 原文、Observation、范围约束 |
| Runner → Validator           | 执行校验   | 候选状态及正文             |

这个区分很重要：Agent 之间可以共享数据，但未必互相拥有控制权限。

## 五、L4.3：Agent 之间传递的究竟是什么

这是整个 L4 最关键的部分。

InkOS 不是依靠 Agent A 给 Agent B 发送一段自然语言，例如“上一阶段我已经完成，请继续”。

它主要利用程序拥有的类型化对象，在不同阶段之间传递结果。

### 5.1 Planner → Composer → Writer 的数据合同

源码定义了以下对象。

ChapterMemo

```
{
  chapter: number,
  goal: string,
  body: string,
  threadRefs: string[]
}
```

ContextPackage

```
{
  chapter: number,
  selectedContext: [
    {
      source: string,
      reason: string,
      excerpt?: string,
      protection:
        | "protected"
        | "compressible"
    }
  ]
}
```

源码：[input-governance.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/models/input-governance.ts)。

其中有几个细节值得注意。

`ChapterMemo` 不是简单的章节标题。

它包含章节目标、正文形式的语义规划以及线索引用。由 Planner 通过 `submit_chapter_memo` 结构化工具生成，再由宿主用 `ChapterMemoSchema` 验证。

`ContextPackage` 不只是检索到的文本拼接。

每条选中内容都包含来源、选取原因、正文片段及保护级别。

这使 Composer 可以告诉后续 Agent：

- 这条内容从哪里来；
- 为什么与当前任务相关；
- 是否属于不可随意压缩的材料。

但 ContextPackage 本身不是完整的权威图谱。

目前该 Schema 不直接包含通用的 Artifact Revision、依赖关系、失效标识或事实可信度字段。来源版本相关能力可能由其他系统提供，不能假定所有内容都在这个对象内实现版本校验。

### 5.2 Agent 之间交接的五类内容

| 数据类型  | 实例                              | 作用           |
| ----- | ------------------------------- | ------------ |
| 意图合同  | ChapterIntent、ChapterMemo       | 确定当前任务做什么    |
| 业务上下文 | ContextPackage                  | 确定任务依据什么     |
| 作品产物  | 正文、设定、状态变化                      | 交付实际创作成果     |
| 审阅反馈  | Observation、AuditResult         | 描述发现的问题与证据   |
| 执行证据  | ChapterTrace、Execution Evidence | 记录用了什么、执行了什么 |

这里的核心是：创作产物、审阅产物和执行证据是三种不同类型的信息。

不能把审阅意见自动提升为新作品事实，也不能把“模型表示已完成”当作持久化成功。

### 5.3 ChapterTrace 提供了哪些交接证据

源码中的 `ChapterTraceSchema` 包含：

| 字段                | 记录内容                        |
| ----------------- | --------------------------- |
| `plannerInputs`   | Planner 使用的来源               |
| `composerInputs`  | Composer 使用的来源              |
| `selectedSources` | 最终被选中的内容来源                  |
| `contextTiers`    | Protected / Compressible 分类 |
| `tokenBudget`     | 各类内容预算与实际估算                 |
| `compression`     | 压缩后的来源及预算情况                 |
| `retrieval`       | 检索引擎、Query、候选、得分及选择模式       |
| `notes`           | 补充信息                        |

这为复查某一章写作时到底使用了什么提供了数据基础。

但它尚不是一个统一的跨 Agent 决策日志。它不能直接回答“Writer 为什么选择让角色背叛”，只能帮助重建当时 Writer 获得了哪些材料。

## 六、L4.4：Context Composer 不只是一个普通 Agent

从 `ComposerAgent` 的代码可以看出，它实际上承担了上下文选择与编译服务的职责。

这和 Planner、Writer 以创作结果为中心的角色存在明显区别。

### 6.1 Composer 的两种入口

`ComposerAgent` 至少提供两个重要方法：

| 方法                    | 目的                  |
| --------------------- | ------------------- |
| `selectTaskContext()` | 为规划、审阅、修订等任务选取相关上下文 |
| `composeChapter()`    | 为章节写作建立完整受治理的上下文    |

这两个方法不等价。

`selectTaskContext()` 可以把当前任务目标临时封装成一个规划意图，检索所需资料，而不必先调用 Planner 重新做一遍完整章节规划。

`composeChapter()` 则接受正式 `PlanChapterOutput`，并结合预算、参考资料、章节记忆和大纲选择机制构建完整写作上下文。

因此：

Composer 是多个专业 Agent 可以复用的上下文能力，不应理解成只能位于 Planner 与 Writer 中间的一次性步骤。

### 6.2 上下文选择不是每次都需要模型

`composeChapter()` 中存在一条优化路径：

当 Context Window 足够容纳全部相关材料时，优先执行 `completeContextWithinBudget()`。

该方法计算：

\\[ B\_{\text{context}}= \left\lfloor \frac{B\_{\text{window}}-B\_{\text{output}}}{2} \right\rfloor \\]

如果完整候选内容没有超过该预算，就保留完整内容。

源码甚至记录：

```
recordExecutionEvidence(
  "context-selection",
  {
    mode: "complete",
    modelCalls: 0
  }
);
```

这个细节意味着：

InkOS 不会为每一次上下文选择都无条件额外调用一个 LLM。

如果内容足够小，可以走确定性的完整装载路径。

### 6.3 什么时候由模型参与选择

当完整装载不可行时，Composer 可以调用：

- 大纲片段选择；
- 历史记忆候选选择；
- 外部参考片段选择；
- 可压缩上下文编译。

例如，`submitSelectedSources()` 的结果工具要求模型提交候选编号，而不是自由生成来源路径：

```
{
  selectedIndices: number[]
}
```

然后由宿主将编号映射回真实 Source ID。

这是一个有价值的控制机制：

模型负责语义判断——选择什么重要；

程序负责来源真实性——所选内容必须属于实际候选集合。

### 6.4 两层 Context 需要明确区分

作品级 ContextPackage

由 Composer 面向具体故事任务组装，包含章节记忆、设定、规划和参考材料。

Worker 消息编译

由 BaseAgent 调用 `prepareWorkerMessages()`，处理当前模型消息、Skill、Work 元数据、预算和 Trace。

这两层可能共同影响一次模型调用，但拥有不同的责任。

作品级上下文解决“故事需要什么信息”；Worker 编译解决“这次模型执行最终收到什么”。

## 七、L4.5：端到端真实协作路径

### 路径 A：规划下一章

已确认的主要调用关系：

```
PipelineRunner.resolveGovernedPlan()
    ↓
PlannerAgent.planChapter()
    ↓
loadPlanningSeedMaterials()
    ↓
ComposerAgent.selectTaskContext()
    ↓
PlannerAgent.planChapterMemo()
    ↓
submit_chapter_memo
    ↓
ChapterMemoSchema.parse()
    ↓
生成 ChapterIntent 与规划产物
    ↓
PipelineRunner.savePersistedPlan()
```

这里存在一个非常重要的复用机制。

在 `resolveGovernedPlan()` 中，如果允许复用现有规划，并且没有新的外部指导，会尝试加载已持久化的章节规划：

```
const persisted =
  await loadPersistedPlan(
    bookDir,
    chapterNumber
  );

if (persisted) return persisted;
```

所以 Planner 不是必然每次调用模型。

已持久化的有效阶段结果，可以成为后续调用的输入，而不需要反复推理同一项决策。

这进一步说明 InkOS 的 Agent 交接不只是内存中的会话消息，还可能通过持久化产物完成。

### 路径 B：正式写下一章

`PipelineRunner._executeNextChapterLocked()` 的主要链路为：

1. 准备受治理输入

   `prepareWriteInput()` 形成章节意图、Memo 和 ContextPackage。
2. 生成章节草稿

   创建 WriterAgent，执行 `writeChapter()`。
3. 审阅草稿

   `reviewChapterDraft()` 调用 ContinuityAuditor，获取 Observation。
4. 构建持久化候选

   使用最终正文及 Writer 状态结果构造 `persistenceOutput`。
5. 校验作品真相变化

   `validateChapterTruthPersistence()` 协调状态验证，检查新正文与状态变化。
6. 提交章节与状态

   通过持久化机制写入正式作品资料。

需要纠正一个容易误解的描述：正常写章链路不是简单的“Writer → Reviewer → Reviser → Settler → Validator”固定队列。

本轮看到的是 Writer 同时承担正文生成和状态结算相关工作；审阅之后再建立最终持久化候选和运行状态验证。Reviser 并不是正常写章每次都必经的独立步骤。

### 路径 C：历史章节修订

与正常写章不同，修订路径包含：

```
指定历史章节
    ↓
读取原章节与版本
    ↓
读取目标章节前一章 Snapshot
    ↓
预审或处理用户明确修订指令
    ↓
Reviser 生成新正文
    ↓
Writer 重新结算状态
    ↓
StateValidator 验证
    ↓
必要时进行状态协调恢复
    ↓
修订后再审阅
    ↓
保存修订结果和 Observation
    ↓
历史章节的下游风险传播
```

这条路径特别体现了 L4 与 L5 的连接：

Agent 负责生成修订内容，Runtime 负责判断如何处理受影响的状态和后续章节。

### 路径 D：连续写多章

`writeChapters()` 使用作品锁，并逐章 `await`，上一章完成后下一章才开始。

因此可以确认它具有单次任务内顺序依赖。

不过，顺序执行并不意味着整个多章任务是一个不可分割的原子事务。前几章已经完成而后续章节失败时，系统需要依靠已有阶段产物和恢复机制进行处理。

## 八、L4.6：Agent 模型调用与结构化结果协议

这一部分是 InkOS 与普通多 Agent Prompt 编排的重要区别。

### 8.1 Agent 输出并不总是自由文本

在 `BaseAgent` 中有两个不同入口：

| 方法                   | 用途                 |
| -------------------- | ------------------ |
| `chat()`             | 普通模型生成             |
| `submitStructured()` | 调用模型并要求通过结构化结果工具提交 |

Planner 的 ChapterMemo、Auditor 的 Observation、Reviser 的局部编辑范围，都属于结构化结果路径。

### 8.2 Structured Worker 的真正执行方式

源码中的 `runWorkerAgentTool()`：

1. 要求已解析的 Pi Model。
2. 为当前任务构造系统提示。
3. 只暴露当前任务所需的结果工具。
4. 要求模型调用该工具，而不是打印 JSON。
5. 对参数执行 Schema 解析。
6. 执行业务校验回调。
7. 成功后由宿主接收结果。

核心指令大意为：

```
Finish by calling ${resultTool.name}
exactly once.
```

该逻辑中，`toolExecution` 设置为 `sequential`。

这说明“提交章节规划”不是模型随便生成一个看似 JSON 的文本，而是必须经过宿主提供的结果工具合同。

### 8.3 结果不合法时如何处理

`runWorkerAgentTool()` 中设置：

```
const maxResultTurns = 3;
```

并记录：

- `worker-arguments-decoded`
- `worker-result-invalid`
- `model-stream-progress`

如果提交参数不符合 Schema 或领域约束，则记录错误，并允许在有限调用轮次内重新提交。

因此，这是一个有边界的模型结果重试机制。

但必须强调：

结构化提交成功，不等于文学目标已经达成。

它证明的是参数符合合同且通过相应业务验证。对于人物动机是否合理、场景张力是否足够等问题，仍需要独立审阅。

## 九、L4.7：Agent 权限到底由谁管理

InkOS 存在一个清晰的责任划分：

Agent 负责内容判断，宿主负责实际执行权限。

例如：

- Planner 可以生成章节计划，却不能因为模型输出一句“删除第 20 章”就越过当前操作范围。
- Reviewer 可以提出问题，却不直接具有修改正文的权力。
- Reviser 可以生成新正文候选，但仍须经过编辑范围及其他校验。
- Writer 可以产生状态变化候选，但是否成为有效状态由执行和持久化逻辑决定。

本轮检查的 `prepareWorkerMessages()` 还会读取真实的 `authorRequest`，并告诉下游 Worker：委派指令可以细化任务，但不能替换作者目标或扩大修改范围。

这一层属于 Prompt 级权限语义约束。

而结构化结果工具、编辑范围校验、文件写入锁及 Pipeline 提交逻辑，则属于程序级约束。

两者需要共同理解，不能只用“Agent 有权限 / 无权限”来概括。

### 9.1 Agent 是否可以自行调用其他 Agent？

当前可确认的是：

- Runner 在代码中创建专业 Agent。
- Planner 在实现中直接调用 Composer 的上下文选择方法。
- Composer 可以调用专业的语义上下文压缩 Agent。
- Worker 的结构化结果调用通常只暴露当前任务的结果工具。

这属于受程序控制的明确委派。

尚不能据此认为 Writer 可以在任何时刻任意创建 Planner、Reviewer、Reviser，组成自发运行的多 Agent 网络。

## 十、失败、中断与恢复的协作语义

L4 研究不能只关注正常执行，失败路径更能反映协作架构是否成熟。

### 10.1 已确认的控制机制

| 机制        | 源码证据                    | 作用               |
| --------- | ----------------------- | ---------------- |
| 作品锁       | `acquireBookLock()`     | 防止相关写入竞争         |
| 顺序章节生产    | `writeChapters()` 循环    | 保持前后章节的状态依赖      |
| 中断信号      | `AgentContext.signal`   | 向 Worker 传播取消    |
| 结构化结果限制   | `maxResultTurns = 3`    | 限制无效结果的重试        |
| Schema 校验 | `Value.Parse()`、Zod     | 拒绝无效数据           |
| 领域校验      | Result Tool `validate`  | 拒绝违反业务约束的结果      |
| 审阅降级      | `review-unavailable`    | 在部分审阅失败时保留明确异常状态 |
| 原子文件集     | `commitAtomicFileSet()` | 降低半完成持久化风险       |

### 10.2 不同失败不能一律重试

这里至少有四类失败。

模型输出失败：结果缺字段、类型错误等，可以在有限轮次内重试模型提交。

上下文失败：找不到必要资料或快照，不能靠模型重新措辞解决，需要重新获取正确数据。

作品状态失败：正文与状态变化不一致，需要重新结算或执行状态协调恢复。

作者授权冲突：修改范围不符合真实请求，不应自动扩大范围继续执行。

源码中已经出现这些不同类型的处理机制，但尚需全面核验它们是否在所有入口共享同样的失败分类和恢复合同。

### 10.3 恢复以后如何保证交接一致

完整的可恢复 Agent 协作应能回答：

- 前一个阶段是否真正提交成功？
- 下一阶段依据的是哪个版本的阶段产物？
- 是否已经存在可复用的规划或 ContextPackage？
- 上次执行是否只完成了部分章节？
- 是否需要重新审阅或重新结算状态？

本轮确认了章节规划复用、顺序执行、结构化状态验证等局部机制。

但不能仅凭这些机制认定全部 Agent 步骤都具备完全统一、可重放的事务式恢复。

## 十一、Agent 协作中的五个关键设计发现

### 发现一：InkOS 是中心化任务编排，不是自由式多 Agent 群聊

这个判断有明确的源码支撑。

`PipelineRunner` 主导实际生产流程，Agent 主要在限定范围内完成专业工作，通过结构化结果和上下文对象交接。

优势是流程可预测、结果容易检查、失败位置较明确。

代价是角色依赖及阶段变化需要在程序中组织，而不能单纯依靠 Agent 自发协商完成全部工作。

### 发现二：Agent 可以嵌套调用专业能力，但不等于任意自治

Planner 调用 Composer、Composer 调用语义压缩 Agent，说明专业能力存在复用和嵌套。

不过这些调用由代码明确规定，并非任意模型之间直接对话。

这使 InkOS 的 Agent 模型更接近：

Coordinator + 专业 Worker + 可复用语义服务

而非完全扁平的 Agent 网络。

### 发现三：上下文是正式交接产物

Composer 产生 `ContextPackage`，Planner 产生 `ChapterMemo`，并有 `ChapterTrace` 记录输入来源。

这些对象让不同 Agent 可以在不共享完整对话历史的条件下完成协作。

但必须注意，结构化交接只能保证类型完整，不能自动保证上下文已经覆盖所有文学上重要的历史事实。

### 发现四：结构化工具将部分 Agent 约定变成程序合同

Planner 的 `submit_chapter_memo`、Composer 的 `submit_selected_sources`、Reviser 的局部编辑范围工具，以及 Auditor 的来源化观察，都体现了这条路径。

模型负责语义任务，程序检查结构、候选集合、修改范围和来源真实性。

这是目前 InkOS Agent 协作中比较成熟的技术部分。

### 发现五：协作执行闭环强于语义反馈闭环

正常写章、修订和状态验证均已存在实际协调过程。

但更高级的协作问题仍未得到充分证据支持，例如：

- Reviewer 发现持续的人物弧光问题后，是否会自动触发 Planner 重新规划后续章节？
- 多个 Agent 对同一故事事实意见冲突时，谁负责正式裁决？
- 修订第 18 章之后，是否会自动决定哪些后续 Agent 任务需要重新执行？
- 某个 Skill 或参考资料版本更新后，能否识别哪些旧 Agent 结果受到影响？
- 已经完成的 Agent 交接能否在恢复执行时验证所有输入版本仍然有效？

这类问题已经超出普通的类型化数据传递，涉及跨阶段、跨版本的语义一致性管理。

## 十三、L4 最终研究结论

基于本轮源码研究，可以把 InkOS 的 Agent 协作机制总结为四层：

控制层：Coordinator / Runtime

决定调用什么能力、执行顺序、权限、取消与持久化。

专业层：Planner / Writer / Reviewer / Reviser 等

承担不同语义任务，通过统一 Worker 基础设施调用模型。

交接层：Memo / ContextPackage / Observation / StateDelta

用类型化产物将任务目标、上下文、内容结果及审阅反馈传递给后续阶段。

证据与状态层：Trace / Revision / Snapshot

记录来源、执行证据、有效版本和可恢复的作品状态。

其中最重要的架构特征是：

Agent 协作不是依靠“彼此知道对方说了什么”，而是依靠 Runtime 将当前任务、权威资料、专业方法和经过校验的阶段结果组织起来。

但 InkOS 当前更强的是阶段级执行编排与结构化交接，尚不能证明已经具备完整的跨阶段语义依赖管理、自主重新规划与长期质量反馈闭环。

这也是本次独立 L4 研究，相比此前 L3+L4 联合报告进一步明确的边界。
