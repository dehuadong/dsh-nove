# InkOS 机制研究：L1 创作质量 + L2 Skill 内容体系

本轮主题：从“确保小说不会写乱”，深入到“如何让 Agent 真正写出好看的小说”。

前面研究的重点是 Runtime、结构化状态、长期记忆、上下文编译、内容权威以及 Agent 交接。这些解决的是创作系统的可靠性，但并不能直接保证小说质量。

本轮继续独立研究 InkOS，暂不讨论 Novel 的具体实现。

这里沿用此前的研究分类：

- L1：文学创作质量机制——人物弧光、故事节奏、场景、读者期待、叙事因果、情绪、伏笔兑现。
- L2：Skill 与内容资源机制——文学方法如何组织、加载、分配给不同 Agent，并在创作与审订中真正发挥作用。

L1/L2 是我们的研究分类，并非 InkOS 官方定义的架构层。

## 一、先明确本轮最重要的研究发现

从 InkOS 当前 `master` 分支的长篇写作 Skill、相关资源文档、Planner 与 Writer 提示词，可以确认一个值得深入研究的变化：

InkOS 已经在尝试把“文学创作方法”从 Agent 提示词中抽离，作为独立的专业知识层，由不同创作角色共同使用。

它不再只要求 Writer “写得精彩”，而是把问题拆成几种可以传递、执行和检查的文学任务。

| 文学问题     | InkOS 的方法            |
| -------- | -------------------- |
| 人物为什么改变  | 动机、限制、选择、代价和不可逆变化    |
| 故事怎样持续推进 | 主线与辅助轴变化、短周期推进、高潮与余波 |
| 场景为什么存在  | 即时目标、阻力、转折和后果        |
| 读者为什么继续读 | 阅读承诺、信息释放、兑现与新的压力    |
| 对话怎样避免灌水 | 改变谈判位置、暴露限制、形成选择或债务  |
| 篇幅怎样自然达标 | 先配置场景容量，不依靠完成后的机械扩写  |
| 审阅怎样发现问题 | 检查可观察的事实、行动、情绪与关系变化  |
| 修订怎样保持质量 | 按根因确定局部修补或结构性修订      |

这些不是我推测的文学理念，而是已经出现在 `inkos-long-writing`、`reader-contract-and-progression.md`、`foundation-design.md`、`scene-dialogue-and-length-budget.md` 与 `inkos-story-review` 中的具体规则。

这里也存在一个必须区分的问题：

有文学规则，不代表这些规则已经在每次真实执行中被正确加载；规则被加载，也不代表生成结果经过了充分验证。

因此本轮研究分为三个层次：

L1｜文学内容的目标与质量标准

人物、节奏、场景、读者期待、叙事因果

L2｜专业 Skill 与内容资源

创作方法、专题参考、角色适用规则、审阅标准

Agent 收到了什么 → 做出了什么 → 审阅能证明什么

这个区分是后续分析 InkOS 是否真正具备“文学创作能力体系”的基础。

## 二、L1：文学创作质量的六个核心机制

### 2.1 人物弧光：不是人物档案，而是选择如何改变人物

InkOS 的 `foundation-design.md` 明确提出，人物需要由动机、限制、历史、关系、矛盾和代价构成。主角还需要拥有起始状态、内部与外部目标，以及不可逆代价。

这是一个比较重要的设计取向。

一般的人物档案回答：

> 他是谁？有什么性格？有什么经历？和别人是什么关系？

人物弧光还要回答：

> 他原来为什么这样行动？什么事件迫使他改变？他付出了什么代价？为什么不能轻易回到原点？

人物弧光的因果结构（研究归纳）

初始信念与行为方式

人物认为怎样做才是安全、正确或值得的

外部压力与内在矛盾

旧有行为模式开始无法解决问题

有代价的关键选择

选择暴露真实价值排序，而不是由旁白宣告成长

新的处境与行为模式

行动、关系、自我理解发生可观察变化

举一个独立的虚构例子：

某位年轻医师认为“遵守规矩才能避免伤害”。他第一次破例救人，虽然成功，却导致自己的师父承担责任。之后他必须决定，是重新服从规矩，还是主动承担违规的后果。

真正的弧光不是他“变得勇敢”，而是他是否从依赖规矩替自己承担责任，转变为愿意对自己的判断负责。

#### InkOS 已具备什么？

它目前在方法层明确要求：

- 选择必须来自人物的动机、知识、恐惧和可承担的代价。
- 关系通过事件发生变化，而不是作者解释。
- 人物弧光必须有代价，配角也应拥有独立动机。
- 审阅时区分“外部处境没有变化”与“人物情绪弧线停滞”。

但这里要注意一个实现边界：

我能确认 InkOS 具备人物弧光的创作指导和审阅标准，尚不能据此认定它存在独立、完整、可计算的“人物弧光状态机”。

例如，人物的“错误信念”“价值转折”“不可逆代价”“已完成的弧光阶段”，是否各自拥有独立结构化字段、跨章节追踪和自动审阅证据，仍需要专项核对。

这也是人物连续性与人物成长质量之间的重要区别。

### 2.2 故事节奏：不是每章都刺激，而是连续的戏剧周期

InkOS 的 `reader-contract-and-progression.md` 有一条关键规则：

一个有效章节应至少改变一个主要叙事轴和一个辅助轴。变化可以发生在情节位置、知识、关系、地位、危险、资源或自我理解上。

这比传统的“每章都必须有冲突和悬念”更合理。

因为高潮、日常、情感沉淀、信息探索和后果处理，本来就不应该采用同一种强度。

示意：一个完整戏剧周期的张力变化

02.557.510建立压力阻力加深局部反转高潮兑现结果余波新压力

概念示意，非 InkOS 实测数据或内置算法

InkOS 强调的是以下关系：

铺垫 → 压力 → 升级 → 兑现 → 余波 → 下一轮推进。

这里尤其值得研究的是“余波”。

一个角色刚刚经历生死冲突，下一章不能机械地立刻开始更大的生死冲突。即使剧情必须继续，也应让人物的行动、关系、认知或资源体现前一次事件的后果。

否则虽然故事一直有事件，读者却容易感到没有重量。

InkOS 还要求审稿从最近数章判断节奏，而不是孤立评价某一章。

#### 关键认识

节奏至少存在四个不同尺度：

| 尺度   | 核心检查                   |
| ---- | ---------------------- |
| 场景   | 压力是否发生变化，有没有实际转折       |
| 章节   | 是否完成本章戏剧任务，留下持久变化      |
| 章节组  | 压力、升级、兑现、余波是否形成周期      |
| 卷与全书 | 主要冲突是否升级，人物和故事阶段是否真正改变 |

InkOS 的现有指导已覆盖这些尺度的主要思想，但是否存在真正的跨章节节奏诊断算法或节奏序列模型，不能仅从 Skill 文本得出结论。

### 2.3 场景设计：由文学功能决定场景，而不是按字数凑内容

InkOS 对场景给出四个关键要素：

Goal｜目标

人物此刻具体想得到什么？

Resistance｜阻力

什么阻止他直接完成目标？

Turn｜转折

什么新行动或信息改变局面？

Consequence｜后果

结束后有什么无法忽略的变化？

例如，一个“主角前往商会谈判”的场景：

低质量版本是主角与商会会长交谈，说明市场背景，双方达成合作。

更有戏剧功能的版本是：

主角本想取得供货权；会长提出必须出卖一位旧友作为交换；谈话期间主角发现商会已有其他人掌握了他的秘密；最终主角放弃供货权，却获得了会长内部势力分裂的线索。

这个场景同时改变了资源、关系、知识和未来冲突。

InkOS 的方法并不是要求所有场景都有强烈反转，而是要求每个场景承担某种真实的叙事工作。

#### 篇幅预算同样被视为场景设计问题

在 `scene-dialogue-and-length-budget.md` 中，InkOS 提出先按戏剧工作把篇幅分配给大约 2—5 个场景，再动笔写正文。

这是一种方法建议，不是要求所有章节固定具有 2—5 个场景。

例如，3000 字的章节可以是：

| 场景  | 戏剧功能          | 预计篇幅    |
| --- | ------------- | ------- |
| 第一场 | 主角发现异常，建立问题   | 600 字   |
| 第二场 | 调查受阻，关系产生摩擦   | 900 字   |
| 第三场 | 获得关键证据，发现更大代价 | 1,000 字 |
| 第四场 | 做出选择，并承受直接后果  | 500 字   |

这种分配的意义，不在于表格，而在于提前判断章节是否拥有足够的故事内容。

如果一个章节只有一件很小的事，却要求 3500 字，应该先检查场景和情节容量，而不是简单要求 Writer 多写环境描写或心理活动。

这是 L1 中很值得借鉴的创作机制。

### 2.4 读者期待：把“悬念”提升为“阅读承诺”

InkOS 的 `reader-contract-and-progression.md` 特别强调 Reader Contract，即读者从故事中期待持续获得的体验。

例如：

- 悬疑故事承诺的是发现、推理和真相。
- 权谋故事承诺的是布局、博弈和局势变化。
- 成长故事承诺的是能力、身份与认知的逐步改变。
- 情感故事承诺的是关系发展、选择和情绪兑现。

这些承诺不限于明确的伏笔。

一本小说完全可能没有复杂的伏笔系统，却仍然具有很清晰的阅读承诺。

反过来，伏笔很多，也不表示读者体验就好。

#### 阅读承诺与伏笔的区别

| 类型   | 例子             | 兑现方式           |
| ---- | -------------- | -------------- |
| 类型承诺 | 这是一部智谋博弈小说     | 持续出现有价值的决策和博弈  |
| 角色承诺 | 主角终有一天会面对旧日失败  | 人物做出不同于过去的选择   |
| 情感承诺 | 两个互不信任的人逐渐建立信任 | 用行动证明关系改变      |
| 情节承诺 | 某个失踪人物的身份是谜    | 展示线索、推理和最终揭晓   |
| 章节期待 | 主角能否拿到关键证据     | 当前章节或后续短周期给出进展 |

不是每项读者承诺都应建成一条伏笔。

InkOS 已在文学方法中区分尚未激活的故事种子与真正进入正文的活跃承诺，而且强调只使用真实存在的 hook ID，不能凭空创建或升级伏笔。

但仍有一个值得检验的边界：它对读者的长期体验承诺，是否具有独立于 Hook Ledger 的表示和追踪方式？

如果没有，系统可能擅长提醒“某个伏笔尚未兑现”，却不一定擅长发现“最近十章一直没有提供该题材承诺的核心阅读体验”。

### 2.5 人物、情节和读者期待必须形成共同的因果网络

单独研究人物弧光、节奏、场景，有可能把它们割裂成三个独立指标。

实际上，优秀的场景往往同时完成三者。

假设主角为救同伴，必须公开自己一直隐瞒的身份：

- 人物弧光：从保护秘密转为承担公开身份的风险。
- 情节推进：旧势力获知主角下落。
- 关系变化：同伴终于知道主角隐瞒的原因。
- 读者兑现：长期存在的身份谜题得到部分解答。
- 下一轮压力：公开身份带来新的敌人。

这一场戏提供的文学价值，并不等于五项指标分别加分，而在于它们产生共同的因果推动。

InkOS 的现有规则中已经有“多个叙事轴”“人物选择因果”“后果存续”以及“承诺兑现”等思想。

下一步真正需要检查的是，Planner 输出的章级任务是否能保留这种相互关联，还是最终退化成一份分离的任务清单。

### 2.6 审订质量：从主观判断转向可定位的问题

InkOS 的 `inkos-story-review/references/review-matrix.md` 没有把文学审查简单变成一个数值评分表，而是强调按作品类型调整判断标准。

比如悬疑重视线索公平性和证据可见性，爱情重视关系发展和潜台词，文学性作品可以牺牲部分情节推进速度，但不能出现空洞重复。

同时审阅问题需要说明：

问题是什么 → 证据在哪里 → 对读者有什么影响 → 应当修复到什么层级。

审订还区分：

- `local`：句子、段落或局部表达问题。
- `structural`：场景缺失、人物因果、视角、时间线或兑现不足。
- `unknown`：现有证据无法确定原因。

这里最有价值的机制是：不是所有写作问题都可以通过润色解决。

如果主角在没有动机的情况下突然背叛同伴，单纯修改句子流畅度根本无法解决故事问题。需要追溯人物动机和场景结构。

而且 InkOS 明确区分模型输出解析失败与作品文学质量失败，不能因为审稿工具本身出错就断定章节不合格。

这避免了把 Runtime 故障错误归因于创作质量。

## 三、L2：InkOS 如何通过 Skill 真正指导 Agent

这一部分是本轮研究的另一项重点。

### 3.1 Skill、参考资料和 Agent 的职责划分

InkOS 当前代码中，已经能看到以下分工。

| 层次       | 代表文件                                     | 负责什么                  |
| -------- | ---------------------------------------- | --------------------- |
| Skill 入口 | `inkos-long-writing/SKILL.md`            | 定义共同的文学创作原则和参考资料加载指引  |
| 专题知识     | `references/*.md`                        | 提供某类文学问题的具体处理方法       |
| Agent 协议 | `planner-prompts.ts`、`writer-prompts.ts` | 定义当前角色要交付什么、遵守哪些动态约束  |
| 结构化任务    | Chapter Memo、Context Package             | 告诉 Agent 当前章节具体需要完成什么 |
| 审阅 Skill | `inkos-story-review`                     | 提供按题材调整的审稿标准和修复判断     |
| 执行工具     | `worker-agent.ts` 等                      | 负责调用模型、取得结构化结果        |

可以看到，Skill 的内容不再主要是“使用什么工具、执行哪个命令、修改哪个文件”。

它聚焦文学知识本身。

### 3.2 长篇创作 Skill 的内容组织

inkos-long-writing/

SKILL.md

共同文学方法、适用角色、按任务加载资源的入口

references/

foundation-design.md

人物弧光、核心冲突、卷结构、长线承诺、不可逆变化

reader-contract-and-progression.md

开篇、阅读承诺、章节推进、故事周期、因果连续性

scene-dialogue-and-length-budget.md

场景预算、对话压力、篇幅偏差修复

state-projection.md

从已完成的正文提取和投影故事状态

来源：[InkOS 长篇 Skill 源码目录](https://github.com/dehuadong/inkos/tree/master/packages/core/skills/inkos-long-writing)。

这样的组织方式体现出三个层次：

第一层是通用原则。 例如“场景要有目标、阻力、转折和后果”，适用于大多数小说任务。

第二层是专题方法。 例如建构故事基础时关注人物弧光和卷结构，章节写作时关注场景容量和对话压力。

第三层是当前作品的动态要求。 例如当前主角处在什么心理状态、本章具体发生什么事、已有伏笔是否已经兑现。这些不应该作为固定文学知识写死在 Skill 中。

这种组织有利于让专业知识长期复用，而不让 Skill 逐渐变成某一本小说的资料库。

### 3.3 同一份文学方法，如何服务不同 Agent

InkOS 的长篇写作 Skill 明确声明，它适用于 Architect、Writer、Auditor、Reviser 等操作。

但不同 Agent 不应简单地复制同一段指导，而是利用同一种文学方法完成不同的交付。

| Agent              | 使用文学知识的重点             | 应有的交付证据          |
| ------------------ | --------------------- | ---------------- |
| Architect          | 设计冲突、人物弧光、卷级目标、长期承诺   | 人物有动机与代价，卷有不可逆变化 |
| Planner            | 将大纲和当前状态转换为下一章的戏剧任务   | 目标、事件、选择、后果、读者期待 |
| Composer           | 组织本次任务所需的权威信息和规则      | 选中上下文、规则栈、编译轨迹   |
| Writer             | 把文学任务落实为人物行动、场景、对话与叙述 | 正文中可以观察到真实变化     |
| Reviewer / Auditor | 判断作品是否完成文学任务          | 具体问题、文本证据、读者影响   |
| Reviser            | 找出适当修复范围，保留有效部分       | 修订内容和修复后的连贯性     |

这一表格是根据源码职责作出的归纳，不是 InkOS 原样提供的 Agent 职责表。

特别值得注意的是：审阅 Agent 应使用与创作 Agent 一致的文学概念，但不必采用相同的创作指令。

例如 Writer 的任务是通过一个场景展示人物的重大选择，而 Reviewer 的任务是判断这个选择有没有充足的动机、压力和后果。

二者共用人物弧光的文学知识，却有不同的执行目的。

## 四、Skill 从发现到参与创作的实际链路

目前在仓库中确认了几种机制：

1\. Skill 发现与解析

从内置 Skill、项目 Skill 和外部目录建立可用 Skill 列表；根据 ID、Profile 或作品类型确定所需 Skill。

2\. Skill 激活

`use_skill` 加载 Skill 主体，允许指定 `resourcePath`，或以 `query` 检索相关参考片段。

3\. 专业指导与任务上下文组装

专业方法需要与作品权威资料、当前用户指令、章节 Memo 和选中上下文共同发挥作用。

4\. Agent 完成专业任务

Planner 交付结构化 Memo，Writer 交付正文，Reviewer 交付问题证据，Reviser 交付修订。

5\. 结果验证

检查交付协议和创作结果，并区分技术错误、叙事事实错误和文学质量问题。

这是端到端分析模型，其中第 3、4、5 步的连接完整性仍需通过调用路径验证。

### 4.1 已确认：Skill 不需要全部预先放进上下文

`agent/skill-tool.ts` 已提供：

- `skillId`：精确选择专业 Skill。
- `resourcePath`：读取某个明确的资源文件。
- `query`：检索与当前任务相关的参考片段。
- 已激活 Skill 的内容与引用资源可以形成一次任务中的指导信息。

`skills/activations.ts` 则负责根据 Work Profile、作品类型等确定必需的 Skill。

这表明 InkOS 不是单纯把所有文学知识文件一次性拼进 Prompt，而是已经具备按需选择和加载的基础设施。

### 4.2 需要特别核实：专业知识是否真正进入每个 Worker

我检查了 `planner-prompts.ts`、`writer-prompts.ts`、`planner.ts`、`writer.ts` 等文件。

其中有一个值得关注的现象：

Planner 的系统提示词明确写着：

> 专业规划方法只来自已激活 Skill。

Writer 也有类似要求：

> 按已激活的专业 Skill 为当前作品写一章。

但是，仅仅在系统提示词中要求遵守已激活 Skill，并不能证明该 Skill 的正文及关联 references 已经传递给了那个 Worker。

完整验证还必须回答：

1. 谁激活了 Skill？
2. 激活结果由哪个对象保存？
3. Planner / Writer 的实际模型消息中是否包含 Skill 内容？
4. 哪些 references 被加载了？哪些仅保留在目录中？
5. 审阅和修订是否使用了与写作一致的文学标准？
6. 加载失败或漏加载能否被运行轨迹发现？

在已读取的代码里，能够确认 Skill 激活工具和 Worker Prompt 都存在；但尚未完整追踪它们之间所有调用路径，因此不能宣布这条链路已经端到端验收通过。

这也是本轮 L2 最重要的技术核查问题。

## 七、这一轮的核心结论

从目前已经确认的源码看，InkOS 具有三个值得重点理解的特点。

第一，它把文学质量从抽象要求转成了具体创作动作。 人物通过选择和代价改变，场景通过阻力和转折推进，读者期待通过事实和行动逐渐兑现。

第二，它开始建立可复用的文学知识体系。 文学方法保存在 Skill 及专题 references 中，角色的动态任务则留在 Agent 协议和作品上下文里。这比把全部内容塞进一个庞大的 Writer Prompt 更清晰。

第三，它还需要用端到端证据证明文学知识确实发挥了作用。 不能仅凭某个 Skill 包含了人物弧光规则，就断言 Writer 会正确应用，更不能据此认为 Reviewer 已经能够可靠发现人物成长失真。

我认为下一轮尤其值得深入的是两个彼此关联的问题：

人物弧光如何跨几十章持续演进，以及 Skill 的文学指导究竟通过什么机制进入 Planner、Writer、Reviewer 和 Reviser 的真实执行上下文。

这两项能够把 L1 的文学内容和 L2 的专业知识组织真正连接起来，而不仅停留在分别分析规则文档和 Runtime 的层面。
