# InkOS 专题研究：历史章节修订与内容依赖一致性

研究基线：[InkOS ](https://github.com/dehuadong/inkos/commit/8fc2ae57080b9821257dee3e37cc677e2b6f389a)[`master`](https://github.com/dehuadong/inkos/commit/8fc2ae57080b9821257dee3e37cc677e2b6f389a)[ · ](https://github.com/dehuadong/inkos/commit/8fc2ae57080b9821257dee3e37cc677e2b6f389a)[`8fc2ae57`](https://github.com/dehuadong/inkos/commit/8fc2ae57080b9821257dee3e37cc677e2b6f389a) · 仅分析 InkOS，不涉及 Novel 改造

## 一、核心发现：历史修订存在两条不完全一致的状态链路

本轮确认了一个关键事实：

InkOS 已经能够用历史快照对早期章节重新结算，但它为 Reviser 准备的创作上下文，并不保证使用同一个历史时间点。

这使得“历史章节修订”不能简单理解为“取出旧正文 → 修改 → 重新定稿”。它实际上涉及两种独立的一致性要求：

- 时间一致性：第 30 章的角色不能凭空知道第 95 章才出现的信息。
- 依赖一致性：第 30 章改变以后，第 31～120 章中依赖旧事实的内容需要被识别和处理。

InkOS 对第一项已经有部分历史快照能力；对第二项已经有下游审阅提示。但两者还没有完全闭环。

### 用一个具体案例贯穿研究

假设作品已经完成 120 章：

| 章节      | 原来的故事事实       |
| ------- | ------------- |
| 第 12 章  | 主角取得一封身份不明的密信 |
| 第 30 章  | 主角从密信中找到可疑的姓名 |
| 第 65 章  | 主角因错误推断而信任某人  |
| 第 95 章  | 主角真正知道幕后主使的身份 |
| 第 120 章 | 主角已经公开真相      |

作者现在要求：修改第 30 章，让主角连可疑姓名也没有发现。

这不是单纯的文字润色，因为它可能改变第 65 章的行为原因，并影响第 95 章的揭露效果。

## 二、InkOS 当前的实际修订流程

根据 [pipeline/runner.ts 中的 ](https://github.com/dehuadong/inkos/blob/master/packages/core/src/pipeline/runner.ts#L874-L1164)[`reviseDraft()`](https://github.com/dehuadong/inkos/blob/master/packages/core/src/pipeline/runner.ts#L874-L1164)，调用顺序如下：

读取第 30 章正文及修订要求

准备修订上下文

Composer 选择任务相关资料，目前读取最新状态

读取第 29 章历史状态快照

建立第 30 章重新结算的状态基线

Reviser 生成修订正文

按修订方式及审阅问题调整

Settler + State Validator

从修订正文提取状态变化，并核对第 29 章基线

保存修订正文及章节索引

非最新章节，不直接覆盖当前第 120 章状态

为下游章节添加连续性审阅提示

### 哪些地方做对了？

第一，历史状态快照是真正的数据对象，不只是历史摘要。

`loadRuntimeStateSnapshotAtChapter()` 会读取目标章节快照目录里的 `manifest.json`、`current_state.json`、`hooks.json` 和 `chapter_summaries.json`，并验证其结构。如果快照不完整，则直接失败。

这为历史事实重算提供了可信基线。

第二，非最新章节的修改不会直接倒退全书当前状态。

在 `reviseDraft()` 中，如果修改的是最新章节，可以走 `writer.saveChapter()`；如果修改的是早期章节，正式写入主要是目标正文和 `chapters/index.json`。

这避免了将第 30 章结算后的状态误当成整个作品最新状态。

第三，下游不会被默认为已经验证。

系统为后续章节添加 `upstream-revision` 观察，提醒需要重新检查连续性。

这些都是实际代码实现的安全边界。

### 但存在一个明显缺口

下游已被标记“需要审查”，不代表旧事实已经重新计算，更不代表依赖旧事实的章节已经修复。

例如第 65 章因为第 30 章发生变化而失去因果依据，单纯给它增加一条 `upstream-revision` 记录，不会自动修好这个问题。

这需要继续分析具体的失效传播和恢复能力。

## 三、历史修订存在三处需要特别注意的风险

### 1. Reviser 可能接触未来信息

结合 [Composer 的 ](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agents/composer.ts#L334-L365)[`selectTaskContext()`](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agents/composer.ts#L334-L365) 与 `prepareExistingChapterContext()`，可以把问题定位到具体的数据来源。

| 内容来源                     | 读取行为                                | 修订第 30 章时的风险      |
| ------------------------ | ----------------------------------- | ----------------- |
| 当前事实                     | `loadRuntimeStateSnapshot()` 读取最新状态 | 可能含第 95 章才出现的知识   |
| 人物卡片                     | 读取当前目录的人物 Markdown                  | 可能含后期身份、关系变化      |
| Chapter Summary          | 最终选择会排除目标章节及之后的摘要                   | 语义筛选候选阶段仍可能接触未来摘要 |
| Hook 引用                  | 从最新可查询伏笔中按 ID 查找                    | 最近推进可能发生在目标章节之后   |
| Story Frame / Book Rules | 读取当前作品规则                            | 新作者决定可能被应用于历史剧情   |

这里还发现一个值得关注的细节。

`buildReferencedHookEntries()` 会使用 Hook 的 `lastAdvancedChapter` 定位最近一次推进，但没有在该函数中限制：

`lastAdvancedChapter` 必须早于本次修订的目标章节。

因此，某个伏笔如果在第 80 章得到推进，在第 30 章的历史修订上下文中，就存在被引用的可能。

而且 `completeContextWithinBudget()` 在资料放得下时，会选择完整工作集，不再依赖模型判断相关性。因此，未来事实不能仅靠“语义模型应该懂时间顺序”来避免。

研究判断：这是一条源码可确认的时间隔离缺口，但尚未通过固定样例实测其对生成正文的实际影响。

### 2. 修订第 30 章后，当前状态未必与新版正文一致

InkOS 的设计刻意避免非最新章节覆盖当前状态，这是正确的保护措施。

然而，它也产生了另一个问题。

假设原状态：

第 30 章旧版

主角发现姓名

第 65 章

基于错误推断作出选择

第 120 章当前状态

包含上述事件的后续结果

第 30 章修订

取消发现姓名

第 30 章正文已经变化，但第 120 章状态仍可能包含旧因果链

`reviseDraft()` 在非最新章节情况下，写入目标正文和章节索引，而不是重新执行第 31～120 章的状态重放。

因此可能出现：

正式正文已经修改，但当前叙事状态仍反映旧正文。

如果下一次 Writer 继续创作第 121 章，使用的可能仍然是历史修订前的状态依据。

InkOS 通过 `upstream-revision` 标记提示问题，但目前没有看到这一标记被 `getNextChapterNumber()` 的进度计算强制作为阻断条件。

`state-bootstrap.ts` 的 `resolveDurableStoryProgress()` 主要核查章节索引与正文文件是否连续、一致，并不对后续章节的叙事依赖进行语义验收。

这说明章节文件完整性与作品因果一致性是两个独立的验收门禁。

### 3. 下游审阅标记可能被普通审阅覆盖

这是本轮新发现的另一处具体实现问题。

历史修订后，`reviseDraft()` 会给后续章节写入：

```
{
  "code": "upstream-revision",
  "summary": "第30章已重写，请重新检查本章与前文的连续性。",
  "evidence": []
}
```

但是在 [runner.ts 的 ](https://github.com/dehuadong/inkos/blob/master/packages/core/src/pipeline/runner.ts#L820-L871)[`reviewChapter()`](https://github.com/dehuadong/inkos/blob/master/packages/core/src/pipeline/runner.ts#L820-L871) 中，普通章节审阅完成后，会用本次审阅返回的 `result.observations` 替换章节原有观察列表。

这意味着：原先的 `upstream-revision` 可能消失，即使本次审阅没有明确证明它所代表的因果影响已经解决。

这里需要区别：

- 审阅发现“没有明显文字问题”。
- 审阅证明“第 30 章的改变没有破坏第 65 章的因果”。

这不是同一个结论。

因此，普通 Review 不应被直接等同于完整的下游影响消除。不过，目前还需要通过针对性测试确认该行为在实际操作中的表现。

## 四、Settler 和 Validator 能否阻止错误进入正式作品？

这一点还需要关注“校验失败后是否继续保存”。

InkOS 的正常创作流程和历史修订流程具有不同的恢复策略。

### 正常创作

[chapter-truth-validation.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/pipeline/chapter-truth-validation.ts) 会在状态验证失败时尝试重新结算。

如果恢复仍不成功，它可以保留原有 canonical runtime state，而不强行采用错误状态，同时将问题作为观察记录。

这是保护事实权威的策略。

但章节本身仍可能带着未解决观察进入持久化流程。是否允许最终交付，需要继续结合具体交付门禁判断，不能把“保留了旧事实”说成“章节完全通过验收”。

### 历史修订

`reviseDraft()` 在状态验证发现不一致时，也会尝试重新结算。

但在当前实现中，即使重新结算后仍有 `stateValidation` 观察，代码仍会整理 `postRevisionObservations` 并继续进入修订正文的保存逻辑。

这说明历史修订存在一种状态：

修订正文已经保存，状态验证问题仍作为观察保留。

对于文学创作草稿，这种做法未必不合理；但如果将这一操作解释为“完成了历史章节修订及因果一致性恢复”，就过度宣称了。

另一个边界是 [StateValidatorAgent](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agents/state-validator.ts)：如果旧状态和新状态相同，它会快速返回一致，不再调用 LLM。这个判断能够识别“没有提交状态差异”，却不能单独证明“新正文确实没有应记录的变化”。

## 五、InkOS 目前有哪些真正可用的恢复手段？

| 恢复机制      | 已确认的实际能力                                 | 局限                 |
| --------- | ---------------------------------------- | ------------------ |
| 历史正文版本    | `archiveChapterVersion()` 保留旧正文          | 保存版本不等于自动解决后续因果    |
| 历史状态快照    | 按章节读取完整 State Snapshot                   | 快照本身可能属于旧叙事分支      |
| 最新章节状态再同步 | `resyncChapterStateAndAudit()` 重新结算并审阅   | 明确只允许最新章节          |
| 状态恢复      | `restoreState()` 从章节快照恢复 canonical state | 单独恢复状态不是重写后续正文     |
| 章节回滚      | `rollbackToChapter()` 回退章节及状态            | 适合明确回滚，不是非破坏性的历史修订 |
| 修订影响标记    | `upstream-revision` 告知后续章节需审阅            | 不会自动形成已验证的因果重算结果   |

这里有一项需要更正可能的误解：

InkOS 的 `resyncChapterStateAndAudit()` 并不是任意历史章节的状态重算工具。

我检查了 `_resyncChapterArtifactsLocked()`，它明确拒绝非最新章节：

> `Only the latest persisted chapter can be synced safely`

这项限制保护了当前状态不被早期状态覆盖。

但也意味着，不能简单地认为“历史修订后，依次调用现有 resync 接口就能把第 31～120 章全部重放”。

当前代码尚未提供这样一个已经验证的完整恢复流程。

## 六、如果要实际验证，应该构造什么测试？

下面是针对 InkOS 本身的测试设计，不涉及修改任何其他项目。

| 测试        | 操作                                         | 通过标准                               |
| --------- | ------------------------------------------ | ---------------------------------- |
| T1 时间隔离   | 在第 95 章新增身份揭露，再修订第 30 章                    | Reviser、Reviewer 和上下文筛选器不会错误使用未来事实 |
| T2 历史正文修订 | 删除第 30 章关键事件                               | 不会将新版第 30 章状态直接覆盖第 120 章状态         |
| T3 下游依赖   | 让第 65 章行为依赖被删除事件                           | 下游影响可明确识别，不能默认为已恢复                 |
| T4 审阅标记保留 | 给第 65 章增加 `upstream-revision`，再执行普通 Review | 未解决的依赖问题不会仅因刷新观察列表而消失              |
| T5 继续创作   | 存在未处理的重大历史依赖时尝试写第 121 章                    | 系统能明确识别风险，而不是静默沿用旧状态               |
| T6 旧 Memo | 修订第 30 章，再复用旧第 65 章规划                      | 能检测 Memo 是否依赖过期事实                  |
| T7 无变化修订  | Reviser 返回与原文相同的正文                         | 不应无意义地让所有下游章节失效                    |
| T8 故障恢复   | 在历史修订保存、同步 Artifact 或更新索引之间模拟中断            | 不会把部分成功当作全流程成功                     |

这些测试中，T1、T3、T4 和 T5 最值得优先开展，因为它们直接影响长篇作品的叙事正确性。

目前我没有实际运行这组新实验，因此不能把源码推断等同于已复现的故障。

## 七、研究结论：历史修订需要区分三个层次

从 InkOS 的实现看，历史章节修订至少有三个层次：

第一层：正文版本修订

已实现

保存旧版、按范围修订、验证来源、保存新版。

第二层：目标章节状态重算

核心已实现

使用目标章节之前的快照，提取修订后的事实变化，并进行校验。

第三层：下游作品一致性恢复

尚未闭环

判断后续章节是否依赖旧事实、是否需要修改，以及如何更新状态、摘要、规划和上下文。

前两层主要解决单章正确性；第三层解决整部作品的一致性。

### 本轮发现的优先级

| 优先级 | 发现                                   | 原因            |
| --- | ------------------------------------ | ------------- |
| P0  | 历史修订可能使用未来状态                         | 直接影响人物认知和时间线  |
| P0  | 历史修订后，最新状态与新版正文可能不一致                 | 可能污染后续创作      |
| P0  | `upstream-revision` 缺乏可靠的解除条件        | 下游风险可能被普通审阅覆盖 |
| P1  | 旧 Chapter Memo 缺少来源版本有效性检查           | 可能复用失效的剧情计划   |
| P1  | 当前 ContextPackage 缺少完整来源 Revision 绑定 | 难以精确重现历史执行依据  |
| P2  | 修订无变化时仍可能产生下游提示                      | 造成不必要的审阅负担    |

## 八、最终判断

InkOS 的历史章节修订并不是一个简单、粗糙的重写工具。它已经有相当扎实的版本快照、历史状态基线、结构化结算、审阅和范围控制机制。

但从当前源码看，它更接近：

安全保存历史正文变更 + 对目标章节重新结算 + 提醒后续章节存在影响。

距离下面这个更强的目标，还有明确差距：

历史章节发生变化 → 精确识别受影响的事实和内容 → 验证或修复下游依赖 → 重新建立一致的当前状态 → 更新记忆索引与任务上下文。

这也是本轮最重要的研究认识：

> 长篇小说的历史修订，真正困难的不是修改第 30 章，而是证明第 31～120 章在这次修改之后仍然成立。

下一轮最值得进一步研究的是 InkOS 如何表示叙事因果依赖，以及是否可以从 StateDelta、Hook、Chapter Summary、ChapterTrace 中推导出可靠的影响范围。这能直接回答：究竟必须重新审阅所有后续章节，还是有办法精准找出真正受影响的部分。

本轮未修改仓库，也未将研究结论扩展为 Novel 的实施方案。
