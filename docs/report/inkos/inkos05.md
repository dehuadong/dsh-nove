# InkOS 第四轮研究：内容权威、一致性与上下文交接的薄弱环节

本轮继续只研究 InkOS，不涉及 Novel 的设计或修改。

我将源码范围固定在 InkOS `master` 提交 [`8fc2ae57`](https://github.com/dehuadong/inkos/commit/8fc2ae57080b9821257dee3e37cc677e2b6f389a)，重点核对了规划、创作、审阅、状态结算、作品基础修订和版本管理。

这次有四个重要发现：

1. InkOS 已经定义了明确的内容权威优先级，但不是所有冲突都能由代码自动裁决。
2. Chapter Memo 的文学内容比 JSON Schema 丰富得多。 结构化字段只有少数几个，大量创作约束仍然依赖 Skill、Prompt 和 Reviewer。
3. Planner、Writer、Reviewer 接收的上下文确实不同，但“按需选择”仍有遗漏关键资料的风险。
4. InkOS 已经实现版本保留和部分下游失效标记，但还不能证明它建立了完整的跨资料依赖失效图。

## 一、内容权威发生冲突时，谁优先？

我从 [writer-prompts.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agents/writer-prompts.ts) 中确认了实际编写给 Writer 的权威规则。

| 权威内容         | 在 Writer 中的作用      | 冲突时的原则         |
| ------------ | ------------------ | -------------- |
| 当前作者指令       | 决定当前章节需要达到的目标      | 不能被普通创作建议替代    |
| Chapter Memo | 规定本章的情节任务和推进方式     | 本章执行依据         |
| 已发生事实        | 约束人物知识、关系与故事事件     | 不能被新规划随意改写     |
| 明确禁令与作品规则    | 禁止违背叙事人称、主角边界和作者要求 | 必须遵守           |
| 当前相关上下文      | 提供背景、人物状态、伏笔依据     | 不可随意丢弃必要证据     |
| Volume Map   | 为后续情节提供规划方向        | 与更高权威冲突时只能作为参考 |
| Skill 创作方法   | 提供专业写作建议           | 不得覆盖作者决定与作品事实  |

这里的关键不是绝对的线性排名。

作者当然可以决定修改自己的创作合同，但这不意味着 Writer 可以据此直接抹掉已经发表的事件。作者的新指令需要先经过正确的领域修改动作，才能改变既有事实的正式版本。

InkOS 已有这些边界的不同执行机制：

- `BookRulesSchema` 对结构化作品规则做类型校验；
- `StateReducer` 检查章节事实和伏笔状态操作；
- `artifact-edit-policy.ts` 限制绕过领域操作修改资料；
- `StateValidator` 检查新旧事实对账；
- Writer Prompt 明确哪些是当前任务、哪些是历史约束、哪些只是规划。

但如果 Story Frame 和人物卡片分别写着两种不同的人物性格，仅靠这些机制的存在，不能证明系统一定能自动判断哪一种设定应生效。

因此，InkOS 已实现的是“内容权威分层与部分强制校验”，还不是“所有语义冲突都能自动确定最终权威”。

## 二、Chapter Memo 的内容设计比 Schema 更重要

这是本轮最值得关注的内容发现。

InkOS 的 [ChapterMemoToolSchema](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agents/planner-tool.ts) 实际只要求：

```
{
  "goal": "本章必须完成的叙事目标",
  "body": "完整的 Markdown 章节规划",
  "threadRefs": ["H1"]
}
```

并没有为每个场景、每个心理变化、每个读者期待都定义独立 JSON 字段。

但在 [reader-contract-and-progression.md](https://github.com/dehuadong/inkos/blob/master/packages/core/skills/inkos-long-writing/references/reader-contract-and-progression.md) 中，它又要求章节规划考虑即时行动、读者期待、兑现或延后、过渡场景的作用、人物选择因果、章尾变化和伏笔推进。

这意味着 InkOS 采用的是：

少量机器字段 + 丰富的文学规划正文 + 专业 Skill 约束。

### 查看测试中的完整 Chapter Memo 样例

[持久化规划测试](https://github.com/dehuadong/inkos/blob/master/packages/core/src/__tests__/persisted-governed-plan.test.ts) 里的示例包含如下内容结构：

| Memo 章节     | 需要回答的问题            |
| ----------- | ------------------ |
| 当前任务        | 本章主角到底要完成什么？       |
| 场景与篇幅预算     | 哪些场景承载多少情节？        |
| 读者此刻在等什么    | 本章应回应什么期待？         |
| 该兑现的／暂不掀的   | 哪些悬念现在推进，哪些保留？     |
| 日常／过渡承担什么任务 | 看似平静的场景如何推动叙事？     |
| 关键抉择过三连问    | 为什么现在行动、是否符合利益与人设？ |
| 章尾必须发生的改变   | 本章结束后什么状态不可逆地改变？   |
| 本章 Hook 账   | 哪条伏笔推进，哪条延后？       |
| 不要做         | 当前章节有哪些明确禁止事项？     |

这类 Memo 不只是剧情摘要，而是一份可直接指导创作的内容合同。

不过，还必须区分两个层次：

- Schema 层面：能验证 `goal`、`body`、`threadRefs` 是否符合基本格式。
- 文学语义层面：是否真的具备场景容量、因果变化、人物动机与读者承诺，需要模型审阅或更进一步的内容验证。

因此，测试文件中有完整的规划样例，不等于所有真实生成的 Memo 都一定包含上述全部章节。

这也是 InkOS 内容方法与运行时强制合同之间的重要边界。

## 三、上下文交接的核心问题：选中资料，不等于选全了资料

在 [composer.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agents/composer.ts) 中，InkOS 对不同资料采用不同的选择方式。

| 内容                       | 选择方式            | 进入上下文后的保护级别  |
| ------------------------ | --------------- | ------------ |
| 作者长期意图                   | 直接读取            | Protected    |
| 当前创作焦点                   | 直接读取            | Protected    |
| Chapter Memo             | 直接注入            | Protected    |
| Story Frame / Volume Map | 按 Markdown 章节筛选 | Protected    |
| 人物卡片                     | 根据章节目标选择角色      | Protected    |
| 当前有效事实                   | 根据任务进行语义选择      | Protected    |
| Memo 指定的 Hook            | 按 ID 追踪初始和最近推进  | Protected    |
| 历史章节摘要                   | FTS5 候选召回与语义筛选  | Compressible |
| 卷摘要                      | 检索后选择           | Compressible |
| 其他相关伏笔                   | 检索后选择           | Compressible |

这里的 Protected 表示选中后不能被随意压缩，不表示该信息一定会被选中。

这一差别非常关键。

### 1. 人物知识可能没有进入上下文

假设第 80 章需要一个配角暗中向反派传递消息，但章节任务只提到了“密信失踪”。

Composer 会按照任务语义选择人物卡片。如果角色姓名、身份或者关联事件没有进入候选选择结果，即使其人物卡片写着重要设定，Writer 也不一定会得到它。

InkOS 能做的是：

- 枚举人物卡片；
- 根据任务筛选；
- 拒绝筛选器返回不存在的来源 ID；
- 将选中的人物卡片作为受保护资料。

但没有看到独立的、必须覆盖所有相关人物的完整性门禁。

这意味着选中的内容能够受到保护，未选中的关键内容仍有可能被遗漏。

### 2. 伏笔 ID 的查找也有特殊边界

Composer 会根据 `threadRefs` 找到具体伏笔，并补充埋设和最近推进信息。

但 `buildReferencedHookEntries()` 中，如果某个引用的 Hook ID 没有在当前可查伏笔列表中找到，就会跳过该条目。

而且，`memory-retrieval.ts` 中的可查伏笔主要是未解决、未被撤销的伏笔。

因此，如果 Memo 仍引用一个已经撤销的 Hook，或者引用了无法解析的 Hook ID，单独这一条 Composer 路径不会保证产生明确的缺失错误。

注意：这不等于系统所有地方都允许无效 Hook ID。 Settler、Hook Arbiter 和 Reducer 另有校验。这里发现的是“上下文准备时的引用完整性”边界，与“最终事实操作是否合法”不是同一层问题。

### 3. 检索结果缺少版本绑定

目前 `ContextSourceSchema` 的字段是：

```
{
  "source": "story/roles/主要角色/某人.md",
  "reason": "本章涉及此人物",
  "excerpt": "人物相关设定",
  "protection": "protected"
}
```

真实 Schema 还没有强制要求：

- 来源 Artifact Revision ID；
- 来源文件的 SHA；
- 对应的 Runtime State Revision；
- 检索时的权威快照版本；
- 选中内容的有效期。

`ChapterTrace` 虽然会保存来源 ID、检索候选、压缩记录与 Token 预算，但不能单凭它证明已保存的上下文一定对应某个可精确重现的作品版本。

这属于可追溯性已经存在，但精确版本一致性尚未充分证明。

## 四、内容修改后的失效传播：目前实际能走多远？

假设一部小说已经写到第 120 章，作者要求更改第 30 章的人物秘密。

理论上受影响的内容可能形成如下链条：

上游变更：第 30 章正文或基础设定

人物卡片 / 角色认知

章节摘要 / 当前事实

伏笔状态 / 回收计划

未来章纲 / Chapter Memo

后续上下文、审阅证据、检索索引

这是潜在依赖关系示意，不是 InkOS 已实现的自动级联流程。

| 变更对象          | InkOS 已确认行为        | 尚未证明的部分                        |
| ------------- | ------------------ | ------------------------------ |
| Foundation 修改 | 重建框架、卷纲、角色卡，保留历史状态 | 是否自动失效全部受影响的 Memo              |
| 作者禁令改变        | 结构化规则重新生成并保存版本     | 是否自动检查所有既有章节的语义冲突              |
| 历史正文修改        | 保存原文版本，标记后续章节需审查   | 是否完成全部后续事件与摘要重放                |
| 伏笔撤销          | 保留撤销原因，排除待解伏笔召回    | 已保存 Memo 是否立即失效                |
| 章节摘要变化        | 下次检索可从新结构化摘要重建索引   | 已持久化的 ContextPackage 是否作废      |
| 角色卡片变化        | 下一次正常上下文选择可以读取新卡片  | 之前保存的 ContextPackage 是否能自动检测过期 |

### 特别值得关注：旧 Memo 的复用

[resolveGovernedPlan()](https://github.com/dehuadong/inkos/blob/master/packages/core/src/pipeline/runner.ts) 在指定允许复用、且没有新的外部指令时，会尝试读取持久化的章节 Memo。

从 `persisted-governed-plan.ts` 的实际 Schema 看，它保存了章节编号、目标、Memo 和 `plannerInputs`，但没有保存完整的上游资料版本集合。

因此，即使上游 Story Frame 已经修订，也不能仅凭 `plan.json` 的格式验证，就确认原 Memo 仍然适用。

这是本轮最明确的潜在一致性缺口之一：缓存存在且合法，不等于它仍然有效。

## 五、还有三个容易忽略的内容交接机制

### 1. InkOS 实际存在三种不同作用域的上下文

研究 [base.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agents/base.ts)、[agent-context.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/harness/agent-context.ts) 和 `composer.ts` 后，可以进一步区分：

| 上下文     | 管理内容                            | 作用范围        |
| ------- | ------------------------------- | ----------- |
| 会话上下文   | 作者当前请求、工具调用、执行进度、对话摘要           | 主 Agent 的会话 |
| 专业方法上下文 | 激活的 Skill、相关 References、创作与审阅方法 | 某次 Agent 执行 |
| 章节领域上下文 | Memo、当前事实、人物、伏笔、历史摘要            | 具体章节任务      |

这三种上下文各有自己的装载、压缩和恢复机制。

尤其重要的是：主 Agent 历史对话被压缩后，其摘要被明确标注为不能替代执行权威。

也就是说，之前的聊天摘要不应该因为保存了某句话，就自动获得覆盖当前作者请求或作品权威文件的权限。

另外，Worker 每次使用 Skill 时会记录 `skills-applied` 证据，包括 Skill 正文及参考片段的哈希。

这至少能追查：本次执行究竟加载了哪个版本的专业方法。但它仍不能证明文学方法已被正确落实到正文。

### 2. Reviewer 不只是文学评价者，也是版本对照者

InkOS 的 Reviewer 可以取得 Artifact 的前后版本，检查修订是否越过用户允许的范围。

[chapter-review-scope.flow.test.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/__tests__/chapter-review-scope.flow.test.ts) 验证了：

- 初始修订修改了作者未允许的段落，产生范围问题；
- 问题没有解决时，交付门禁拒绝将其视为完成；
- 后续修订解决范围问题，才允许通过相应检查。

这种机制把“文学质量审查”和“授权范围审查”区分开了。

### 3. 状态校验有一个需要进一步验证的快速路径

[StateValidatorAgent.validate()](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agents/state-validator.ts) 有一个优化：

当旧状态与新状态文本相同、旧伏笔与新伏笔文本也相同时，直接返回一致，无须再次调用 LLM。

对于真正没有产生状态变化的章节，这是合理的优化。

但存在需要检验的另一种情形：

正文实际产生了重要事件，而 Settler 错误地提交了空变化。

此时旧状态与新状态仍然相同，快速路径本身无法判断是否遗漏了应记录的事实。

其他审阅或结算步骤可能发现问题，因此目前不能直接认定会发生漏记。不过，该快速路径不能单独证明“新正文的所有必要状态变化均已提取”。

这说明状态质量至少包含两个不同问题：

- 已提交的变化有没有矛盾？
- 应该提交的变化有没有遗漏？

后者通常更难检查。

## 六、一次实际内容变更的完整影响分析

用一个虚构情境，把本轮发现放在同一条链路中。

假设第 120 章即将开始，作者决定撤销原本计划在第 130 章揭晓的“幕后主使是男主父亲”这一设定。

| 内容节点                  | 需要发生什么              | InkOS 当前可确认的能力            |
| --------------------- | ------------------- | ------------------------- |
| 作者意图                  | 保存新裁决               | 有创作控制文档与明确执行请求            |
| Story Foundation      | 修改反派身份、主线及相关角色卡     | 有 Architect 基础修订          |
| 已发生事实                 | 保留此前确实发生的事件         | 基础修订不直接重置 Runtime State   |
| Hook H015             | 原承诺作废，保留撤销原因        | Reducer 支持 `superseded`   |
| 第 120 章 Memo          | 不能继续要求按原计划揭露父亲身份    | 未证明自动依赖失效                 |
| Writer ContextPackage | 加载新的作品规则，不使用废弃设定    | 能重新选择资料，但需验证完整性           |
| 第 121—130 章规划         | 调整相关场景和因果关系         | 未证明自动级联更新                 |
| 历史审阅证据                | 区分旧版本中的有效信息和撤销的未来计划 | 有 Artifact 版本能力，但完整关联仍需验证 |

这个案例揭示了几个不同操作不能混淆：

创作方向修改不是事实重写；撤销未来伏笔不是抹除既有事件；索引更新不是旧规划自动失效；重新选择上下文也不等于完成依赖审查。

从源码看，InkOS 已为这些问题分别建立了一些机制，但跨越所有内容类型的自动传播仍缺少充分证据。

## 八、下一轮最值得研究：内容依赖与失效机制

本轮已经梳理清楚了“内容如何生成 → 如何选取 → 如何交接 → 如何保存”。接下来值得深入的是内容依赖如何确定，以及发生变化后如何重新验证。

我建议独立研究 InkOS 的四个具体问题：

| 专题      | 研究问题                                |
| ------- | ----------------------------------- |
| 内容依赖图   | 一项人物设定关联了哪些事实、伏笔、章纲和上下文？            |
| 失效边界    | 哪些变化只需更新索引，哪些必须重新规划或审阅？             |
| 历史版本重现  | 能否证明第 80 章创作时确实使用了某个版本的设定？          |
| 召回充分性验证 | 如何发现 Planner 或 Writer 缺失了不可忽略的历史信息？ |

其中，我认为最值得优先的是 “内容依赖图 + 精确版本绑定”。

原因是 InkOS 已经有 Artifact Revision、Runtime State、Chapter Memo、ContextPackage 和 Retrieval Trace。现在的关键研究问题不是还要存储什么，而是这些已经存在的对象之间的关联，是否足以支持可靠的变更影响追踪。

本轮最终发现：InkOS 在“内容产生与任务交接”方面已经比较成熟，但“上游权威变化后，如何确保所有下游 Agent 不再依赖旧内容”，仍是值得继续验证的核心问题。

这一轮仍是 InkOS 独立研究，没有修改仓库，也没有将上述判断转换为 Novel 的实施方案。
