# InkOS 专题研究：数据库检索、长期记忆与记忆召回

独立源码研究｜2026 年 10 月 21 日

## 一、核心结论

本轮已经定位到 InkOS 的实际记忆检索实现，而不仅是 README 中对 SQLite 和长期记忆的介绍。

InkOS 的核心架构是：以作品状态文件为权威，以 SQLite FTS5 作为可重建检索索引，先召回候选，再由模型进行语义筛选，最后将相关记忆交给章节上下文编译器。

它不是把整部小说长期保存在 LLM 的对话历史中，也不是主要依靠向量 Embedding 进行相似度搜索。

依据 `memory-retrieval.ts`、`local-search.ts` 和 `composer.ts` 的实际调用关系整理。

一个非常关键的发现是：FTS5 在这里主要负责排序和优先召回，并不是唯一的候选入口。 当前代码会把没有命中的记忆也加入后续语义选择集合，以避免纯关键词检索漏掉间接相关的长期记忆。

这使系统比传统的“FTS 命中前 10 条，直接放进 Prompt”更加灵活，但也引入模型调用成本和大规模记忆候选筛选的问题。

## 二、实际使用哪些记忆

源码：[memory-retrieval.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/utils/memory-retrieval.ts)

| 类型    | 权威来源                                 | 检索粒度       | 主要作用             |
| ----- | ------------------------------------ | ---------- | ---------------- |
| 章节摘要  | `story/state/chapter_summaries.json` | 一章一条       | 回忆人物、事件、变化、情绪与伏笔 |
| 未完结伏笔 | `story/state/hooks.json`             | 一个 Hook 一条 | 召回仍有效的故事承诺       |
| 卷级摘要  | `story/volume_summaries.md`          | 一个二级标题章节一条 | 保留较长时间跨度的情节记忆    |
| 当前事实  | `story/state/current_state.json`     | 事实条目       | 提供人物、地点、关系等当前真相  |
| 前章内容  | 前一章真实正文                              | 章节正文       | 保持相邻章节的叙述衔接      |

这里有必要区分：前三类实际进入 `retrieveMemorySelection()` 的数据库记忆检索流程；当前事实和前章正文通过 Composer 等其他路径进入上下文，不能说所有内容都已统一通过 FTS5 检索。

### 2.1 伏笔过滤的实际规则

源码明确过滤：

```
hook.status !== "resolved" &&
hook.status !== "superseded"
```

也就是说，已经兑现或被废弃的 Hook 不再作为“未解决伏笔”进入此检索候选集合。

而 `open`、`progressing`、`deferred` 仍属于可检索范围。

这不是简单把近期未更新的伏笔丢弃，因为一个长期伏笔可能几十章都没有推进，但仍然是有效的叙事承诺。

### 2.2 章节摘要的特殊规则

最终选择摘要时，源码要求：

```
summary.chapter < chapterNumber
```

并额外保证前一章摘要被选中：

```
summary.chapter === chapterNumber - 1
  || selectedIds.has(summaryDocumentId(summary.chapter))
```

这意味着较早的历史摘要需要经过语义选择，而前一章摘要始终保留在结果中，用于保证最近叙事的连续性。

这是明确的“近期记忆保障”机制，但不意味着其他重要历史摘要一定能够被正确召回。

## 三、SQLite FTS5 与 BM25 的真实实现

源码：[local-search.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/retrieval/local-search.ts)。

InkOS 有一个统一的 `LocalSearchIndex`，用于故事记忆、归档材料和 Skill References 的词法检索。

### 3.1 数据库结构

主要分为两张逻辑表：

| 表                         | 职责                                     |
| ------------------------- | -------------------------------------- |
| `retrieval_documents`     | 保存 ID、Scope、Kind、来源、标题、内容、Metadata 和哈希 |
| `retrieval_documents_fts` | SQLite FTS5 全文检索索引                     |

FTS5 表基于 `retrieval_documents` 的外部内容建立，通过 INSERT、UPDATE、DELETE Trigger 保持索引同步。

数据库使用 WAL 模式，并在 `replaceScope()` 中通过事务执行更新。

### 3.2 索引不是每次全部删除重建

`replaceScope()` 首先计算每个文档的内容哈希，再比较已有索引记录。

相同 ID、相同内容哈希的文档不需要更新；内容变化时执行 Upsert；不再存在的文档则删除。

这意味着它在逻辑上执行按范围的增量同步，不是每次无条件清空整库。

```
replaceScope("story-memory", documents)
```

每次调用 `retrieveMemorySelection()` 都会用当前权威文件重新同步这组故事记忆索引。

这有助于避免数据库仍然保留已经从权威记忆文件中删除的记录。

但这只能解决索引与其输入文件之间的一致性，不能保证输入文件自身在历史章节修订后已经完成语义重算。

### 3.3 中文检索采用什么分词方法

`tokenizeSearchText()` 使用 JavaScript `Intl.Segmenter` 进行词级切分，并做 NFKC 归一化和小写处理。

对于相邻汉字单字分词结果，还会补充相邻双字组合。

例如，某个中文词被拆成单字时，补充双字组合可改善部分中文词法匹配。

此外，连字符、下划线组成的标识也有额外处理，适合检索某些术语和 ID。

但必须注意：

这不是严格意义上的中文语义搜索。

它不能天然理解：

- “失去了钥匙”与“钥匙被别人拿走”；
- “不再信任”与“关系决裂”；
- 人物别名；
- 隐含因果关系；
- 没有共同关键词的情节呼应。

这些问题仍需要后续模型语义选择处理。

### 3.4 BM25 实际如何排序

源码查询使用：

```
bm25(
  retrieval_documents_fts,
  5.0,
  1.0
)
```

即标题词项权重 5，正文词项权重 1。

FTS5 的 `bm25()` 越小表示匹配越好；InkOS 返回时取相反数，使较好的结果显示为较高的 `score`。

但评分本身只代表词法匹配排序。

高 BM25 分数不意味着该记忆的事实更权威、时间更正确，或对当前剧情更重要。

## 四、记忆召回不是简单 Top-K

这是本轮最有价值的实现细节。

### 4.1 检索 Query 从哪里来

Composer 的 `deriveRetrievalHints()` 拼接：

```
[
  plan.intent.goal,
  plan.memo.body,
  ...plan.memo.threadRefs
]
```

这意味着记忆召回不只是根据章节标题进行。

它综合章节目标、详细规划和当前涉及的伏笔 ID，使检索与本章具体创作任务关联。

### 4.2 第一阶段：FTS5 词法排序

数据库首先检索最多 200 个匹配项。

不过，源码随后执行：

```
const allCandidates = [
  ...hits,
  ...documents
    .filter(document => !hitIds.has(document.id))
    .map(document => ({
      ...document,
      score: -1_000_000
    }))
];
```

因此，没有词法命中的文档也会进入后续候选集合，只是被赋予很低的默认分数。

这是一个重要的策略选择：宁可让语义筛选器再次判断，也不把所有词法未命中项直接丢弃。

但这里也存在明显代价：随着章节摘要和伏笔数量增加，语义候选可能接近全部历史记忆，而不是严格固定大小的候选集。

### 4.3 第二阶段：LLM 语义选择

Composer 通过 `selectMemoryCandidates()` 进行模型判断。

系统要求模型根据当前章节任务，理解修订、因果、别名和改写表达，并只挑选有实质帮助的记忆。

候选过长时，`groupMemoryCandidates()` 会根据输入预算拆成多个组；过长的候选正文还可以被分片。

最终模型通过结构化工具选择候选编号，再映射回原始记忆 ID。

因此，记忆召回的整体逻辑是：

1

FTS5：优先级排序

识别显式关键词相关性。

2

全候选补足

保留未命中的潜在语义相关内容。

3

LLM：语义筛选

结合任务目标和故事因果判断相关性。

4

Composer：上下文整合

将选中的历史记忆与当前权威信息组合。

这套机制的优点是有利于降低纯关键词漏召回；缺点是模型筛选成本可能随长期记忆数量增加，需要通过实际压测判断可扩展性。

## 五、精准伏笔召回：比普通语义检索更可靠的一条路径

本轮还发现一条特别值得记录的机制：

章节 Memo 显式引用 Hook ID 时，Composer 会直接回溯该伏笔的建立与最近推进历史。

`buildReferencedHookEntries()` 读取：

- `plan.memo.threadRefs`；
- 全部可查的有效 Hook；
- 全部章节摘要；
- Hook 的 `startChapter`；
- Hook 的 `lastAdvancedChapter`。

然后建立包含初始和最近推进信息的条目。

例如：

示例：第 52 章再次涉及伏笔 H-017

示意数据，并非仓库中的真实作品。

| 伏笔   | H-017                           |
| ---- | ------------------------------- |
| 建立   | 第 8 章                           |
| 最近推进 | 第 31 章                          |
| 当前章节 | 第 52 章                          |
| 回忆材料 | 建立时的章节摘要 + 最近推进的摘要 + 当前 Hook 状态 |

这条路径有两个优点。

第一，它不完全依赖 FTS5 命中关键词，而是通过稳定的 Hook ID 定位。

第二，它不仅召回当前伏笔描述，还召回伏笔历史上的关键节点。

这比仅在 Prompt 中加入“请记住伏笔 H-017”更有用，因为模型能够看到该伏笔原本承诺了什么，最近实际发生了什么。

不过，当前溯源仍主要依赖章节摘要，不代表它自动引用了建立伏笔时的精确正文段落。

## 六、记忆如何进入最终上下文

数据库检索完成，并不意味着所有候选都会直接送给 Writer。

`collectSelectedContext()` 会把不同内容组织成带来源和保护等级的 `ContextPackage`。

| 内容           | 进入方式         | 保护等级         |
| ------------ | ------------ | ------------ |
| 当前章节 Memo    | 明确注入         | Protected    |
| 作者长期意图       | 读取权威文件       | Protected    |
| 当前创作重点       | 读取权威文件       | Protected    |
| 文风指南         | 读取权威文件       | Protected    |
| 相关当前状态事实     | 语义选择         | Protected    |
| 大纲与人物资料      | 分段选择         | 根据来源类型       |
| Memo 引用的伏笔历史 | Hook ID 定向关联 | Protected    |
| 历史章节摘要       | 数据库召回及语义选择   | Compressible |
| 卷摘要          | 数据库召回及语义选择   | Compressible |
| 一般未完结伏笔      | 数据库召回及语义选择   | Compressible |

### 6.1 为什么要区分 Protected 和 Compressible？

因为长期记忆不断增长，而模型 Context Window 有上限。

InkOS 优先保护当前作者意图和关键事实，再处理可以压缩的历史材料。

当上下文超出预算时：

- Protected 部分不允许被压缩。
- Compressible 部分可交给 `SemanticContextCompilerAgent` 归纳。
- 如果 Protected 自身超出预算，直接报错。
- 如果需要压缩，但没有可用编译器，也会报错。

这避免为了塞进更多历史信息，把作者禁令、当前状态或关键伏笔证据压缩丢失。

但也要明确：压缩本身可能损失文学细节。 程序能保证保留哪些资料不被压缩，却无法单靠压缩成功验证保留了全部重要潜台词、情绪铺垫和隐含因果。

### 6.2 完整装载优先策略

Composer 还会尝试判断：如果当前资料总量足够小，能否不经复杂语义删选，直接完整装载相关内容。

这避免在早期作品资料较少时，为不必要的选择额外消耗模型调用。

因此，InkOS 实际具有两种路径：

| 情况      | 处理                |
| ------- | ----------------- |
| 上下文足够容纳 | 尽量完整载入            |
| 上下文不足   | 选择相关资料，必要时压缩可压缩内容 |

这里的“完整”指 Composer 收集到的相关资料集合，不是整部小说所有正文。

## 七、长期记忆的更新与失效

这是判断记忆系统是否可靠的关键。

### 7.1 正常写章：结构化状态更新

写完新章节后，Writer 的 Settlement 阶段生成 `RuntimeStateDelta`。

Delta 更新：

- 当前事实；
- 伏笔状态；
- 章节摘要。

随后 Runtime 应用这些变化，更新结构化状态文件。

因此，长期记忆的主要来源并不是模型在对话中随意声称“我记住了”，而是章节完成后形成的结构化作品状态。

### 7.2 索引失效：通过权威文件重同步

下一次 `retrieveMemorySelection()` 调用时，会重新读取结构化摘要、伏笔和卷摘要，并执行 `replaceScope()`。

如果一个 Hook 已经被标为 `resolved`，它将不再出现在未完结 Hook 索引集合里。

如果某条摘要发生变化，相应内容哈希也会变化，并更新数据库。

这形成了：

`权威文件变化 → 索引同步 → 下一次检索使用新索引`

但要注意，同步检查发生在调用检索时，并不能据此认为每次文件变化都会立即推送更新到数据库。

### 7.3 历史章节修订：仍然是最重要的缺口

结合此前 L5 研究：

假设第 18 章原本写到角色 A 获得一封密信，第 42 章依据此事展开剧情。

后来作者修改第 18 章，让密信从未出现。

InkOS 可以标记后续章节需要重新检查连续性。

但这不等于：

- 第 42 章正文自动修复；
- 第 42 章摘要自动重写；
- 所有相关 Snapshot 自动重算；
- 依赖密信的全部记忆自动失效；
- 下一次召回一定过滤掉不再成立的历史叙述。

数据库的重同步只能反映已经更新的输入内容。

如果章节摘要仍然包含旧事实，SQLite 会忠实索引这个旧事实。

所以，索引更新和语义修复是两回事。

## 八、长期记忆的技术边界

本轮可以更明确地评价不同能力。

| 能力             | 状态       | 说明                         |
| -------------- | -------- | -------------------------- |
| SQLite 持久化记忆索引 | 已实现      | `story/memory.db`          |
| FTS5 全文检索      | 已实现      | 基于标题、正文词项                  |
| BM25 排序        | 已实现      | 标题权重高于正文                   |
| 中文分词处理         | 已实现      | `Intl.Segmenter` + 汉字双字组合  |
| 按 Scope 索引同步   | 已实现      | 哈希比较、增量更新与删除               |
| LLM 语义重排/选择    | 已实现      | 结构化提交候选编号                  |
| 非词法命中补召回       | 已实现      | 非命中文档仍可进入候选                |
| 近期记忆保障         | 已实现      | 前章摘要保留                     |
| 远期伏笔定向召回       | 已实现      | 使用 `threadRefs` 和 Hook ID  |
| 卷级压缩记忆         | 已实现读取与检索 | 从 `volume_summaries.md` 读取 |
| Protected 内容保护 | 已实现      | 超预算时不擅自压缩                  |
| 召回过程 Trace     | 已实现      | 候选、分数、选中 ID                |
| 基于向量的语义索引      | 未在本链路发现  | 当前为 FTS5 + LLM 选择          |
| 自动生成完整事件因果图    | 未证实      | 章节摘要仍主要为文本字段               |
| 历史修订后精准失效传播    | 未证实完整实现  | 参见 L5                      |
| 超长连载的检索规模控制    | 需压测      | 非命中候选可能全部进入语义选择            |
| 记忆召回准确率与覆盖率    | 未验证      | 缺少真实测试结果                   |

## 九、一个关键风险：全候选补足的扩展成本

InkOS 当前的召回机制实际上可能把整个故事记忆集传给语义筛选阶段。

例如，假设一部作品已有：

- 800 条章节摘要；
- 150 条未完结伏笔；
- 20 条卷摘要。

那么理论上可能形成约 970 个候选文档。

即便 FTS5 只命中其中 50 条，其余未命中记录也会作为低分候选加入。

Composer 会将候选分组，避免一次模型调用超过预算。

但这不能消除总成本：

1. 需要读取、索引及处理完整候选集合。
2. 可能产生多轮语义选择模型调用。
3. 模型需要跨批次做局部相关性判断。
4. 结果合并后，不保证全局最优排序。
5. 召回质量和调用成本可能随篇幅增长。

这里存在明确的工程权衡：

牺牲一部分检索效率，换取更高的潜在召回覆盖率。

这种权衡是否合理，需要对不同作品规模进行实际基准测试。

## 十、最值得进一步研究的三个问题

### 10.1 长期记忆是否应该只有摘要与伏笔？

InkOS 当前故事记忆索引主要由章节摘要、伏笔和卷摘要构成。

但文学创作中还有很多长期信息：

- 人物关系逐步变化的证据；
- 人物不知道却读者知道的事实；
- 某句话、道具或动作形成的隐含承诺；
- 角色反复出现的行为模式；
- 尚未被明确命名为 Hook 的伏笔；
- 跨章节场景之间的细节呼应。

这些未必都能从摘要中准确恢复。

因此，摘要式长期记忆不等于全文级高保真记忆。

### 10.2 检索相关性是否等于文学重要性？

BM25 可以判断词语相关性，LLM 可以判断语义相关性。

但文学重要性还取决于：

- 事件是否构成当前选择的因果前提；
- 某个角色是否在此前获得关键知识；
- 某个承诺是否即将兑现；
- 某项事实是否已经被修订推翻；
- 某个细节是否具有长期结构性作用。

这类重要性不是纯相似度能够完整表达的。

### 10.3 记忆来源是否具有版本可验证性？

当前 Story Memory 的检索文档包含稳定 ID、Source、Metadata 和内容哈希。

但其主要来源引用通常指向章节或 Hook，而不是始终绑定具体 Artifact Revision。

因此，当历史内容发生修订时，召回结果是否仍对应有效版本，需要依赖额外的内容同步和一致性机制。

这里是 L3 内容权威、L5 依赖传播以及本专题记忆召回之间的重要交叉点。

## 十一、专题最终结论

从代码实现来看，InkOS 的长期记忆与召回机制可以概括为：

结构化状态负责记住事实，章节摘要负责记住历史，Hook 负责记住承诺，SQLite 负责找到候选，LLM 负责判断相关性，Composer 负责组织当前任务真正需要的上下文。

这套设计具有三个明确优势：

第一，长期记忆不依赖无限延长对话上下文。 作品历史被持久化为结构化文件和可检索索引。

第二，兼顾词法效率和语义理解。 FTS5 提供排序，LLM 进一步理解角色、因果与任务相关性。

第三，对关键记忆有特殊保护机制。 最近章节、显式 Hook 引用、作者意图和当前事实，并非完全依赖普通关键词召回。

但它也有三个尚未完全解决的问题：

第一，长期记忆的语义颗粒度仍然较粗。 摘要和伏笔能够保留主要历史，却未必覆盖全部人物心理、因果细节和隐含承诺。

第二，召回的扩展性尚需实测。 全候选补足可以提高潜在覆盖率，但可能导致模型筛选成本随作品规模增长。

第三，历史修订后的语义失效仍不完整。 索引可以重建，却无法自动判断旧记忆是否已经因为前文修改而失去文学事实依据。

因此，InkOS 当前更准确的定位是：

一套已经落地的混合式长期记忆检索系统，而不是完整的、可自动维护所有故事因果关系与版本有效性的文学记忆引擎。
