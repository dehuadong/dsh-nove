# InkOS 总体研究结论

> **研究类型**：独立第三方源码研究与机制归纳  
> **研究对象**：[InkOS（dehuadong/inkos）](https://github.com/dehuadong/inkos)  
> **固定研究基线**：`master` — [`8fc2ae57080b9821257dee3e37cc677e2b6f389a`](https://github.com/dehuadong/inkos/commit/8fc2ae57080b9821257dee3e37cc677e2b6f389a)  
> **整理日期**：2026-10-21  
> **版本**：研究总结 v1.0  
> **范围**：整合此前关于创作质量、Skill 与资源文档、作品权威、Agent 契约、长期记忆、审阅与历史修订、运行可靠性的多轮研究；**不涉及 Novel 的现状对拍、方案设计或实施决策**。

## 0. 执行摘要与总体结论

**核心判断：InkOS 值得借鉴的不是多 Agent、SQLite 或某一种具体数据格式，而是它把“文学内容方法、作品权威、相关信息召回、角色任务交接、可证据化审阅、状态结算与版本保存”组合成受控创作过程。**

从已检查的源码和测试看，InkOS 的特点是：

1. **创作内容和运行机制分离。** Skill / References 负责如何写，作品资料负责这本书是什么，Agent Schema 负责本次要交什么，Runtime 负责哪些结果允许成为作品权威。
2. **规划和事实分离。** Story Frame、Volume Map、Chapter Memo 是创作依据，但计划中的事件不等于已经发生；章节正文经 Settler 提取、Reducer 应用、Validator 检查后，才形成可持续使用的结构化状态。
3. **全量存储与有限上下文分离。** 权威状态长期保存；SQLite FTS5 只是可重建的索引；Composer 按当前任务选择、保护与压缩需要的内容，不要求模型始终记住整本小说。
4. **不同 Agent 使用不同的内容合同。** Architect 生成作品基础，Planner 生成章节 Memo，Writer 创作正文，Reviewer 提出有来源的观察，Reviser 按授权范围修改，Settler 结算事实，Validator 核对状态。
5. **版本和来源具有真实的工程约束。** Artifact Revision、Snapshot、Checksum、Episode、Work Lineage、ChapterTrace 使“哪份资料、哪次任务、哪个版本”在不同层次上可追踪。
6. **历史修订仍有重要的系统性边界。** 早期章节可以安全修订和以历史状态重新结算，但现有代码尚不能证明完整的下游因果重算、旧规划自动失效、历史上下文时间隔离和准确的受影响章节集合。

**成熟度判断**：InkOS 在单章生产、结构化状态与可验证交接上具有实质实现；在“跨数十至数百章的内容依赖传播与历史变更一致性”上仍以局部保护、提示及人工/模型审阅为主。此前研究以静态源码及既有测试审查为主，尚未执行独立的长篇规模、故障注入及文学质量对照实验；不能将源码风险直接宣称为已复现故障。

### 0.1 研究结论证据分级

| 等级 | 含义 | 本报告用法 |
|---|---|---|
| **A：源码及测试确认** | 可定位实现，既有测试验证对应局部行为 | “已实现”，但仅限被测范围 |
| **B：源码确认** | 可定位明确调用/结构，未确认完整端到端运行 | “有实现”“代码路径显示” |
| **C：源码可推导风险** | 两条真实路径组合显示风险，未建立固定样例复现 | “潜在风险”“一致性缺口” |
| **D：待验证/研究假设** | 缺少充分代码或实验依据 | “尚未证明”，不等于肯定不存在 |

## 1. 总体架构：七类机制构成的内容闭环

七层是本研究使用的分析分类，**不是 InkOS 官方的七层架构声明**。

```text
作者意图 / 当前任务 / 作品基础（内容权威）
                 │
     Skill 与 References（专业方法）
                 │
             Agent 编排
                 │
   Planner → ChapterMemo / threadRefs
                 │
  Composer → 来源召回 / ContextPackage
                 │
         Writer → 候选章节正文
                 │
      Reviewer ↔ Reviser（证据修订）
                 │
      Settler → StateDelta / Summary
                 │
     Reducer + Validator（状态约束）
                 │
  已采纳正文 / 状态快照 / Artifact 版本
                 │
    SQLite 检索投影与下次任务上下文
```

必须区分以下概念：

- **方法不是事实**：Skill 描述如何营造悬念，不代表某部作品已经存在该悬念。
- **规划不是事实**：Chapter Memo 安排未来行动，不代表角色已经做出行动。
- **摘要不是正文**：摘要用于检索和连续性，遇到争议仍需返回权威原文和正式状态。
- **索引不是权威**：SQLite 丢失可以重建；不能反向以索引覆盖故事状态。
- **来源被读取不是因果成立**：ChapterTrace 表明 Agent 见过资料，不能证明某情节依赖该资料。
- **已审阅不是已修复**：问题被记录、问题被消除、下游依赖完成复核，是不同状态。

## 2. L1：创作方法与内容质量

研究对象包括 [inkos-long-writing/SKILL.md](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/skills/inkos-long-writing/SKILL.md)、[reader-contract-and-progression.md](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/skills/inkos-long-writing/references/reader-contract-and-progression.md) 和 [scene-dialogue-and-length-budget.md](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/skills/inkos-long-writing/references/scene-dialogue-and-length-budget.md)。

### 2.1 读者承诺与剧情实质推进

InkOS 不把“没有事实冲突”等同于“写得好”。章节应建立或回应读者期待，并带来可观察的变化，例如行动结果、认知变化、关系变化、风险升级或新代价。反复重复“发现疑点—准备调查”，不构成有效推进。

### 2.2 伏笔的文学生命周期与机器状态

伏笔可以埋设、提及、推进、延后、兑现和被作者正式撤销。其中 **mention 不等于 advancement**。结构化 Hook 有 `open`、`progressing`、`deferred`、`resolved`、`superseded` 等状态；状态词不能替代正文层面的阅读效果判断。撤销既有承诺与否认已发生事件必须区分。

### 2.3 场景功能、对话与字数容量

场景需要目标、阻碍、行动、变化和后果；对话应承担冲突、信息、角色关系或选择功能。篇幅先由场景的情节承载量支持，再由运行时检查字数，而非写短后以环境、心理或重复谈话填充。

### 2.4 人物发展与长期节奏

人物欲望、知识、能力、关系压力和代价约束其行动。真正的长篇质量还取决于跨章节的冲突变化、情绪曲线与读者承诺兑现。InkOS 已提供专业指导和部分结构化摘要字段（如 `mood`、`chapterType`），但 **不存在仅凭这两个字段就自动判定人物成长与全书节奏质量的证据**。

### 2.5 非正式剧情预演

`forecast` 体系可以生成不同剧情发展方向并保存候选，供作者比较；预演成果不等于正式作品状态。相关入口：[forecast/runner.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/forecast/runner.ts)。

**L1 结论**：创作方法的优势在于围绕“发生变化的故事”组织专业指导；主要验证缺口是：Skill 被加载并不能自动证明作品质量提高。需要真实作品样本、盲审或预先定义的叙事质量评价。

## 3. L2：Skill、References 与专业资源加载

主要证据：[builtin-profiles.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/harness/builtin-profiles.ts)、[skill-tool.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/agent/skill-tool.ts)。

### 3.1 Work Profile、Skill 与任务方法

Work Profile 声明适合某种作品类型的能力、推荐 Skill 和产物类型；Skill 主文件放主要原则；References 按文学任务细分长文内容。小说作品拥有自己的 Story Frame、Book Rules、人物卡与状态，**不能与 Skill 的通用写作范式混放**。

### 3.2 三种 Skill 获取方式

1. 按 `skillId` 启用 Skill 及显式关联资源。
2. 按 `resourcePath` 读取指定资源文档。
3. 按 `query` 检索相关 References 片段，返回文件、标题、片段和位置信息。

References 有分块与检索实现，因此不是必须一次将所有文档加入 Prompt。但通过主文档显式关联的资料仍可能增加初始上下文开销。“支持按需加载”不等于“任意调用的 Token 成本一定很低”。

### 3.3 Skill 的内容角色

| 内容类型 | 应解决的问题 | 典型资源 |
|---|---|---|
| 创作方法 | 怎样构思、推进、控制节奏 | Foundation、Reader Contract、Scene Budget |
| 评价标准 | 怎么判定正文存在何种问题 | Review Matrix |
| 状态提取方法 | 怎样从正文识别事实、Hook 和摘要 | State Projection |
| 执行合同 | 哪些对象可被谁编辑和提交 | Runtime Schema / Tool Contract，**不应由文学指南代替** |

**L2 结论**：InkOS 的重点不是 Skill 数量，而是**方法资源按任务调用、与作品事实和工具授权解耦**。需要进一步实测不同 Skill 的实际加载范围和创作质量影响。

## 4. L3：作品内容模型、权威和版本

核心文件：[architect.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/agents/architect.ts)、[runtime-state.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/models/runtime-state.ts)、[artifact-revisions.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/harness/artifact-revisions.ts)。

### 4.1 作品内容不是一份全能文档

| 领域 | 主要内容 | 权威/用途 |
|---|---|---|
| 长期方向 | `author_intent.md`、`current_focus.md` | 用户方向与近期任务约束 |
| 故事基础 | `story_frame.md`、`volume_map.md` | 框架、冲突、全书与卷章规划 |
| 作品规则 | `book_rules.md`、`book_rules.json` | 可读规范与机器可校验约束 |
| 角色资料 | 角色索引和分人物 Markdown 卡片 | 动机、知识、关系、能力边界 |
| 正文 | 章节原文、章节索引 | 事件依据；修订需保留版本 |
| 正式运行状态 | `state/current_state.json`、`hooks.json`、`chapter_summaries.json`、`manifest.json` | 当前事实、伏笔和摘要的结构化权威 |
| 派生视图 | `current_state.md`、`pending_hooks.md`、`chapter_summaries.md` | 人类可读投影，不反向覆盖 JSON |
| 章节执行 | `ChapterMemo`、`ContextPackage`、`ChapterTrace` | 本次任务和来源证据，不是故事既成事实 |

Architect 采用分阶段生成：故事框架/卷章方向 → 作品规则及初始 Hook → 角色索引 → 分人物卡片。后阶段继承前阶段材料，避免将所有复杂作品资料交给一次巨大的结构化输出。

### 4.2 两种权威必须区分

- **作者决策权威**：决定允许怎样创作、结局边界和当前指令；作者可正式修订它。
- **已发生事实权威**：记录章节中真正发生的事件；旧计划被撤销不能自动抹除已发生的情节。

新创作方向可以让尚未兑现的伏笔 `superseded`；但已兑现的历史不能简单以撤销计划的方式删除。

### 4.3 Artifact Version、Work Lineage 与章节状态

Artifact 的 `revisionId`、`parentRevisionId`、`checksum`、`snapshotPath` 能保存和验证历史字节；跨 Work 衍生可固定 `sourceWorkId`、`sourceArtifactId`、`sourceRevisionId`，防止原作品变化后衍生任务悄悄改用另一个母本版本。相关测试：[derived-source.flow.test.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/__tests__/derived-source.flow.test.ts)。

局限在于：**“一个 Artifact 有版本”不等于“所有消费它的 Memo、Context 和下游章节都绑定该版本”。**

**L3 结论**：InkOS 已建立多种内容权威与版本类型，但跨文件语义权威冲突、来源版本绑定及跨章节失效传播尚未统一闭环。

## 5. L4：Agent 编排、结构化契约与交接

相关入口：[planner-tool.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/agents/planner-tool.ts)、[writer.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/agents/writer.ts)、[review-tool.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/agents/review-tool.ts)、[settler-tool.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/agents/settler-tool.ts)。

| 角色/模块 | 主要输入 | 输出或动作 | 不应混淆的权威边界 |
|---|---|---|---|
| Architect | 创意、作者目标、现有作品基础 | Story Frame、Book Rules、Volume Map、角色资料 | 设定建议不等于已发生事实 |
| Planner | 当前目标、规则、历史记忆与伏笔 | `goal`、`body`、`threadRefs` 的 Chapter Memo | 规划不等于正文 |
| Composer | Memo、结构化状态、人物卡、摘要、外部参考 | ContextPackage、ChapterTrace | 选中来源不代表已验证因果 |
| Writer | Memo、上下文、规则、专业方法 | 章节正文候选 | 不能凭正文候选直接宣布状态权威 |
| Reviewer / Auditor | 正文、审阅标准、任务上下文、前后版本 | 分类 Observation、引用证据 | 观察不等于自动修改 |
| Reviser | 原文、授权范围、Review、相关事实 | 局部修订或重构正文 | 不能擅自修改范围外正确内容 |
| Settler | 最终正文、旧状态、现有 Hook | factOps、hookOps、章节摘要 | 提取到的变化仍需校验 |
| Reducer / Validator | 旧状态、Delta、正文与权威规则 | 状态投影、冲突/对账结果 | Schema 正确不保证提取完整 |

### 5.1 为什么 Planner 与 Writer 分别需要上下文选择

Planner 的任务是确定“本章写什么”，Composer 在 Chapter Memo 出现之后还能按新的 Hook ID、场景目标等线索重新召回“写这章必须知道什么”。两次上下文准备并不完全相同；`threadRefs` 用于明确 Hook 引用，其他历史通过检索补充。

### 5.2 合理的结构化程度并不相同

Chapter Memo 仅有 `goal`、`body`、`threadRefs`，文学场景安排留在可读 Markdown；Settler 则使用较强结构化的 Fact/Hook 操作，因为它们直接改变权威状态。**结构化应服务于可验证的领域操作，而不是要求所有文学内容都被拆成复杂 JSON。**

### 5.3 审阅结果要求证据

Observation 可区分 `quality`、`execution`、`scope`，以及 `issue`、`resolved`、`unavailable`、`observation`。原文来源可通过宿主校验，保证引用的片段确实存在。局部修订支持选取行范围，保护未授权的原文范围。测试：[chapter-review-scope.flow.test.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/__tests__/chapter-review-scope.flow.test.ts)。

**L4 结论**：不同角色对应不同内容输入和结构化合同，是已落地的核心强项；但是合同验证、方法是否真正生效、叙事是否正确仍是不同层次的问题。

## 6. L5：长期记忆、数据库索引和上下文管理

代码依据：[local-search.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/retrieval/local-search.ts)、[memory-retrieval.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/utils/memory-retrieval.ts)、[composer.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/agents/composer.ts)、[context-compiler.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/harness/context-compiler.ts)。

### 6.1 记忆至少有五种，不应统称“向量知识库”

| 记忆类型 | 示例 | 合理的权威与查询方式 |
|---|---|---|
| 创作合同 | 作者禁区、人称、结局约束 | 直接加载、受保护 |
| 当前世界状态 | 人物位置、关系、身份认知 | 结构化当前态和有效区间 |
| 历史事件 | 曾发生的交易、秘密传递、矛盾冲突 | 章节摘要、事件原文与来源定位 |
| 叙事承诺 | 未回收伏笔、谜团、读者期待 | Hook 状态与稳定 ID |
| 执行过程 | 哪次 Agent 读取了什么、失败在哪里 | Trace、Episode 和任务证据 |

### 6.2 已实现的检索路径

```text
结构化章节摘要 / 未解决 Hook / 卷摘要
                    ↓
       可重建 SQLite FTS5 索引
         中文分词 / BM25 排序
                    ↓
        搜索命中 + 其他候选
                    ↓
          按任务语义选择
                    ↓
          精确 Hook ID 补齐
                    ↓
    Protected / Compressible 分类
                    ↓
    Token 预算检查与必要时压缩
                    ↓
       ContextPackage + Trace
                    ↓
          Planner / Writer
```

`LocalSearchIndex` 采用 SQLite FTS5 与 BM25；本次所检查的故事记忆链并未发现其依赖独立向量数据库或 Embedding 索引。**语义选择器是使用模型从候选中筛选，不等于底层向量检索。**

FTS5 是可重建的派生索引，`replaceScope` 在召回前依据权威摘要和 Hook 更新搜索集合；数据库存取不能替代状态结算。

### 6.3 上下文预算与保真

Composer 检查完整工作集能否符合预算：符合时可直接加载而避免额外语义选择；不符合时再选取并压缩。`protected` 表示被选中后不能任意语义压缩，`compressible` 可被提炼；受保护资料本身超限应报错，不可静默截断。

必须区分：**某资料被选为 Protected，不等于所有必要资料都会被选中。** 人物卡片、当前事实和部分章节摘要依然可能因候选选择遗漏而缺席。

### 6.4 两类主要记忆风险

1. **时间边界**：面向历史章节的最终摘要集合会过滤未来章节，但候选筛选阶段仍可能接触全量摘要；当前事实选择又读取最新状态，存在历史任务见到未来知识的风险。
2. **版本边界**：ContextPackage 主要保存来源路径、原因、摘录和保护类型，ChapterTrace 保存选中来源与检索过程，但 Schema 没有要求每个来源绑定 Artifact Revision、内容哈希与相应的历史状态版本。

**L5 结论**：InkOS 有实质的可重建检索、精确与语义结合、预算保护和可追溯上下文，但召回充分性、来源版本一致性和历史时间隔离尚需要专门验证。

## 7. L6：审阅、历史修订与内容依赖一致性

主要证据：[pipeline/runner.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/pipeline/runner.ts)、[runtime-state-store.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/state/runtime-state-store.ts)、[state-reducer.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/state/state-reducer.ts)。

### 7.1 已有的历史修订保护

以第 120 章已经写完、作者修改第 30 章为例，`reviseDraft()` 会读取第 29 章状态快照来结算新版第 30 章；对非最新章节，正式保存目标正文与章节索引，不直接用第 30 章状态覆盖第 120 章当前状态；并对下游章节写入 `upstream-revision` 连续性观察。旧正文可以归档以供审阅比较。

这一边界是正确的：**修订旧章节不能直接把“当前事实”倒退到旧时间点。**

### 7.2 未完成的是“下游恢复”，不是“保存修订”

第 30 章正文已经改动，不代表第 31～120 章的人物动机、伏笔推进、摘要和当前事实已重新对账。当前版本存在“新正文 + 旧后续状态/旧摘要”短暂或持续并存的可能。重新构建 SQLite 只会检索现有结构化摘要，不会自动理解新正文并修正摘要。

而 `resyncChapterStateAndAudit()` 当前只允许同步最新章节，不能直接用于任意旧章节的连锁重放。

### 7.3 几个由源码定位的具体边界

| 编号 | 发现 | 依据 | 定性 |
|---|---|---|---|
| R1 | 第 30 章修订的 Settler 使用第 29 章快照，但 Reviser 经 Composer 可读取第 120 章最新事实 | `runner.reviseDraft()` + `composer.selectTaskContext()` | **源码可推导的时间隔离风险** |
| R2 | `ChapterMemo` 可以复用，但缓存只保存 `plannerInputs` 路径，缺少上游完整 Revision 绑定 | `persisted-governed-plan.ts` + `resolveGovernedPlan()` | **陈旧规划复用风险** |
| R3 | 非最新章节修订仅保存正文及索引；下游状态、结构化摘要没有在该分支连锁重算 | `runner.reviseDraft()` | **下游一致性未闭环** |
| R4 | 后续章节的 `upstream-revision` 可被普通 `reviewChapter()` 用新的 Observations 数组覆盖 | `runner.reviseDraft()` + `reviewChapter()` | **未完成风险可能丢失的代码路径** |
| R5 | Hook 已有可选 `dependsOn`、`paysOffInArc`，但 Reducer 合并、Validator 校验、投影与检索未形成依赖传播链 | `runtime-state.ts` + `state-reducer.ts` + `state-validator.ts` | **部分数据模型、缺乏依赖治理** |
| R6 | Memo 引用找不到的 Hook 在 Composer 的特定读取路径中被跳过 | `composer.buildReferencedHookEntries()` | **召回完整性风险** |
| R7 | ContextSource/Trace 不强制绑定精确来源 Revision 与状态快照 | `input-governance.ts` | **历史来源精确重现未证明** |
| R8 | Validator 对相同新旧状态存在快速路径；单凭无 Delta 不能证明正文没有漏提取事实 | `agents/state-validator.ts` | **状态提取完整性仍需外部证据** |

上述“风险”不是已运行并复现的缺陷报告。R1、R3、R4、R5 有明确的多文件调用或字段证据；产生实际错误的条件、频率与严重程度需要固定案例实验。

### 7.4 叙事依赖不是普通文本关联

InkOS 有四类可用于分析的线索：

- **事实时序**：`subject`、`predicate`、`object`、`validFromChapter`、`validUntilChapter`、`sourceChapter`；可以识别部分状态变更，但缺少稳定 `factId`、实体 ID 和显式 `causedBy`。
- **Hook 关系**：稳定 `hookId`，还有可选 `dependsOn`；但后者缺少依赖有效性检查、循环校验和可靠的更新传播。
- **章节摘要**：`events`、`stateChanges`、`hookActivity` 等自由文本可提供因果候选；不是机器确认的因果边。
- **使用来源**：`ChapterTrace.selectedSources` 说明当时选择过某资料，但**读过某来源 ≠ 某情节依赖该来源**。

因此，候选影响集合可以从结构化事实、Hook、Summary 和 Trace 缩小；但当前不能证明可精准且无遗漏地识别真正的下游因果关系。简单将所有命中关键词的章节视为“必然受影响”，会同时产生误报和漏报。

**L6 结论**：单章修订版本控制、范围保护与历史基线已做出相当多的工程工作；真正未闭环的是**上游事实改变之后，如何确定、审查、修复并证明所有下游情节仍然成立**。

## 8. L7：长时间运行、执行证据与验收

代表实现：[episode-store.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/harness/episode-store.ts)、[session-transcript-restore.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/interaction/session-transcript-restore.ts)、[atomic-file-set.ts](https://github.com/dehuadong/inkos/blob/8fc2ae57080b9821257dee3e37cc677e2b6f389a/packages/core/src/utils/atomic-file-set.ts)。

InkOS 对 Episode、执行事件、会话恢复、事务性保存和执行证据有独立处理。有效的阶段性提交可以避免把整个连续创作批次视为不可分割的一次巨型任务。Audit 与 Artifact 历史比较能够核查哪些内容发生改变。

但要区分：

- **会话可恢复**，不代表中断时的外部模型调用可以无损重演；
- **事务保存原子性**，不代表跨章节的叙事关系已自动恢复一致；
- **CI 测试通过**，不代表在真实外部宿主上连续写几十章的文学质量、性能和错误恢复均通过。

**L7 结论**：已有可靠性建设，但尚需长篇规模压力、索引失效、宿主中断、重复任务恢复和质量对照的独立实验。

## 10. 研究中最有价值的十项机制性认识

1. **长篇创作首先是内容权威治理问题，不是“提示词越长越好”。**
2. **文学指导和机器合同应分别组织**：能表达复杂审美的方法保留自然语言，影响持久化状态的操作须结构化。
3. **同一章可以产生不同的 Agent 上下文**：Planner 决定任务，Composer 为 Writer 重新建立工作集。
4. **事实、摘要、伏笔和阅读期待各有身份**：它们不能靠一个统一的全文检索结果互相替代。
5. **检索系统的质量依赖于上游内容是否正确**：错误摘要被高效索引，仍然是错误记忆。
6. **`Protected` 保护的是已选资料，不是召回完整性的证明。**
7. **版本记录和依赖传播是不同能力**：知道旧文件版本，不等于知道哪些后续章节依赖旧版。
8. **历史修订需要时间隔离**：修订者与结算者必须使用兼容的历史基线，否则未来状态可能泄漏到早期章节。
9. **审阅观察必须有生命周期**：刷新评论不能默认消除尚未完成的上游影响审查。
10. **创作质量证据不能只来自工具成功**：Schema 合法、CLI 成功、CI PASS 与文学叙事质量必须分别评价。

## 11. 未闭环机制与优先验证问题

优先级是**研究验证优先级**，不是其他项目的实施排序。

| 优先级 | 问题 | 判定依据 | 推荐验证方式 |
|---|---|---|---|
| P0 | 历史修订 Reviser 使用未来信息 | 最新 CurrentState 与历史 Settler 基线不同 | 第 120 章回修第 30 章的固定 Mock |
| P0 | 历史改动后下游仍保留旧状态与摘要 | 非最新修订保存路径不重放后续状态 | 删去第 30 章关键事实后读取第 120 章状态 |
| P0 | `upstream-revision` 可能被普通 Review 覆盖 | Review 替换 Observations | 增标记后普通审阅并核实标记是否仍有效 |
| P0 | 旧 Memo 复用未校验上游 Revision | 缓存 Schema 与加载入口 | 修改 Story Frame 再复用 Memo |
| P1 | 必要 Hook / 人物事实未召回 | 来源选择和丢失 Hook 的读取路径 | 未知 Hook、别名与隐含因果样本 |
| P1 | Hook `dependsOn` 缺少验证与传播 | Schema、Reducer、Validator、Projection | 写入依赖、更新依赖、循环依赖测试 |
| P1 | 来源与 ContextPackage 缺少强版本绑定 | ContextSource 与 Trace Schema | 角色卡变更后恢复旧任务 |
| P1 | 状态验证可能漏掉未提取的事实 | 相同新旧状态快速路径 | 正文发生新事件、Settler 返回空 Delta |
| P2 | SQLite 检索在长篇规模的性能成本 | FTS5、语义选择候选集合 | 50/200/500/1000 章性能基准 |
| P2 | 创作指南对文学效果的真实作用 | 有 Skill 方法，暂无对照质量证据 | 真实章节质量评分与一致性评测 |

### 11.1 推荐的完整跨章节测试样例

统一使用一部含 120 章摘要、若干 Hook、人物知识变化与关系变化的固定测试故事。

1. 第 12 章取得密信；第 30 章发现姓名；第 65 章基于该姓名作出选择；第 95 章得知真实身份；第 120 章已公开事实。
2. 修订第 30 章，删除“发现姓名”事件，同时保持第 65、95、120 章初始内容不变。
3. 检查修订 Agent 是否见到第 95 章才成立的事实。
4. 核对第 30 章结算差异、章节摘要、Hook、现有 FTS5 文档和旧 Memo。
5. 检查第 65、95、120 章的影响标记能否保留、被明确解除以及何时允许继续写第 121 章。
6. 注入一次修订提交与索引刷新间的中断，验证恢复后是否误认任务完成。
7. 将候选章节和真实受影响章节作比对，记录误报、漏报和 Token 费用。

**本研究没有声称已完成以上新增实验。** 这些步骤是为了把当前的源码证据推进为可复现的行为证据。

## 12. 最终综合评价

### 12.1 确认的优势

InkOS 的强项是：**按作品内容职责分层、Skill 资源检索、结构化章节任务、受控上下文加载、证据化审阅、状态机结算、版本保存和运行恢复**。这些能力不是单纯在文档中承诺，而是已有具体代码及一定范围的既有测试。

### 12.2 已确定的能力边界

最显著的边界在于：**内容来源有记录，但没有形成完整的语义因果依赖网络；历史章节修订后的叙事当前态、摘要、Memo 与下游章节不能自动证明全部一致。** 对于隐含人物动机、秘密认知、关系因果，检索匹配与 Hook ID 也无法单独提供可靠结论。

### 12.3 不能从本次研究推出的结论

本次未做独立长篇生成、中文大规模召回基准和系统故障注入，因而不能据此断言：

- InkOS 在真实数百万字作品中始终不会遗漏记忆；
- 当前识别的所有潜在风险都已产生用户可见错误；
- 任一所研究的技术选择（如 FTS5、Agent 数量或分层数）天然优于所有替代方案；
- InkOS 的工作流已经能自动完成全部下游因果恢复。

### 12.4 一句话总论

> **InkOS 已将长篇创作由“依赖单次模型提示词的文本生成”推进为“有专业方法、有内容权威、有结构化交接、有可追溯记忆与版本证据的受控创作流程”；但其下一步最值得验证的能力不是更多数据字段或 Agent，而是“作品历史被改写以后，系统能否准确识别、处理并证明下游内容仍然成立”。**
