## 五、实际调用链：Composer 如何决定加载哪些记忆？

进一步查看 [composer.ts](https://github.com/dehuadong/inkos/blob/master/packages/core/src/agents/composer.ts)，可以确认：长期记忆不是一个可选的搜索命令，而是被接入了章节创作上下文的准备过程。

这里还有两个非常关键的设计。

### 1. 上下文装得下时，不必调用模型筛选

InkOS 会先计算完整资料工作集的大小。如果完整资料可以放进分配给上下文的预算，就直接使用完整资料，不额外调用语义选择器。

如果放不下，才启动选择和压缩。

其逻辑可以简化为：

读取本章任务与可用记忆

完整资料是否符合上下文预算？

符合

直接使用完整工作集

无需额外语义选择

超出

检索、筛选、必要时压缩

控制上下文体积

源码中的完整上下文判定，会将可用上下文扣除预留输出 Token 后，大约一半留给资料工作集，另一半预留给指令、正文和协议。这是 InkOS 当前的分配策略，不是通用的最佳比例。

它体现了一个实用原则：检索是降低上下文成本的手段，不必在任何情况下强制执行昂贵的语义筛选。

### 2. 显式引用的伏笔，不依赖搜索排名

这点尤其值得注意。

InkOS 的章节备忘支持 `threadRefs`，即直接指定本章涉及的伏笔 ID。

Composer 会根据这些 ID，找到伏笔最初埋设的章节、最近一次实质推进的章节，以及预期回收内容，并把结果作为受保护上下文提供。

这是一种精确检索与语义检索相结合的策略：

- 作者或 Planner 已明确指定伏笔 ID，就按 ID 查找。
- 没有明确引用，但可能有关联的历史内容，通过 FTS5 和语义筛选召回。
- 作者认可的约束、明确引用的伏笔等关键资料，不受普通搜索排名控制。

因此，长期记忆不能只依赖向量相似度或全文搜索排名。

有些信息是必须加载的依赖，而不是“可能相关”的背景知识。

## 六、完整链路中的一致性与失效问题

这部分值得单独研究，因为“搜得到历史资料”和“召回正确版本的历史资料”并不相同。

| 问题     | InkOS 现有机制            | 仍需关注的边界                 |
| ------ | --------------------- | ----------------------- |
| 内容更新   | 按文档 ID 与内容哈希更新 FTS 索引 | 索引与领域状态的提交时间可能不同        |
| 内容删除   | `replaceScope` 清理旧索引项 | 查询期间数据发生变化的并发一致性        |
| 伏笔回收   | 已解决和已撤销的伏笔不进入待解伏笔候选   | 其历史记录仍可能是当前剧情的必要因果依据    |
| 来源定位   | 章节编号、伏笔 ID、资料路径及字符区间  | 原始文件修改后，旧位置可能失效         |
| 资料压缩   | 保留重要 ID、约束与来源指针       | 压缩内容是否忠实，需要独立核查         |
| 历史章节修订 | 领域状态可以重新计算            | 下游摘要、检索索引和已生成上下文也需要联动失效 |

尤其要注意：当前 `memory-retrieval.ts` 在检索前会调用 `replaceScope` 更新故事记忆索引。这能降低陈旧索引风险，但也可能导致每次召回都需要重新整理一批资料。

它尚不能单独证明在数百万字作品中具备最优的增量索引性能，也不能证明并发修订与检索始终得到同一个一致快照。

这些应该通过基准和故障注入测试验证，而不是只根据“使用 SQLite”得出性能结论。

## 七、长期记忆还需要区分五种不同的记忆

经过这次源码追踪，我认为这是理解整套系统时最容易忽略的问题。

“长期记忆”不是一种单一数据结构。不同记忆有不同的权威性、有效期和召回方式。

| 记忆类型   | 举例                        | 最适合的处理方式            |
| ------ | ------------------------- | ------------------- |
| 创作合同记忆 | 作者确定的主线、结局边界、禁区           | 权威数据，按任务强制加载        |
| 世界状态记忆 | 人物当前位置、关系、拥有物品、已知秘密       | 结构化查询，使用当前有效状态      |
| 情节事件记忆 | 第 12 章发生的交易、第 68 章的背叛     | 章节摘要、事件索引及来源追溯      |
| 叙事承诺记忆 | 尚未回收的伏笔、重要悬念、读者期待         | 状态跟踪、明确 ID 引用、相关性召回 |
| 过程记忆   | Agent 执行了什么、哪里失败、哪些修改已获批准 | Episode、任务凭证、执行事件   |

其中，InkOS 对创作合同、结构化状态、章节摘要、伏笔以及执行轨迹都有相应机制，但这并不意味着上述五类已经完全统一为一个记忆模型。

还需要区分当前真实状态与历史状态。

例如，第 20 章两人互相信任，第 70 章关系破裂，第 100 章需要回忆第 20 章的事件。查询“当前关系”应返回破裂状态，查询“第 20 章关系”则应返回当时的信任状态。

只使用最新状态，会丢失历史语境；只使用历史检索，又可能错误地把旧关系当作当前事实。

这就是为什么长期创作需要同时保留事件历史与当前投影。

## 八、从机制角度，还值得深入的四项能力

### 1. 时间与有效区间检索

搜索“男主什么时候得知真相”，不应只找到包含“真相”两个字的章节，而应该识别知识状态发生变化的节点。

值得研究的字段有事件章节、事实生效章节、失效章节、信息来源及人物知识主体。

这属于时态知识检索，比普通全文检索更精细。目前不能认定 InkOS 已完整实现这一层。

### 2. 实体别名、身份与关系检索

同一个人物可能具有姓名、称号、假名和隐藏身份。

如果搜索只以名字为关键词，就可能遗漏某个化名时期的关键事件。

一种值得研究的方式是让人物具有稳定实体 ID，名称和别名只是该实体的不同属性；检索时先解析实体，再查询相关事实和文本。

但隐藏身份本身也可能属于剧情秘密，因此必须区分“系统内部识别为同一实体”与“当前角色或读者是否已经知道”。

### 3. 依赖关系召回

假设 Planner 正在安排第 110 章回收某条伏笔。

比起召回所有带有该关键词的内容，更重要的是找到：

- 最初埋设事件；
- 已发生的实质推进；
- 相关人物已经知道什么；
- 当前尚未解决的因果约束；
- 作者是否修改过这条伏笔的原定方向。

这是沿故事依赖关系检索，与按文本相似度召回不同。

InkOS 的 `threadRefs` 已体现这种思想，但更完整的事件依赖图和影响传播能力，还需要进一步核对。

### 4. 召回质量评估

长期记忆机制是否有效，不能只看查询耗时。

假设当前章节有五条必须使用的历史事实：

- 召回了其中四条，召回率为 80%；
- 召回了十条信息，其中六条与本章无关，则还存在大量上下文噪声；
- 如果把已经失效的旧事实当成当前事实，即使相关性很高，结果仍然错误。

因此至少要评估以下指标：

| 指标      | 判断标准               |
| ------- | ------------------ |
| 关键事实召回率 | 必需历史事实是否被找回        |
| 版本正确性   | 是否使用当前有效的资料版本      |
| 精确来源率   | 是否能定位到原始章节或权威记录    |
| 约束保留率   | 作者硬性要求是否完整进入上下文    |
| 上下文效率   | 有效信息占用了多少 Token    |
| 检索延迟    | 章节增加后查询是否明显变慢      |
| 误用旧事实率  | 是否错误引用已失效的关系、知识或设定 |

这类评测应使用固定的长篇样本，而不是仅测试能否搜索到某个关键字。

## 九、值得采用的研究模型

### 长期记忆完整链路

L1 · 权威存储层

创作合同 · 事件 · 当前事实 · 伏笔 · 章节正文

L2 · 索引层

实体索引 · 章节索引 · FTS5 · 来源版本 · 关系索引

L3 · 检索规划层

精确查询 · 全文召回 · 时间过滤 · 依赖展开

L4 · 相关性与权威校验层

语义筛选 · 版本核对 · 冲突识别 · 来源验证

L5 · 上下文编译层

强制约束 · 任务相关事实 · Token 预算 · 有损压缩

L6 · Agent 执行和记忆更新

创作 · 审阅 · 状态结算 · 索引失效与重建

这里的 L1–L6 是我根据源码提炼的分析模型，不是 InkOS 原仓库声明的六层架构。

其中，InkOS 已有比较明确的 L1、L2、L4、L5 和 L6 实现。L3 中的时间过滤、别名解析和复杂依赖展开，则属于还需要进一步确认或者研究的方向。

## 十、接下来最值得做的深入实验

仅看代码已经能理解主要设计，但如果要判断这些机制的真实性能和可靠性，建议安排四组对照实验。

实验 A：中文检索准确性。 构造姓名、化名、短中文词、隐含因果和同义表达，比较 FTS5 与语义筛选的召回结果，分析漏召回率。

实验 B：长篇规模压力。 分别模拟 50、200、500、1000 章的摘要、伏笔和事件规模，记录索引构建耗时、查询延迟、候选量、模型筛选 Token 与成本。

实验 C：历史修订一致性。 修改前期章节的已定稿事实，检查当前状态、摘要、索引、来源位置、上下文是否同时失效或更新。

实验 D：上下文保真。 给语义编译器包含大量人物和关系的历史资料，检查是否错误合并人物、丢失因果、改变知识边界，或省略作者硬性要求。

这四组实验能回答比“要不要使用 SQLite / 向量数据库”更重要的问题：这个长期记忆系统是否真的让长篇写作更准确、更稳定，而且成本可控？

## 阶段性结论

根据 InkOS 当前的代码，已经可以明确：

- 它使用 SQLite FTS5 作为可重建的词法检索索引，而不是把搜索数据库直接当作故事权威。
- 它结合任务目标、语义选择、明确伏笔 ID 和上下文预算决定资料使用范围。
- 它区分受保护的创作约束与可压缩的历史上下文。
- 它能记录检索与上下文选择轨迹，但仍需要实测证明大规模召回质量和一致性。
- 对于别名、人物知识时间线、事件依赖图和历史修订后的跨层失效，仍有继续研究的空间。

最重要的认识是：长期记忆的目标不是“尽量把过去的内容都送给模型”，而是“在正确的时间，把正确版本、正确来源、对当前任务真正必要的信息交给 Agent”。
