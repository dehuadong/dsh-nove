# Agent Note: F13 250 章性能预算

Status: implemented

工作项：`#87`。

## Problem

`store-perf.test.mjs` 已经覆盖 200 章：`readManifest < 100ms`、批量追加 `< 5000ms`、单章追加 `< 50ms`、检索与 `assembleBrief < 400ms`（预算归 sqlite-store Note 与检索 Note）。但 F13 还缺：

- 目标规模是 **250 章**，现有夹具只到 200；
- 没有 `listWorks` 的多作品 N+1、`readWork` 章节目录、`status` 聚合、`exportWorkAtomic` 的测量；
- 没有内存上限证据；
- 夹具只在测试文件里，不能复用。

所以问题不是“仓库没有性能证据”，而是“证据没覆盖目标规模与真实消费者”。

## Decision

### 共享夹具

新增 `tests/perf-fixture.mjs`，只用公开 storage 动作生成：

- 1 个 250 章作品：每章章纲、批准、正文、摘要、审稿（包含 observation 的章节与清稿章节）、2 条状态事件；前 20 章 settle，覆盖已定稿路径；
- 20 个 10 章作品，覆盖 `listWorks` 的 N+1；
- 返回 `{ root, work, smallWorks, chapters, bulkAppendMs }`，结束后由调用方删除临时目录。

`store-perf.test.mjs` 与任何报告脚本共用此夹具，避免三套生成器漂移。

### 测量

在 250 章作品上，读操作 warm 一次后跑 3 次取中位数；批量追加沿用现有单次测量（生成成本高），单章追加取 3 次最小值，内存子进程跑 3 次取 maxRSS 中位数：

| 操作 | 预算 | 依据 |
| --- | --- | --- |
| `readManifest` | < 100ms | 沿用现有 200 章预算，不放松 |
| `readWork`（章节目录） | < 150ms | manifest + workbench 投影；比 manifest 多一层，仍给余量 |
| `status` | < 300ms | 250 章审稿/伏笔/摘要聚合 |
| `assembleBrief`（第 250 章） | < 400ms | 沿用现有预算 |
| `exportWorkAtomic`（250 章） | < 3000ms | 原子导出含 staging/swap；清空目标在计时外 |
| `listWorks`（21 部作品） | < 500ms | 21 次 open + 聚合；暴露 N+1 失控，仍留机器余量 |
| 单章追加（第 251 章） | < 50ms | 沿用现有预算 |
| 批量追加 250 章 | < 5000ms | 沿用现有预算 |
| 独立子进程读取 250 章后的 `maxRSS` | ≤ 256MB | 子进程从冷启动开始读取；避免父进程生成夹具的峰值污染 |

预算不是产品限制，是工程回归线；现有更严的预算（100/400/400/50/5000）一律保留，不因新表放松。

### 证据入口

扩展 `tests/store-perf.test.mjs`，CI 已有的单测循环自动运行，不新增独立命令；失败信息打印操作、实测、预算。若需要单独报告，可加 `scripts/bench-250.mjs` 薄包装，但夹具与断言仍只有一份。

`exportWorkAtomic` 的目标目录在每次采样前清空（计时外），避免把删除上一次导出的时间算进去。

## 对拍参考

- `inkos-master/CHANGELOG.en.md:354`：会话列表性能改为“并发读取 + 轻量摘要”，避免 sidebar 载入大量完整会话；对应我们的 `listWorks` N+1。
- 参考工程没有 250 章基准脚本或预算表；本项按我们的 SQLite 读路径定义，不复制其运行时。

参考工程的 SQLite（retrieval/local-search.ts:24-28）是**可重建的 FTS 投影**，正文/状态仍以文件为权威；我们的 SQLite 是**权威存储**，检索只是同库内的投影。两者读路径不同，F13 的预算只测我们的存储读路径，不能套用参考的 retrieval-only 数字。

| 参考做法 | 我们的做法 | 原因 | 裁决 | 验证 |
| --- | --- | --- | --- | --- |
| 列表返回轻量摘要、避免载入完整会话 | 先测 `listWorks` N+1；超预算再批量/轻量查询 | 当前只取计数，未载入正文；先量化 | 等价适配 | store-perf |
| 无 250 基准 | 扩展现有 200 章测试到 250 + 真实消费者 | 目标规模必须有证据 | 采纳 | store-perf |
| 无内存证据 | 独立子进程 `maxRSS` 上限 | 检测整库读入，避免父进程峰值污染 | 采纳 | store-perf |
| 单独基准脚本 | 共享夹具 + 扩展现有测试 | 避免生成器漂移、不增 CI 入口 | 采纳 | 夹具复用 |

## Alternatives considered

**A. 新建 `bench-250.mjs`，与现有 200 章测试并存。** 最强的理由是报告可独立运行、不拖慢单测。否决原因：两套夹具会漂移，CI 已有测试入口；共享夹具 + 扩展测试更省维护。若需要独立报告，只做薄包装。

**B. 只把 200 改成 250，不加消费者与内存。** 最强的理由是最小改动。否决原因：F13 明确要作品列表、章节目录、写前装配与内存；只改数字不覆盖。

**C. 用 100 章代替 250。** 最强的理由是快。否决原因：目标规模是 250，不能用更小规模证明。

**D. 先优化 `listWorks` 的 N+1。** 最强的理由是提前消除热点。否决原因：当前只取计数，先测；超预算再改，避免扩大范围。

## Testing

`store-perf.test.mjs` 与 `tests/perf-fixture.mjs` 在 250 章 + 20×10 夹具上运行；本机一次结果：

| 操作 | 实测 | 预算 |
| --- | --- | --- |
| `readManifest` | 2.5ms | <100ms |
| `readWork` | 16.0ms | <150ms |
| `status` | 5.3ms | <300ms |
| `listWorks`（21 部） | 18.4ms | <500ms |
| `assembleBrief`（第 250 章） | 13.9ms | <400ms |
| 批量写 250 章正文 | 2780ms | <5000ms |
| 单章追加 | 24.6ms | <50ms |
| 250 章检索 | 6.7ms | <400ms |
| 512KB 素材检索 | 8.6ms | <400ms |
| 带素材 brief | 13.2ms | <400ms |
| 250 章原子导出 | 368ms | <3000ms |
| 子进程 maxRSS | 约 74MB | ≤256MB |

全量 `node storycraft/scripts/ci.mjs`：83 单元 + 29 E2E。

## Consequences

- 250 章读路径（manifest/work/status/brief/listWorks/export）有可重复证据；预算作为回归线，不改变产品上限。
- 现有更严的 100/400/400/50/5000 预算保留，没有因新基准放松。
- 批量追加沿用单次测量（生成成本高），读/导出/内存取 3 次中位数，单章追加取 3 次最小值；口径写在 #87。
- 内存上限 256MB 目前是崩溃护栏，子进程实测约 74MB；后续可据基线收紧。
- 没有生产代码、schema、公开动作或导出格式变更；基准只是测试夹具与断言。
