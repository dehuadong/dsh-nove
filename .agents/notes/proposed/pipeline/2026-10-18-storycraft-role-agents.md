# Agent Note：故事工坊：角色子代理的拆分与交接

## 问题

现在规划、写作、审稿、修订都由主 agent 一次做完：自己写、自己审，判断容易自我确认；上下文里同时塞着大纲、正文、历史审稿，越写越贵；角色边界只存在于技能文字里，没有执行层约束。

产品行为与验收由提案工作项与其切片工作项拥有，不在这里。

## 提案

### 角色与职责

| 角色 | 输入 | 输出 | 只读 | 可写动作 |
| --- | --- | --- | --- | --- |
| 规划 | 意图、真值、卷图、上一卷摘要 | 卷/章纲 | 是 | `story_plan`、`story_volume` |
| 写作 | `story_brief` 的分段、章纲 | 正文 | 是 | `story_write` |
| 审稿 | 正文、真值、质检指标 | 审稿清单 | 是 | `story_review` |
| 修订 | 正文、清单条目、模式 | 新版本正文 | 是 | `story_revise` |
| 归档 | 结算后的章节 | 事件与伏笔 | 是 | `story_state` |

### 交接协议：文件 + 动作，不共享记忆

每个子代理收到三样东西：

1. **任务**：一句话（“审第 12 章，产出问题清单”）；
2. **输入清单**：可以读的作品相对路径（章/纲/真值/摘要）与已派生的只读事实（质检指标 JSON）；
3. **动作子集**：只暴露本角色可用的动作。

产物落盘仍由动作完成。父代理只读产物、不读子代理的推理过程，因此：

- 上下文隔离：审稿看不到写作时的取舍理由，判断更接近读者；
- 失败可回滚：产物没落盘就等于没发生，与现有两阶段提交一致；
- 可并行：同一卷的多个审稿可以并行（不同章），写作用串行。

### 兜底：角色切换

若插件侧拿不到“派生子代理”的能力，用同一套角色定义做**阶段切换**：主 agent 在某一阶段收到该角色的指令段与动作子集（动作子集靠工具可见性无法动态收窄，则靠校验与提示）。接口（角色、输入、输出）不变，后续替换实现不改上层。

### 顺序与理由

1. **审稿**：只读、产出清单、独立判断收益最大、失败不影响正文；
2. **修订**：输入就是清单 + 正文，交接干净；
3. **规划**：上下文独立，可提前给结构建议；
4. **写作**：最依赖用户交互与全量上下文，最后拆。

## 备选方案

- **一次性全拆**：无法逐段验收，回滚代价大；否决。
- **子代理共享主会话上下文**：失去隔离收益，等于换个名字的单代理；否决。
- **子代理直接改文件不走动作**：绕开版本与提交闸门；否决。

## 验收条件

- 探针：插件能派生一个只读子代理，拿到结构化结果（JSON），父代理看不到其推理过程；
- 审稿子代理对同一章产出的清单条目与单代理路径等价（条目 id、可处理性一致）；
- 修订子代理产出的新版本能通过既有闸门，且只改清单点到的地方（patch 模式）；
- 任一子代理失败时，作品目录与进度清单不变；
- 单代理路径仍可用，可在两者间切换。

## 风险

- 每章多 1–2 次模型调用，成本上升；用模式开关控制，默认单代理；
- 子代理与父代理对“当前工作项”的解析要一致，否则会写到别的作品；
- 角色动作子集如果只能靠提示约束，仍可能越权；上线前加动作级校验（如审稿阶段禁止 `story_write`）。
