# Agent Note：故事工坊：作品编排与章节生产动作的技术设计

## 问题

创作型 Agent 需要把「写一部作品」拆成可追溯的动作：立项、章纲、正文、审稿、修订、状态结算。当前只有模式壳（人设、技能、脚本）与一个预设目录页，模型能读到方法，却没有任何动作把结果落到作品目录；页面也没有可读的作品与章节。

本设计要固定在 Harness 现有扩展点上的落法：动作如何在某个模式内可见而不污染其他会话、产物如何落盘并保留版本、页面如何只读地呈现作品并下发指令。产品范围与验收由工作项拥有，不在这里。

约束：

- Harness 只有一个事实来源——落盘产物；动作成功必须带回产物引用。
- 工具按作用域分层：`ctx.tools.register()` 在无作用域上下文注册为全局，在预设的常驻组合里注册只对那个预设生效。
- 页面不直接写文件。写盘只由模型调动作完成，页面最多投递一条用户消息。
- 现有预设 id、技能行与随技能发布的脚本保持不变。

## 提案

### 边界

| 部分 | 职责 | 不负责 |
| --- | --- | --- |
| `dsh-storycraft/tools`（预设内一行） | 注册长篇的七个动作；只在该预设的会话里可见 | 渲染、会话推进 |
| `dsh-storycraft`（bundle 入口） | 只读 HTTP 路由（作品列表、作品、章节、审稿、状态） | 写盘、动作编排 |
| `dsh-storycraft/client`（浏览器半边） | 侧栏入口与工作台页面、指令投递 | 直接改文件、持有第二份数据 |
| 预设行 | 组装人设 + 技能 + 动作子集 | 产品行为定义 |

### 动作与作用域

动作模块由预设挂一行（`dsh-storycraft/tools`，不带配置），因此在预设的常驻作用域里注册：该模式会话可见，其他会话不可见。本次只有长篇预设挂这一行。工具名统一 `story_*` 前缀，输入输出都是 JSON 对象；写盘动作无产物引用的成功不算成功，`story_status` 是只读动作、只返回汇总。工具定义必须落在工具注册表支持的 JSON Schema 子集内（`type/oneOf/properties/required/additionalProperties/items/enum/const` 与注解），其中 `required` 是数组——写错会让整条预设装载失败，因此动作模块自带一份同规则的形状校验。

| 动作 | 输入要点 | 产物 | 失败语义 |
| --- | --- | --- | --- |
| `story_init` | 标题、可选 workId、形态、可选标签 | `manifest.json`、`outline/`、`chapters/`、`reviews/`、`state/`、`hooks.md` | 标题为空，或同 id 作品已存在时拒绝，不覆盖 |
| `story_plan` | 作品 id、章号、五位内容（视角/目标/阻力/代价/结尾变化） | `outline/<章>.plan.md` | 五项缺一即拒绝，不写文件 |
| `story_write` | 作品 id、章号、正文 | `chapters/<章>.md`（或新 revision）、manifest 字数与状态 | 正文为空、章号已存在且未声明改版时拒绝 |
| `story_review` | 作品 id、章号、问题清单（位置/问题/建议） | `reviews/<章>.r<N>.md`，轮次按章独立编号 | 正文不存在、清单为空时拒绝；绝不改正文 |
| `story_revise` | 作品 id、章号、问题条目 id（至少一个）、改后正文 | 新 revision 文件、清单条目标记为已处理 | 没有审稿清单、未给条目、条目不存在、正文与当前版本相同都拒绝 |
| `story_state` | 作品 id、章号、人物事实与伏笔变化 | `state/events.jsonl` 追加事件、重生成的 `hooks.md` | 缺作品或章、状态非法、「已用」指向未埋伏笔时拒绝，不写部分事件 |
| `story_status` | 作品 id | 只读汇总（进度、当前版本、未处理问题、未解伏笔） | 作品不存在时返回结构化错误 |

返回值统一为 `{ ok: true, artifact: { path, revision }, words?, problems? }` 或 `{ ok: false, error: { code, message } }`。写盘动作的 `path` 相对工作区根、用 `/` 分隔，便于页面与 git 使用；只读的 `story_status` 不带 `artifact`。

### 作品存储

- 路径：`<工作区>/works/<workId>/`，`workId` 由标题生成小写 slug（也可显式指定）；同 id 已存在时拒绝新建。
- `manifest.json`：`{ version, workId, title, form, tags, createdAt, updatedAt, chapters: [{ id, number, title, status: planned|written|reviewed|revised, currentRevision, words, updatedAt }], counters: { reviewRounds, openProblems } }`；`version` 是结构版本；`counters` 每次变更后由磁盘上的审稿文件重算（`reviewRounds` 是各章审稿轮数之和，`openProblems` 是各章**最新一轮**里未处理的条目数），不手工累加。
- 章节文件：`chapters/ch-0001.md` 为首版；修订写 `chapters/ch-0001.r2.md`、`.r3.md`，旧文件不改写；`manifest.chapters[].currentRevision` 指向当前版本。
- 审稿清单：`reviews/ch-0001.r<N>.md`，轮次按章独立编号；条目形如 `- [ ] Q1 :: 位置 :: 问题 :: 建议`（`::` 分隔便于解析），修订完成后原地把对应条目标为 `[x]`。
- 状态：`state/events.jsonl` 追加带章号的事件（人物事实、伏笔 opened/used/resolved），`hooks.md` 由事件折叠后重生成；`story_status` 与工作台都从事件折叠，不维护第二份状态。
- 原子性与回滚：写文件先写 `<目标>.tmp-<随机后缀>` 再 `rename`；manifest 最后写。提交失败或任一步出错时，本次新增的文件被删除、被改写的文件恢复原内容，作品回到动作开始前的自洽状态。
- 单写者：变更动作全程持有 `<works>/.<workId>.lock`（排他创建），提交 manifest 时再校验 `updatedAt` 与读取时一致；两步任一失败都返回 `work-busy`，不合并、不覆盖。

### 页面数据与指令

- 只读路由（`dsh-storycraft` 入口行注册，`kind: 'exact'`，前缀 `/api/dsh-storycraft`）：`/works?root=`、`/work?root=&id=`、`/chapter?root=&id=&chapter=&view=body|plan&revision=`、`/review?root=&id=&chapter=`，外加诊断用的 `/roster`、`/document`。全部只读、无副作用，沿用同源 cookie + 仅本机策略，失败统一为 `{ ok:false, error:{ code, message } }`。
- `root` 由浏览器给出，宿主只用自己工作区注册表认识的目录放行，避免把只读接口变成任意目录读取器。
- 页面用这些路由渲染列表、正文、审稿清单与状态；不订阅会话事件，不缓存成第二份事实。
- 指令下发：按钮把一条文本消息投递给当前会话（会话控制器在客户端暴露的消息投递接口，排队模式；具体命名空间以宿主实际暴露为准），由该会话的模型调动作完成动作。页面不判断"该写什么"，只表达意图（写下一章 / 审稿 / 按清单修订 / 结算状态）。
- 章节预览的渲染：Markdown 在页面内渲染（标题、段落、分隔线、引用、列表、代码块），不引入外部渲染库；未知语法按纯文本段落显示。

### 兼容与迁移

- 现有预设 id（`storycraft-longform` / `storycraft-shortform` / `storycraft-screenplay`）不变；技能行与三个脚本保留。
- 预设目录页不再作为独立页面：工作台无作品时呈现模式说明，有作品时呈现编排。原页面移除，避免两处展示同一份事实。
- 短篇/剧本预设本次只保留模式与技能，不挂动作；工作项把它们的动作列为后续范围。
- 入口行依赖 `webServer`：不组合 Web 的部署里入口行不激活，页面与只读路由缺席，而预设内的动作行是独立模块、照常挂载，动作仍可用。
- 没有当前会话、或当前会话不是长篇模式时，指令按钮点击后只说明原因、不投递，也不猜测目标会话；长篇预设装载失败时，工作台在顶部显示宿主给出的失败原因。
- 现有的预设名册与声明诊断路由（`/api/dsh-storycraft/roster`、`/document`）保留为排错入口，不参与作品编排。

## 备选方案

- **只靠文件约定，不注册动作**：模型用现有文件工具直接读写作品目录。放弃原因：没有产出校验、没有版本切换、没有结构化结果，审稿与修订无法区分"成功"与"看起来写了"。
- **页面直接调宿主接口写文件**：少一层模型调用、响应更快。放弃原因：写盘绕过模型与审稿动作，产物无法追溯到一次具体创作决定，也违反"页面只读、动作由模型发起"的约束。
- **全局注册动作，用提示词区分形态**：实现最省事。放弃原因：所有会话的工具面都会被故事动作污染，且不同形态的输入契约不同，一个全局工具无法既做长篇又做短剧。
- **每步一个子代理**：立项、章纲、正文、审稿各起一个子代理。放弃原因：每步都要重新装配上下文，状态传递只能靠文件，收益低于成本；本设计用同一会话内顺序动作，必要时由技能指导再分派。
- **作品数据进数据库**：放弃原因：产物需要人可读、可 diff、可外部编辑；文件是唯一事实来源，索引只在需要时重建。

## 验收条件

- 动作模块在临时目录上可独立测试：原子写失败后目录无半成品；revision 递增且旧文件不被改写；manifest 与文件一致。
- 作用域验证：同一部署里，故事模式会话的工具列表含 `story_*`，非故事模式会话不含。
- 路由契约：四个只读路由对不存在的作品返回结构化错误而不是 500；对存在作品返回与文件一致的内容。
- 端到端：一次会话完成立项 → 章纲 → 正文 → 审稿 → 修订 → 状态结算后，页面能读到每一步产物，且 `git diff` 只有新增/改写的产物文件。
- 失败注入：并发写、章号重复、条目不存在三类输入都返回结构化错误，磁盘不变。

## 风险

- **模型不按动作走**：模型可能用文件工具直接写正文，绕过 manifest。缓解：预设人设与技能明确规定"正文只能由动作落盘"；`story_status` 与页面以 manifest 为准，绕过动作的作品在页面上显示为未登记章节。
- **会话式指令的不可确定性**：按钮投递的是自然语言，模型可能选择别的动作。缓解：指令文本由插件固定，且工具描述写明触发条件；验收以产物为准，不以对话文本为准。
- **长章节与上下文**：整章正文经工具入参传递，长章会占用上下文。缓解：先落盘再引用路径，后续章节写作按路径读取；必要时分场景写。
- **并发与多窗口**：同一作品被两个会话同时写。缓解：单写者锁 + `updatedAt` 校验，失败即报错。
- **路径与权限**：作品根留在工作区内，受 Workspace 与文件沙箱约束；跨工作区访问未在本次范围内。
- **schema 演进**：manifest 与状态结构后续会变；缓解：`version` 字段，读到不支持的版本时拒绝并报错（迁移在需要时另行设计），不改写历史文件。
