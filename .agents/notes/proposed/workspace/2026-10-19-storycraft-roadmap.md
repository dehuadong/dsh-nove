# Agent Note：故事工坊：路线图（角色化、输入契约与后续阶段）

> 本文件是长期跟踪表，不随交付迁移 lifecycle。

## 问题

角色化、提纲、质量层、形态、检索这些工作分别由不同提案推进，但**没有一张共同的路线图**：不知道哪些已交付、哪些在飞、下一个阶段依赖什么。缺少它，计划项会变成遗忘项。

## 2026-10-23 对拍复核

按 `inkos-master` 2.0.0 与 `docs/report/inkos` 复核后，三条主线需要修正：

- **Skill / 资源**：R6a 已补长篇 foundation / 读者承诺 / 状态投影三份方法参考；仍没有拆稿分析与市场研究方法。
- **Agent 编排**：委派只到 writer / reviewer / reviser / summarizer；writer 的形态路由已由 R6b 接上；`architect`、`planner` 没有委派角色；`story_state` 之后没有 settler 投影与 state validator 对账。
- **形态路由**：委派提示固定写「长篇小说」，短篇/剧本即使走同一套动作，子代理也拿不到形态技能。

详细证据与逐项状态见 `pipeline/2026-10-18-storycraft-parity-matrix.md` 的「2026-10-23 复核」；2.0 源码增量见 `docs/report/inkos/2.0-harness-delta.md`，研究索引见 `docs/report/inkos/readme.md`。

### 实施顺序

1. **R6b 形态路由**：最小改动、直接修短篇/剧本子代理拿错技能的问题；
2. **R9 状态预检已交付**：`story_state` 已有确定性 preflight；R9b 只读语义检查已交付；R11 接自动链路（重算一次、未解决不定稿）；
3. **R6a 方法资源已交付**：三份 references 在 `storycraft-longform-method`，规划、写作、审稿与主编按触发读取；
4. R10 / R11 依赖 R9；R12 依赖 R5；
5. R7 / R7b / R7c / R8 按触发条件推进，不提前铺技能目录。

## 备选方案

- **先做检索（R5）**：没有输入契约时检索结果没有位置可放；已完成，但后续语义重排仍等 R12。
- **先做角色扩展（R7）**：新角色会重复同样的输入问题；先修形态路由与状态对账。
- **一次性重写所有角色的上下文**：无法逐段验收；按角色推进。
- **按 InkOS 每个技能一比一建目录**：分类不同且会拉进市场/封面/翻译；按角色与形态归并。

## 验收条件

1. 路线图里的「已交付」都有工作项与提交记录可查；
2. 「进行中」的每一项都有对应切片工作项；
3. 「后续」每一项都有触发条件；
4. 每次阶段推进后更新本文件，不另起新路线图；
5. Skill / 资源 / 编排类变更必须同时更新对拍矩阵，不只在路线图里记一行。

## 风险

- 路线图变长后容易过期：以「已交付 / 进行中 / 后续」三段维护，过期项直接删；
- R1 的七项是**输入**层的抽象，若某个角色实际不需要某项（例如规划不需要文风），必须在契约里写明「不需要 + 理由」。
- 委派提示里的技能名是硬编码字符串（`delegate.js` 的 `ROLE_META`）；改名或新增形态不会自动同步，需用测试校验技能名与路径存在。
- InkOS 2.0 的 capability / confirmation / skill auto-injection 与我们的宿主闸门模型不同；只借方法与资源组织，不复制其权限层。
