# Agent Notes

本目录保存一类设计文档：影响代码库、且代码和现有文档无法解释其长期价值的技术提案与决定。Agent Note 写清为什么这样设计、真实考虑并放弃了什么，以及决定交付后的后果。目录树和只读导航用于查找记录，分类以 [项目配置](./config.json) 为唯一来源。文档归属与正文写法遵循项目 [文档标准](../../docs/AGENTS.md)；本 README 是记录元数据与生命周期格式的唯一来源，检查器负责校验。

Agent Note 面向后续理解、修改和审查代码的 Agent 与人类维护者，提供跨工作项仍有价值的设计依据。它不是产品用户指南，也不替代代码使用处的行为合同或工作项的执行授权。代码注释可按需链接适用于当前代码的已交付 Note，以补充长期理由；引用规则由项目文档标准统一维护。

## 记录范围与信息归属

新部署的 Agent Notes 由仓库管理根目录的 `.agents/notes/` 统一承载。管理根目录依项目配置确定，不随当前子项目工作目录改变；Git 顶层仅作未明确配置时的查找依据。多上下文共用根级文档归属入口和记录系统，不在各子项目重复初始化。

上下文映射负责领域边界，记录分类仅由本目录 config.json 管理，不自动一项目一分类。同一技术设计与决定在其 Note 中完整说明，其他位置链接；适用的合同、设计输入与约束按项目文档入口读取。注册的位置值以管理根目录为基准，普通 Markdown 链接仍相对所在文件解析。

当代码、测试和现有文档不足以解释长期有用的设计理由时，在同一 PR 或同一交付变更中新增或更新记录；重大未来工作从 proposed Note 开始评审。机械或局部修改无需为凑数量创建记录。分类不是工件类型，也不是必须逐一生成的产物。

工作项拥有本次交付范围、产品行为与验收、评审和批准证据，并从工作项链接到相关 Note。Note 拥有长期有效的技术设计、决定、真实备选与理由，不复制工作项的产品合同或进度，也不为追踪目的反向链接工作项。proposed Note 的验收条件只说明该设计怎样被证明成立；产品验收仍由工作项或已登记的独立产品合同拥有。跨工作项持续生效的行为合同可按需由独立仓库文档拥有。

纯机械编辑、链接修复和格式整理属于文档维护，按请求直接处理并检查，不启动一轮工程规划或新建提案。若文档修改实质改变工程合同，按所改变的合同处理。记录制度不新增批准或执行权限。

## 目录与项目分类

路径为 `{lifecycle}/{category}/YYYY-MM-DD-topic-slug.md`。日期表示首次提出日期，无法核实时使用建档日期并说明。文件名在所有生命周期及分类中唯一，不因状态变化重命名；主题使用小写英文和连字符。分类目录按需创建。

config.json 使用如下结构，示例类别仅展示字段，不是默认分类：

```json
{
  "version": 1,
  "categories": [
    { "id": "example", "name": "项目类别名称", "scope": "覆盖的实际交付对象" }
  ]
}
```

初始化优先复用项目分类；没有时依据项目能力、系统对象和工程范围提出方案，由用户确认。记录选择一个主要类别，跨类别通过链接关联。新增类别只改配置，脚本读取它，校验记录分类；空 categories 可初始化空项目，创建首份记录前必须确定类别。

## 按上下文隔离记录

上下文布局（边界、名称、路径及初始化范围）由用户确定，复用 `GLOSSARY-MAP.md`，扫描到项目不自动初始化上下文。启用 Notes 时，在同一次配置说明中另外确认哪些上下文需要记录、是否需要公共记录区；只确认尚未确定的部分。新增上下文不自动启用记录。

根级 config.json 可增加 `contextMap`（相对仓库管理根目录）和 `recordRoots`（仅登记已选记录范围）。例如，下例表示用户已选择 ordering 的记录和公共记录，其他上下文未启用：

```json
{
  "version": 1,
  "categories": [],
  "contextMap": "GLOSSARY-MAP.md",
  "recordRoots": [
    { "context": "ordering", "name": "订购", "path": "ordering" },
    { "context": null, "name": "公共决定", "path": "shared" }
  ]
}
```

这是配置格式示例，不是默认选择；分类沿用项目配置。context 使用映射中已确定的标识，null 表示用户选定的公共记录区。path 是 `.agents/notes/` 内唯一的一级目录名（小写字母、数字及连字符），不能使用生命周期名或 templates。每个上下文及公共范围只有一个记录目录；目录位置不随子项目工作目录改变。

新记录路径为 `{recordRoot}/{lifecycle}/{category}/YYYY-MM-DD-topic-slug.md`。先登记，首份记录需要时再创建目录。目录树是清单；`node scripts/decisions/list.mjs --context ordering`（将 ordering 替换为已配置标识）只读列出对应上下文目录；`--shared` 和 `--legacy` 分别选择公共区与旧根目录记录。阅读时按当前上下文及选定公共区定位相关记录。跨上下文决定选定一个公共区或参与上下文作为属主，其余位置引用；没有适合的已选属主时先解决归属选择。

不配置 recordRoots 时保持原有单目录行为；空数组表示未新增上下文记录目录。原有 `{lifecycle}/{category}/...` 记录继续保留并可由 `list.mjs --legacy` 定位，不因新增映射而移动或改写。历史迁移需明确授权并修复引用。上下文与分类独立，不从项目目录自动生成分类。

脚本检查映射文件存在和记录目录配置；上下文标识是否忠实于映射、启用范围是否经用户选择由审阅核实，不通过解析任意格式的 Markdown 推断授权。

## 生命周期与批准

| 目录与 `status` | 含义 |
| --- | --- |
| `proposed/`：`proposed` | 实施前评审的设计提案；尚未交付或仅部分交付，记录备选、设计验收与风险。 |
| `implemented/`：`implemented` | 决定已交付并完成必要验证；记录实际决定、放弃的方案和后果，与交付事实保持一致。 |
| `rejected/`：`rejected` | 提案已否决；仅在理由还能防止诱人且影响重大的错误时保留。 |

批准依据与生命周期分开，由工作项按项目约定维护；执行授权另行判断。批准不能自动进入 implemented，测试通过也不能自动批准。没有充分交付证据时保留 proposed。未实施的提案被否决才进入 rejected；已交付决定后续被推翻时，由新 Note 记录新决定，不把旧记录改写成相反结论。

所有记录统一使用 UTF-8 Markdown 和一行一个 `key: value` 的简单元数据，不使用嵌套 YAML、引号语法或项目自定义字段。字段顺序固定：`title`、`status`、`created`、`updated`，然后按状态添加 `verification` 或 `reason`。`proposed` 只使用前四项；`implemented` 必须添加 `verification`；`rejected` 必须添加 `reason`。批准证据由工作项维护，不在 Note 中复制。日期为 YYYY-MM-DD，`created` 与文件名日期一致，`updated` 在实质变更时更新。

例如，一条已交付记录的元数据块为：

```yaml
title: 记录标题
status: implemented
created: YYYY-MM-DD
updated: YYYY-MM-DD
verification: 实际验证证据
```

2026-09-22 前创建、原始材料无法还原真实备选方案的历史记录，可以用以下注释代替 `## 备选方案`；不得用于新记录：

```markdown
<!-- agent-note-format: alternatives-not-recorded (pre-format Agent Note) -->
```

元数据块后第一个非空行必须是 `# Agent Note：<title>`，标题与 `title` 一致；正文首节固定为 `## 问题`。`proposed` 必须含 `## 提案`、`## 备选方案`、`## 验收条件`、`## 风险`；`implemented` 必须含 `## 决定`、`## 备选方案`、`## 后果`、`## 验证`，且不得保留提案、计划、迁移计划或验收条件章节；`rejected` 必须含 `## 提案`、`## 备选方案` 并保留提案正文。只写真实考虑过的备选方案；历史证据缺失时如实说明，不补造依据。检查器校验格式和章节存在，内容真实性仍由审阅负责。

新建 `proposed` 记录可复制 [record.md](./templates/record.md) 作为起点，填写真实内容并按已选分类与上下文存放。本 README 拥有格式和生命周期规则；模板不另设规则。

状态变化在同一变更中完成文件移动、status 更新、按实际结果改写正文及入站/出站链接修正。检查目标冲突；拒绝时记录原因。implemented Note 的路径、名称、默认值与机制等交付事实随实现同步更新，不积累变更流水；决定或理由反转时新建 Note，并让新旧记录相互链接。部分替代时保留两份记录并写清各自仍适用的范围。完全替代且旧记录不再有独立价值时，先将所有独有的理由、备选、后果、必要验证和覆盖缺口并入新属主，修复入站链接，再删除旧记录；不能只依赖 Git 历史保存这些依据，无法确认价值或引用时保留并说明。

## 总体方案、阶段和模块工程

总体提案拥有目标、范围、阶段划分、依赖和阶段验收条件，链接阶段工作项及模块工程。提案与进度由已配置的跟踪器管理，本地 Markdown 也需明确配置，不在每层复制合同。

模块工程遵循项目指令规定的推进权限，记录系统不另设阶段编排或授予阶段切换权限。阶段完成还需要集成和阶段验收，不能只累加模块完成状态。覆盖总体范围的变更记录在全部交付前保持 proposed，独立下级记录可以先进入 implemented；Proposal 本身使用跟踪器工作状态。只有包含独立重要决定的模块才另建记录，不机械要求一模块一 Note。

## 更新责任与文件边界

同一决定的事实修正和必要补充更新原记录；可独立判断的新选择另建记录；实质改变已接受决定时新建替代记录，保留历史理由。记录不积累会议纪要、完整实现清单或测试日志。

| 阶段 | 动作 |
| --- | --- |
| Discuss / Planning | 查已有合同与相关记录，仅在项目授权范围内形成必要提案和未决事项 |
| Plan Review | 结论与批准证据写回本次工作项；实质设计结论同步写入 Note |
| Implement | 同一变更维护事实与引用，重大合同变化按项目权限规则停止受影响工作并交还用户决定 |
| Implementation Review | 核对范围、实现与记录一致，必要维护已完成 |
| Verify | 验证交付范围，据实迁移生命周期并引用证据 |

只检查相关记录，不要求每个任务遍历全部历史。日常文档治理不受上表的工程阶段序列约束。

## 导航与检查

从项目根目录运行，使用 Node.js，无第三方依赖：

```sh
node scripts/decisions/check.mjs
node scripts/decisions/list.mjs --context ordering
```

不生成 `INDEX.md`；根级和上下文目录中的旧索引应在修复活动链接后移除。`list.mjs` 只输出目录导航，不写文件。检查覆盖配置、目录与生命周期一致性、必要元数据、日期、文件名唯一性和内联本地链接目标。关联工作项的本地链接同样检查；远程目标、标题锚点、批准真实性、实际交付是否充分及替代关系语义仍由审阅判断。代码示例中的链接不检查。

脚本不自动批准、迁移状态或修改决定，不默认安装 CI、钩子或外部发布。初始化资源部署后属于项目副本；重复 setup 不覆盖，升级时保留项目分类和定制。既有项目使用旧元数据格式时，须在明确授权的升级中同步调整记录与检查器。
