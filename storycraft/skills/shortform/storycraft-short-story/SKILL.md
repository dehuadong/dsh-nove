# 短篇小说写法

形态：`story_init` 的 `form: "short"`。章节单位是「篇」；同一套动作，步骤更短（篇纲 → 正文 → 审稿 → 修订 → 摘要 → 定稿），通常一篇写到底。

短篇不是压缩的长篇。它只允许一个核心转折、一条主线和一次结尾回响。写第二转折之前先确认第一个转折已经用尽。

## 开工前定三件事

1. **一句话故事**：谁在什么处境下想要什么，什么挡住他，最后他付出了什么。写成一句，不超过四十字。
2. **转折位置**：核心转折通常落在大约三分之二处。先定位置，再安排前面的铺垫。
3. **结尾形状**：回环（回到开头场景）、反转（重新解释前文）、留白（状态悬置）三者选一，不要都想要。

三件事没有定下来就直接写，几乎一定写成中篇的开头。不确定时先给用户两到三个一句话方案挑一个。

## 先讨论，后立项

作者用自然语言提想法时，**先讨论**：前提、主要人物、核心冲突、想写的体验，优先复用作者已经说过的内容。讨论阶段不写任何文件，也不调用 `story_init`。

方向成熟后，用 `story_propose` 落一份建项方案（标题、形态、一句话前提、主要人物、冲突、约定），把方案讲给作者看，**等作者明确同意**后再 `story_init`（带 `proposal`）。立项完停下，等作者决定要不要写第一篇。

## 写作流程

1. **开头**：第一段就要有具体场景与不稳定因素，不要从天气、回忆、自我介绍开始。
2. **中段**：每一场都推进“主角离目标更近一步但代价更大一点”。重复同一种阻力的场景要合并或删掉。
3. **转折**：转折必须由前面的具体细节支撑，不能靠临时新增的巧合或新人物。
4. **结尾**：回响靠呼应开头的物件、动作或一句话，不靠总结感慨。

## 输出契约

- 正文通过 `story_write` 落库；委派时通过 `story_submit {title,body}` 提交，一次成篇，不写“上/下”。
- 不要再写 `stories/*.md` 或 `stories/*.notes.md`：作品只存在 `.storycraft/works/<workId>.db`，文件路径不会进库。
- 一句话故事、转折位置、结尾形状写在提案 brief 或作者对话里；需要时用 `story_plan` 落篇纲。
- 不写标题党式标题；标题从正文里的具体物件或动作里取。

## 自检清单

- 删掉第一段，故事还能成立吗？能就删。
- 有没有第二转折在抢第一个转折的分量？有就砍。
- 结尾的最后一句是否回到了开头出现过的具体物象？
- 全文是否有超过三句的说明性背景（历史、设定、心理总结）？有就压到一句或改写成场景。
- 主角在结尾的状态，与开头相比是否有一个不可逆的变化？

## 脚本

`scripts/story-metrics.mjs` 统计字数、段落数、对话占比与场景数，用来判断节奏是否失衡（对话过多、段落过长、场景过碎）。

这是**作者侧离线工具**：先从面板导出或复制正文到临时文件，再运行；委派子代理不写文件，正常流程用 `story_critique`。

```bash
node <技能目录>/scripts/story-metrics.mjs <正文文件>
```
